# Доступ к домашнему хосту (Synology) — что реально закрывает

> Не юридическая консультация. Памятка для личного стенда kppdf (домашний Synology + внешний мост).
> Обновлено: 2026-08-10 (разбор «публичность» / Basic Auth / Cloudflare Access / VPN).

## 1. Юридический ориентир (кратко)

По факту для РФ важнее **доступность неограниченному кругу лиц**, а не надпись на странице.

| Мера | Делает ресурс «непубличным»? |
|------|------------------------------|
| Текст «личный учебный / не коммерческий» | **Нет** — декларация намерений |
| `robots: noindex, nofollow` / robots.txt | **Нет** — только сигнал поисковикам |
| Angular `authGuard` (контент за логином) | **Недостаточно** — `/login` и сам HTTP-ответ всё ещё видны всем |
| Сетевой барьер до приложения (VPN / Access / Basic Auth / allowlist) | **Да, по смыслу** — доступ не у «всех подряд» |

Итог: дисклеймер + robots **не выводят** сайт из зоны «ресурс в интернете». Спокойный сон = **техническое** ограничение круга лиц, а не табличка.

### Основные риски, пока порт/домен торчит наружу

1. **Фасад публичный:** любой может открыть URL, увидеть форму, зондировать стек (сканеры, боты).
2. **Брутфорс / credential stuffing** по `/login` и API auth — даже без «взлома Angular».
3. **152-ФЗ (ПДн):** логины, cookies, логи доступа — обработка; при утечке/жалобах «учебность» не освобождает автоматически.
4. **Контент и ответственность владельца:** пока мало контента снаружи — риск ниже; но сам факт открытого сервиса + домен усиливает интерес сканеров и будущие претензии, если появится чужой/спорный контент.
5. **Домашний IP / Synology за мостом:** сканирование = лишний шум на NAS, риск смежных сервисов, если мост шире нужного.
6. **Ужесточение практики:** закон может меняться; опираться на «мы написали, что непубличные» — слабая позиция. Опора — **фактический** закрытый доступ.

ORI / тяжёлые режимы для мессенджеров обычно не про одностраничный личный CRM, но это **не** аргумент держать `/login` открытым всему интернету.

## 2. Что уже есть в приложении

- ERP за `authGuard` — без логина контент не открывается.
- Публично обычно торчит `/login` + факт, что порт/домен доступен из интернета.
- Текст на `/login` и `robots noindex` — **пояснение для приглашённых**, не замок (см. TZ-AUTH-301).

## 3. Три рабочих варианта (без зависимости от офисного IP)

Критерий PO: заходить с любого устройства; посторонние **не видят даже** `/login`; IP allowlist — не основной путь.

### A. HTTP Basic Auth (Nginx / Caddy / Synology Application Portal)

| | |
|--|--|
| **Суть** | До Angular — второй пароль (или htpasswd). Без него — 401, страницы входа нет. |
| **Публичность** | Сильно сужает круг: «кто угодно с URL» → «кто знает секрет». Юридически ближе к закрытому доступу, чем один только app-login. |
| **Плюсы** | ~10–30 мин; бесплатно; работает при port forward, VPS-прокси, частично на Synology. |
| **Минусы** | Секрет надо раздать 1–2 людям; UX грубее Access; пароль в менеджере паролей / браузере. Не заменяет TLS и сильный app-пароль. |
| **Когда** | Мост = прямой проброс или VPS+nginx **без** Cloudflare Tunnel. Быстрый первый барьер. |

### B. Cloudflare Access (если Cloudflare Tunnel)

| | |
|--|--|
| **Суть** | Перед приложением — вход по e-mail (OTP / IdP). Политика: allowlist e-mail автора + 1–2 доверенных. |
| **Публичность** | Один из лучших «бесплатных» вариантов: посторонний без приглашённой почты **не** доходит до `/login`. |
| **Плюсы** | ~10–20 мин если Tunnel уже есть; Zero Trust Free; с телефона/офиса/дома одинаково; **без** IP. |
| **Минусы** | Нужен Cloudflare Tunnel (или прокси через CF). Зависимость от CF. |
| **Когда** | Мост уже через Cloudflare Tunnel — **делать первым**. |

### C. VPN only (Tailscale / WireGuard) — сайт не в публичный интернет

| | |
|--|--|
| **Суть** | Убрать port forward / публичный туннель к веб-UI. Доступ только из overlay-сети (Tailscale) или WireGuard в дом. |
| **Публичность** | Максимально близко к «не публичный ресурс»: с интернета нет HTTP-ответа на имя/порт приложения. |
| **Плюсы** | Лучший дефолт для спокойствия; 1–2 человека = share node / peer; телефоны ок; без IP allowlist. |
| **Минусы** | На каждом устройстве клиент VPN; DNS/имя внутри сети; если нужен редкий «показать коллеге без VPN» — неудобно (тогда временно Access/Basic, не открывать навсегда). |
| **Когда** | Целевое состояние личного стенда. Tailscale на Synology обычно проще WireGuard «с нуля». |

### Сводка

| Вариант | Скорость | Без IP | Прячет `/login` | «Не публичный» по факту |
|---------|----------|--------|-----------------|-------------------------|
| Basic Auth | ★★★ (~10–30 мин) | да | да | сильно лучше, чем ничего |
| Cloudflare Access | ★★★ (если Tunnel есть) | да | да | да |
| VPN only (Tailscale) | ★★ (вечер) | да | да (снаружи нет сервиса) | максимум |

IP allowlist — только запасной костыль, не стратегия (офисный IP плавает).

## 5. Фактический мост kppdf-8.0 (канон из deploy)

Source of truth: [`deploy/synology/DEPLOY.md`](../../deploy/synology/DEPLOY.md).

```
Интернет
  → DNS kppdf-crm.ru → VPS 193.222.62.240
  → nginx:443 (Let's Encrypt, конфиг /etc/nginx/sites-available/kppdf-proxy)
  → proxy_pass http://127.0.0.1:4200
  → SSH reverse tunnel (autossh / kppdf-tunnel с VM)
  → Ubuntu VM на Synology 192.168.1.103:3000 (Docker kppdf-backend + mongo)
```

Это **не** Cloudflare Tunnel. Упоминание cloudflared в `CREDENTIALS.example.md` — legacy из kppdf-3.0; для v8 канон = VPS + SSH `-R`.

| Мера | Под вашу схему |
|------|----------------|
| **1-я (сегодня)** | HTTP Basic Auth **на VPS nginx** перед `proxy_pass` |
| Cloudflare Access | Не «из коробки» — нужен перенос DNS/прокси на Cloudflare |
| Цель (неделя) | Tailscale на VM/Synology → при желании свернуть публичный nginx к приложению |

## 6. Чеклист: Basic Auth на VPS (~15 мин)

SSH: `ssh root@193.222.62.240` (секреты в gitignored `deploy/synology/CREDENTIALS.md`).

1. [ ] Создать пароль (только вы + 1–2 человека; хранить в менеджере паролей):
   ```bash
   apt-get install -y apache2-utils
   htpasswd -c /etc/nginx/.htpasswd-kppdf YOUR_LOGIN
   # для второго человека: htpasswd /etc/nginx/.htpasswd-kppdf OTHER_LOGIN  (без -c)
   chmod 640 /etc/nginx/.htpasswd-kppdf
   ```
2. [ ] В `/etc/nginx/sites-available/kppdf-proxy` внутри `server { … 443 … }` добавить **до** `location`-блоков (или в каждый `location /` и static — проще в `location /` и в static location):
   ```nginx
   auth_basic "Private";
   auth_basic_user_file /etc/nginx/.htpasswd-kppdf;
   ```
   Практично: поставить эти две строки в `location /` **и** в `location ~* \.(js|css|…)` — иначе статика отдастся без пароля (менее критично, но лучше закрыть).
3. [ ] Не закрывать Basic Auth на `location = /robots.txt`, если хотите оставлять noindex снаружи — по желанию; для «не публичный» можно закрыть и его.
4. [ ] Проверка конфига и reload:
   ```bash
   nginx -t && systemctl reload nginx
   ```
5. [ ] С телефона / инкогнито (без сохранённого пароля):
   - `https://kppdf-crm.ru/` → браузер просит логин/пароль Basic;
   - без пароля — **нет** Angular `/login`;
   - с паролем → обычная форма входа приложения.
6. [ ] С офиса/дома убедиться, что app-login (admin) по-прежнему работает после Basic.
7. [ ] Health снаружи без Basic должен давать 401:
   ```bash
   curl -sI https://kppdf-crm.ru/api/health/ready
   # ожидаем HTTP/2 401
   curl -sI -u 'LOGIN:PASS' https://kppdf-crm.ru/api/health/ready
   # ожидаем 200
   ```

**Не делать:** IP allowlist офиса как основную меру; Cloudflare Access «на авось» без смены моста; открывать `:3000` VM в интернет.
