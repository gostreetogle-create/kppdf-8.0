## 0. Правило продукта (канон)

1. **Раздел = продукт внутри продукта.** Пока раздел не в статусе **READY TO USE**, менеджеры туда **боевые данные не кладут** (только смоук/песочница).
2. **Деплой после READY** обязан быть **аддитивным**: новые экраны/поля — ок; ломающие миграции SoT без миграционного плана — запрещены без явного PO.
3. **Автоматизация «галочка → само на склад»** — nice-to-have **после** ручного приход/расход. Не блокирует READY.
4. Статусы ниже — про **пользовательский контур** (UI + стабильный API + понятный SoT), не про «в репо есть файл».

### Статусы

| Статус | Значит |
|--------|--------|
| **NOT STARTED** | Нет рабочего UI или SoT неясен |
| **SHELL** | Смотреть можно, писать нельзя / писать опасно |
| **MVP BUILD** | Идёт доводка до READY |
| **READY TO USE** | Можно вести боевые данные; обновления не должны ломать контур без миграции |
| **HARDENING** | Уже пользуемся; допиливаем ACL/автоматизацию/удобство |

## 2. Склад — критерий READY TO USE

**Минимальный смысл склада для цеха:**  
положить → забрать / скорректировать → видеть, что осталось и что происходило.

### Must-have (без этого — не READY)

| # | Критерий | Сейчас |
|---|----------|--------|
| W1 | Реестр складов: создать / переименовать / зоны / активен | ✅ `/warehouses` |
| W2 | Остатки по складу × материал/продукт (таблица) | ✅ |
| W3 | Поставить на склад (создать позицию / начальный qty) | ✅ dialog на Остатках |
| W4 | Приход / расход (движение с записью в журнал) | ✅ dialogs на Движениях |
| W5 | Корректировка qty с причиной | ✅ Остатки ✎ + Движения «+ Корр.» |
| W6 | Журнал движений с фильтром типа | ✅; фильтр склада — TZ-WAREHOUSE-UX-301 ✅ |
| W7 | SoT количества = `StorageItem` / движения; не `Material.stockQty` | ✅ |
| W8 | Документ/smoke: менеджер проходит сценарий без консоли | ⚠️ UI готов — smoke у PO |

### Should-have (можно HARDENING после старта)

| # | Критерий | Сейчас |
|---|----------|--------|
| W9 | Ответственный за склад + write только ему/admin | ❌ vision |
| W10 | Worker видит только «свой» склад | ❌ vision |
| W11 | Авто-списание при завершении вида работ / заказа | ❌ позже |
| W12 | Перемещение между складами UI | ⚠️ API type=transfer |
| W14 | Дашборд без дубля TOC-кнопок; подсказка типа склада | ✅ TZ-WAREHOUSE-UX-301 |

### Запрет после READY склада

- Менять уникальность `(warehouse, material|product, zone)` без миграции.
- Возвращать остаток в `Material.stockQty` как SoT.
- Удалять движения без явной политики (soft / reverse).

**Vision / очередь:**  
`docs/superpowers/specs/2026-08-05-warehouse-workshop-vision.md`  
`docs/superpowers/specs/2026-08-05-warehouse-ui-design.md`

**Статус:** must-have W1–W7 закрыты в UI; W14 (dedupe + type help) — TZ-WAREHOUSE-UX-301. Перед боевым Excel-заменителем — 5‑минутный smoke (W8): создать склад → поставить материал → приход → расход → корректировка → проверить журнал (с фильтром склада).

## 3. Каталог — кратко

| Must до «можно жить» | Сейчас |
|----------------------|--------|
| Материалы CRUD + фото/поля | ✅ сильно продвинуто |
| Продукция / модули списки + composition | ⚠️ BE/FE волнами |
| Связь «материал → остатки склада» ссылкой | ✅ `Склад →` |
| Не дублировать складской qty в карточке материала | ✅ |

Каталог **не** блокирует склад READY: склад опирается на ID материала/продукта из каталога.

---

## 4. Справочники — кратко

Группы chips + категории/цвета/единицы — **можно пользоваться** для поддержки каталога.  
Не смешивать реестр складов сюда (дом складов — раздел Склад).

---

## 5. Документы — кратко

Шаблоны/builder — витрина; боевые сгенерированные документы — отдельно.  
Не смешивать с READY склада.

---

## 6. Как агент отвечает PO

На вопрос «чем можно пользоваться?» / «что осталось по складу?»:

1. Открыть **этот файл** §1 + нужный раздел.  
2. Назвать статус одной фразой.  
3. Перечислить **открытые must-have** чекбоксами.  
4. Не обещать READY, пока must-have не закрыты и не прогнан W8 smoke.

При закрытии must-have — **обновить таблицу §1 и §2 в том же PR/сессии**.
