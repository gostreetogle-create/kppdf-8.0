## IDEA-001 — Универсальное сохранение данных предприятия (portable export)

**Дата:** 2026-08-19  
**Статус:** идея, требует проектирования формата  
**Приоритет PO:** высокий по ценности, но не срочный — «копить правильно уже сейчас, реализовать когда созреет»

### Проблема

Со временем в ERP накапливаются ценные данные: товары, материалы, категории, привязки, контрагенты, фото, справочники, документы. Люди тратят часы на аккуратное заполнение. Если случится откат, поломка сайта, смена хостинга или решение поднять «новый сайт с нуля», текущие ops-бэкапы (`deploy/synology/backup.sh` — Mongo + uploads) восстанавливают **эту же** инсталляцию, но не дают гарантии **лёгкой переносимости** в другую систему, другую схему или ручной контроль PO.

Нужен слой **«данные предприятия в чистом, универсальном виде»** — отдельно от технического snapshot сервера.

### Цель

1. **Накопление без потерь:** по мере работы данные можно периодически выгружать в формат, который PO хранит локально (диск, NAS, облако вне продакшена).
2. **Disaster recovery:** при любой аварии — восстановить бизнес-содержимое, а не только «поднять тот же Mongo».
3. **Миграция:** те же файлы должны **легко ложиться** на новую инсталляцию kppdf или (в перспективе) другой стек — в т.ч. с помощью ИИ-агента, который «скачал → перелил → проверил целостность».
4. **Целостность медиа:** фотографии и вложения не оторваны от записей; связи однозначны (по стабильным id или согласованным именам/путям).

### Два целевых формата (оба желательны)

#### Вариант A — «Универсальный пакет данных» (machine-first)

Структура каталога (черновик, уточнить в TZ):

```
kppdf-export-YYYY-MM-DD/
├── manifest.json          # версия схемы, дата, checksums, список сущностей
├── data/                  # нормализованные JSON/NDJSON по сущностям
│   ├── products.jsonl
│   ├── materials.jsonl
│   ├── categories.jsonl
│   ├── counterparties.jsonl
│   └── …                  # полный перечень — из domain preflight
├── media/
│   ├── photos/            # файлы; имя = stableId или manifest.photoId → path
│   └── documents/         # если применимо
└── relations/             # явные связи many-to-many, если не вложены в сущности
    └── product-category.jsonl
```

**Требования к формату:**

- Стабильные **business keys** (slug, артикул, внешний код) **и/или** export-id — чтобы при re-import не было «висящих» ссылок.
- Явная **версия схемы export** (`exportSchemaVersion`) — для эволюции без поломки старых архивов.
- **manifest** с checksum файлов и счётчиками записей — быстрая проверка «архив цел».
- Пути к медиа **относительные** внутри пакета; при импорте — remap в storage новой инсталляции.
- Импорт **идемпотентный** где возможно (upsert по stable key).

**Сценарий PO:** скачал zip → положил в сейф → через год новый сервер → агент/скрипт импорта восстанавливает каталог + фото одним проходом.

#### Вариант B — «Excel для людей и ИИ» (human-first)

Один `.xlsx` (или набор связанных файлов), **вкладки = сущности**:

| Вкладка (пример) | Содержимое |
|------------------|------------|
| Товары | id, артикул, название, категория (ref), ед. изм., … |
| Категории | id, родитель, название, … |
| Материалы | … |
| Контрагенты | … |
| Связи | productId ↔ categoryId, … |
| Медиа | entityType, entityId, fileName, relativePath |

**Требования:**

- Заголовки колонок **стабильные и документированные** (глоссарий в README внутри zip или отдельный лист «_schema»).
- Ссылки между вкладками — по **явным id**, не по «красивым названиям» (название может дублироваться).
- Фото: либо отдельная папка `media/` рядом с xlsx в zip, либо лист «Медиа» + общий архив.
- Экспорт должен быть **обратимо импортируемым** скриптом или ИИ: «отдал Excel + папку фото → получил базу».

**Сценарий PO:** открыл в Excel, проверил глазами, отдал агенту «накати обратно» — без ручного копипаста по сотням строк.

### Что спроектировать до первой реализации

1. **Перечень сущностей** для v1 export (не «вся Mongo», а осмысленный минимум: каталог, материалы, контрагенты, справочники, медиа — сверка с `docs/data-model.md` и живым кодом).
2. **Stable key policy:** что считается первичным ключом при re-import (`_id` Mongo vs артикул vs slug).
3. **Частота и триггеры:** ручная кнопка «Скачать архив», nightly job, перед deploy/wipe (см. `docs/ops/DANGEROUS-OPS.md`).
4. **Размер и инкременты:** полный vs дельта с `since` (на будущее).
5. **Секреты и ПДн:** что **не** попадает в export (пароли, токены, audit с персональными данными сверх нужного).
6. **Связь с ops-backup:** portable export **дополняет**, не заменяет `backup.sh`; в доке явно развести роли.

### Критерии «идея реализована» (для будущего TZ)

- [ ] PO может с UI или CLI получить **полный portable-пакет** (A) и **Excel-пакет** (B) без доступа к серверу по SSH.
- [ ] Пакет содержит медиа; checksum/manifest позволяет убедиться в целостности.
- [ ] Документирован **import path** на чистую инсталляцию (хотя бы smoke: N товаров + M фото восстанавливаются).
- [ ] Формат версионирован; старый архив не ломает новый importer (migration note или reject с понятной ошибкой).
- [ ] В runbook есть место для PO: «куда класть локальные копии, как часто».

### Открытые вопросы (для PO / architect session)

- v1 только **каталог + материалы + медиа** или сразу контрагенты/заказы?
- Excel — один файл или zip «xlsx + media» (скорее zip)?
- Нужен ли **шифрование** архива паролем PO (compliance)?
- Export только для **admin** или отдельная capability?

3. Smoke: export → empty DB → import → spot-check в UI.
