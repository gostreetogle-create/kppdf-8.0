=== Diagnostic: why the existing pi-showcase-card `size="sm"` onerror mechanism
    (`mediaBroken` signal + `(error)="onMediaError()"`, already in
    pi-showcase-card.component.ts before this TZ) did not visibly prevent the
    broken icons ===

Forced every `<img>` into view via Playwright `scroll_into_view_if_needed()` (defeats
native `loading="lazy"` deferral) BEFORE the fix:
  img_count_after_settle: 1 (down from 22)
  img_naturalWidth_0_count: 0 (down from 21)
  empty_media_class_count: 66 (up from 45)
  count_404: 55 (up from 34 — forcing intersection triggered more real fetches)

Conclusion: the existing FE onerror mechanism DOES work correctly — it is gated on the
browser actually attempting the image load, which native `loading="lazy"` defers until
real viewport intersection. During a plain settle-and-check (no scroll), most vitrina
cards never got that chance, so the broken `<img>` lingered. This is why the TZ's
explicitly preferred fix (backend existence-check, "единая точка правды") is the right
primary fix — it removes the broken URL before it ever reaches the client, independent
of any scroll/lazy-load timing. No FE code changed (see below) — re-implementing an
onerror handler that already exists and already works would have been pure duplication.

=== ШАГ 1: Backend fix ===

- `document-render.utils.ts`: extracted `localUploadFileExists()` (was a private method
  on `StudioDataResolverService`, third copy of the same logic per the TZ's own
  root-cause note) into a public export, reusing the existing `resolveUploadsRoot()`.
  Added `blankMissingUploadUrls(docs)` — batch helper, dedupes unique storageUrl values
  per call (same dedup pattern as `resolveCatalogPhotoUrls`), blanks `storageUrl` in
  place on any doc whose file is missing.
- `studio-data-resolver.ts`: now imports `localUploadFileExists` from
  `document-render.utils.ts` instead of its own private copy — one implementation, not
  two (was already the plan per this TZ's ШАГ 1 text).
- `product.service.ts` `findAll()`: applies `blankMissingUploadUrls` to all populated
  `photoIds` sub-documents before mapping the response.
- `material.service.ts` `findAll()`: applies `blankMissingUploadUrls` to both populated
  `photoIds` sub-documents AND the populated `mainPhotoId` (material list populates both,
  unlike product).

=== ШАГ 2: Client-side fallback — deliberately NOT re-implemented ===

Per the diagnostic above, `pi-showcase-card.component.ts`'s `size="sm"` branch (the
variant the vitrina uses) already has `(error)="onMediaError()"` → `mediaBroken` signal
→ falls back to the empty-media placeholder, confirmed functionally correct via the
scrollIntoView test. Left unchanged — the backend fix (ШАГ 1) makes `mediaUrl` empty
from the start for the orphan case, which is the actual bug; the existing client
fallback remains valid defense-in-depth for the residual race (file deleted between
request and render).
