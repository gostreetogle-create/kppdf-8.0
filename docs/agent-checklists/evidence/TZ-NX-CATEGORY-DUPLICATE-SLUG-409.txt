=== Root cause (confirmed exactly as TZ described) ===

`Category` has TWO unique indexes: compound `{type, slug}` and a standalone
`skuPrefix`. Neither `CategoryService.create()` nor `.update()` caught a
Mongo E11000 duplicate-key error — it propagated straight to NestJS's
default exception filter as a raw 500 "Internal server error", exactly the
class of bug `ProductService`/`MaterialService` already guard against for
their own unique fields (sku/article).

=== Fix (category.service.ts) ===

1. `create()`: wrapped `this.model.create(...)` in try/catch, delegating to
   a new `rethrowDuplicate()` helper on any error.
2. `update()`: wrapped `doc.save()` the same way (an `update()` that changes
   `slug`/`type`/`skuPrefix` can hit the same unique-index collision).
3. `rethrowDuplicate(err)`: on Mongo code 11000, inspects `err.keyPattern`
   to give a specific, readable RU message — `skuPrefix` collision vs.
   `{type, slug}` collision get distinct messages (mirrors the fact these
   are two independent unique indexes, not one). Any other error is
   re-thrown unchanged (not swallowed).

Per the TZ's "НЕ" list, did not touch the slug DTO's validation rules and
did not add an auto-suffix-on-collision retry (`-2`/`-3`) — the TZ marked
that "опционально", and a clean 409 + the FE's own existing toast (already
confirmed working in WAVE3.2's evidence) is a complete, honest fix without
adding retry-loop complexity nobody asked for.

=== Specs (category.service.spec.ts, new describe block) ===

- `create()` maps a duplicate `{type, slug}` to the readable ConflictException.
- `create()` maps a duplicate `skuPrefix` to its own readable ConflictException.
- `update()` maps a duplicate `{type, slug}` to a readable ConflictException,
  not a raw 500.
- A non-duplicate-key error (plain `Error`) is re-thrown unchanged, not
  accidentally swallowed into a false-positive 409.
