=== ШАГ 2: BE — issuer reassignment ===

`UpdateStudioDocumentDto`: new optional `organizationId` (`@IsObjectId`).

`StudioDocumentService` gained a 6th constructor param, `OrganizationService`
(new `OrganizationModule` import in `studio-document.module.ts` — confirmed
it exports `OrganizationService`, no circular-dependency risk).

`update()`, right after `assertDocTypeForFinal(...)`:
  if (dto.organizationId !== undefined) {
    await this.organizationService.findById(dto.organizationId, { organizationId });
    doc.organizationId = this.toObjectId(dto.organizationId, 'organizationId');
  }
Reuses `OrganizationService.findById(id, user)`'s existing IDOR-safe
visibility check verbatim (unscoped caller sees any org; a caller bound to
one org can only "pick" that same org, else 404) instead of duplicating
the policy inline. Uses the RAW (unresolved) `organizationId` param for
that check — resolving via `resolveOrganizationId()` first would make an
unscoped admin look bound to whatever fallback org that resolves to,
defeating the admin's intended full visibility.

Live curl round-trip (fresh throwaway doc, deleted after):
  - POST /studio-documents -> organizationId = supplier-fallback org
    (revision 1).
  - PATCH {expectedRevision:1, organizationId:<isOurCompany org>} (admin,
    unscoped) -> 200, organizationId updated, revision 2.
  - PATCH {expectedRevision:2, organizationId:'000000000000000000000000'}
    (nonexistent org) -> did NOT reach my new IDOR check as a clean 404 —
    see known_limitation below, it hit a DIFFERENT pre-existing 403 first.

Bound-user IDOR rejection path: NOT separately live-tested (no bound
non-admin test user exists on this dev stand — every seeded account is
either admin or has no organizationId set). Covered by 4 new unit tests in
`studio-document.service.spec.ts` (admin picks any org; bound caller
rejected on a different org via mocked `organizationService.findById`
throwing; bound caller re-selecting their own org is a no-op-equivalent
pass; field omitted from patch leaves organizationId untouched — service
never calls `organizationService.findById` in that case).

=== known_limitation (live-reproduced, WORSE than the TZ's own description) ===

The TZ text says: "после смены issuer документ может «пропасть» из
текущего списка admin, если list всё ещё фильтрует fallback-org." Live
reproduction on the dev stand shows this understates the actual severity:

  1. Created a fresh doc as unscoped admin (organizationId = fallback org,
     "АО «Лакокраска-Сервис»", via `resolveOrganizationId`'s
     alphabetical-first-by-name default).
  2. PATCH organizationId -> an `isOurCompany` org ("Самопроверка F5 UI")
     -> 200, succeeds (this TZ's own select+PATCH path working exactly as
     designed).
  3. ANY subsequent request for that same doc by the SAME unscoped admin
     -> 403 "Studio document belongs to another organization scope" — on
     GET, PATCH, *and* DELETE. Confirmed via curl (all three) and via a
     live FE reload in the browser (Playwright): the editor page hangs
     forever on "Загрузка документа…" with no error message shown to the
     operator, only a silent 403 in the network console.
  4. It does not just "disappear from the list" — `findById()` (the same
     helper `update()`/`GET :id` both call) throws 403 unconditionally
     on any org mismatch, so the document becomes fully inaccessible
     (read AND write) to that admin from that point forward. There is no
     recovery path via the UI or API for that admin — not even to switch
     the issuer back — since every further call re-runs the same
     scope check before any patch is applied.
  5. Root cause: `resolveOrganizationId(null)` (used for the CALLER's own
     tenant scope on every method) and the NEW per-document `organizationId`
     identity field this TZ makes user-editable are the same physical
     field/concept (`StudioDocument.organizationId`) — pre-existing
     conflation the TZ's own preflight explicitly names and accepts.
  Cleanup: both throwaway test documents were deleted directly via
  `docker exec kppdf-mongo mongosh kppdf --eval
  'db.studio_documents.deleteOne(...)'` since the API itself was locked
  out for the admin session that created them.

Per the TZ's own instruction ("Если воспроизведётся — WARN + successor
«list by selected org / admin all-orgs», не блокировать этот TZ если
select+PATCH+preview ок на открытом документе") this is filed as a WARN,
not a blocker — the select+PATCH+preview path itself (ШАГ 3's actual scope)
works correctly on an already-open document; the lockout only bites on the
*next* request after switching away from the fallback org. Documented in
`document-studio.page.md`'s known_limitation paragraph; a successor TZ is
warranted to decouple tenant-scope resolution from issuer-identity, or at
minimum surface a real error state (not an infinite spinner) when
`findById`'s scope check rejects.
