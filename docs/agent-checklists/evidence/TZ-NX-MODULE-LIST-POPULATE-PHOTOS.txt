=== Root cause (confirmed exactly as TZ described) ===

`ProductModuleService.findAll()` populated `workTypes.workTypeId`,
`categoryId`, and `materials.materialId` — never `photoIds`/`mainPhotoId`.
The studio vitrina's "Модули" tab therefore always showed the empty
placeholder for every module regardless of whether it actually had a photo
uploaded — a missing-populate bug, distinct from the orphan-reference
broken-icon class already closed for product/material in WAVE3.1.

=== Fix (product-module.service.ts) ===

1. `findAll()`: added `.populate('photoIds').populate('mainPhotoId')` to
   both query branches (with and without `productId` filter), switched to
   `.lean()` (read-only list endpoint, matching product.service.ts /
   material.service.ts's own pattern — no internal caller relies on
   Document methods, confirmed via repo-wide grep), return type changed
   from `Promise<ProductModuleDocument[]>` to `Promise<Record<string,
   unknown>[]>` to match the now-plain lean shape.
2. New private `blankMissingModulePhotos()` — same `blankMissingUploadUrls`
   helper WAVE3.1 introduced in `document-render.utils.ts`, applied to the
   newly-populated `photoIds` arrays and `mainPhotoId` singles, exactly
   mirroring `MaterialService.findAll`'s own call site.
3. `findById()` deliberately NOT touched — it's used internally by
   `update()`/`addComposition()`/etc. for mutate-then-`.save()` flows, and
   the TZ's own text scopes this fix to "findAll (и findById если
   list-карточки его не используют)" — confirmed the vitrina's Модули tab
   calls `PiModulesService.list()` → `GET /modules` → `findAll()`, not
   `findById()`, so extending to `findById()` would be scope creep against
   this TZ's own necessity framing. The edit dialog's own
   `/api/photos/:id/raw` fallback (in `module-form-dialog.component.ts`'s
   `hydratePhotos()`) already handles a non-populated string ref there.

=== Specs (product-module.service.spec.ts, new describe block) ===

- "populates photoIds/mainPhotoId and blanks storageUrl for a photo whose
  file no longer exists on disk" — two modules, one with an orphan
  storageUrl (blanked to '') and one with a genuinely-existing file (kept),
  using a real temp uploads dir + real `access()` check (same pattern as
  WAVE3.1's product/material specs).
- "returns an empty list untouched when no modules exist" — trivial guard.
