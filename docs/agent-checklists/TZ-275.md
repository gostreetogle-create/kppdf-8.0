# TZ-275 checklist

- Dependency order: completed after TZ-277; no frontend changes required.
- Conflict keys: `backend/src/modules/admin/permissions-admin.controller.ts`, `backend/test/e2e/permissions-admin.e2e-spec.ts`, `backend/src/common/interceptors/audit.interceptor.ts`, `docs/RBAC-CONTRACT.md`.
- Decision: use `role:write` plus existing `@Roles('admin')`. The catalog is required by role creation/editing, while `role:read` alone must receive 403. This is intentionally a combined legacy role + effective capability contract; seeded admin receives `role:write` through admin-role promotion.
- Audit design: `AuditActionMetadata.auditRead` is an explicit opt-in. Ordinary GET requests remain unaudited; `GET /api/admin/permissions` emits `admin.permissions.catalog` for entity type `Permission`.
- Acceptance criteria:
  - role:read-only user receives 403 from `/api/admin/permissions`, and the response contains the PermissionsGuard `Required permission` message (not only a RolesGuard denial).
  - admin user receives 200 and a non-empty catalog.
  - successful catalog access creates the required audit action.
  - controller metadata unit tests pin permission, role, and audit contracts.
  - backend typecheck, targeted Jest, and available e2e pass.
  - RBAC documentation describes the endpoint requirement and read-audit opt-in.
- Planned checks: targeted backend unit Jest; targeted permissions/audit e2e; backend typecheck; backend lint/diff-check; independent review; full backend checks if time and environment permit.
- Browser/e2e limitation: no browser check is claimed unless an authenticated live flow is actually run. The Mongo-backed e2e is reported separately from browser verification.
