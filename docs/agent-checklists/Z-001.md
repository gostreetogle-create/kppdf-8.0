## План (3 фазы)

### ФАЗА 1 — External-session API на подчинённых

`StockMovementService.create(dto, externalSession?: ClientSession)`:
- если externalSession передан → выполнить write-graph через него БЕЗ own `startSession`/`withTransaction`;
- иначе → собственный путь (backward compatible).

`ReservationService.fulfill(id, externalSession?: ClientSession)`:
- если externalSession передан → `findOne().session()`, save+create на этой сессии; commit НЕ делаем (это обязанность вызывающего);
- иначе → existing own session.

### ФАЗА 2 — Обёртка трёх write-путей

`shipment.dispatch`, `purchase-order.receive`, `order.ship` оборачиваются в `sessionRunner.run`. Внутри:
- `this.stockMovementService.create(..., session)` (внешний),
- `this.reservationService.fulfill(rid, session)` (внешний),
- `doc.save({ session })`.

Модули: зарегистрировать `SessionRunner` в `ShipmentModule.providers` и `PurchaseOrderModule.providers`.

Best-effort `try/catch` на fulfill внутри dispatch — fail-fast: пусть abort покроет всё (предпочтение явное в спецификации).

### ФАЗА 3 — `stock-movement.remove` (вариант a)

В одной транзакции: если движение уже применено (origin.type=in→insert reverse 'out', out→'in', transfer↔transfer), создать reverse-movement через `stockMovementService.create(...)` на той же session (с пометкой `originId: <orig>` если schema уже поддерживает), затем soft-delete origin. Суммарный складской эффект стремится к нулю.
