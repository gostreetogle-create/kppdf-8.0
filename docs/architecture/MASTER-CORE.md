## 1. Архитектура — финальное решение и обоснование

### 1.1 Технологический стек (зафиксировано, не подлежит пересмотру без нового TZ)

| Слой | Решение | Почему именно так |
|------|---------|--------------------|
| **Frontend** | Angular standalone + Signals + `OnPush`, `input<T>()`, `inject()`, `@if/@for` | Единственная линия с боевой глубиной (v1→v8), а не экспериментальный Next.js-остров (v5/v6) |
| **Workspace** | Только `frontend-nx/` | `frontend/` (legacy) и всё, что относится к Next.js/React-линии (v5/v6), — архивируется. Дублирующих рабочих пространств быть не должно |

**Явно не переносится в финал:** микросервисы, Kafka/RabbitMQ, ChromaDB/Vector DB как источник истины (только future-seam на `$vectorSearch`, если понадобится), Next.js runtime, PrimeNG/Material/AG Grid, мультисклад/зоны/ячейки, PurchaseRequest/PurchaseOrder/Tender-UI (legacy), SSR.

### 1.2 MongoDB vs PostgreSQL — решение: **MongoDB Replica Set**

v5/v6 (Next.js-линия) были построены на PostgreSQL + Prisma ради ACID-целостности финансов. v8 (боевая линия, ~90 схем, 19+ backend-модулей) — на MongoDB + Mongoose с RS-транзакциями. Решение: **остаёмся на MongoDB**.

Обоснование:
- MongoDB Replica Set уже даёт полноценные ACID-транзакции (нужны для атомарных счётчиков `prefix-YYYY-NNN`, для проведения `StockMovement`, для `OrderClosing`) — реляционная СУБД не даёт здесь принципиально нового свойства.
- Источник истины остатка склада — **сумма движений** (`StorageItem` + `StockMovement`), а не кэшированное поле `stockQty`. Это ledger-паттерн, который снимает главный риск, ради которого обычно тянут в PostgreSQL (гонки при списании остатка).
- Масштаб — single-tenant, ~10 пользователей (v6 BIG-BOOK). Миграция 90-схемной боевой модели на Prisma — дорогая работа без измеримой выгоды на этом масштабе.
- v8 — единственная линия, доведённая до 87 backend-модулей и продакшн-контура (Synology deploy, health-checks). Переезд на Postgres означает остановку всей боевой линии ради теоретической выгоды.

### 1.3 Инфраструктура — решение

- **Хостинг:** Synology NAS остаётся продакшн-хостом (`deploy/synology/`, `docker-compose.prod`), запуск через `start.mjs`, health-check и no-wipe deploy — эта линия уже рабочая (v5→v8) и соответствует масштабу (~10 пользователей, single-tenant, без enterprise-инфраструктуры).
- **Бэкапы:** отдельный in-app UI управления бэкапами (был в v1) не восстанавливаем как отдельный модуль — на этом масштабе достаточно штатных снапшотов/Hyper Backup Synology для дампов MongoDB и медиа-файлов. Если позже появится потребность в самостоятельном restore прямо из приложения — это небольшая точечная фича, а не архитектурный вопрос.
- **Очереди/асинхронные задачи:** Redis+BullMQ поднимаются исключительно рядом с Desktop-импортом (Excel/фото) — не как общий рантайм-брокер.
- **Portable Export (IDEA-001):** формат — двойной: machine-first JSON как основной снапшот (для DR и переносимости) + генерируемый human-friendly Excel-пакет поверх него для ручной сверки. Отдельного бизнес-решения не требует — это техническая реализация уже сформулированного требования.

| Дубликаты в истории | Целевое имя |

### 2.4 Ключевые сквозные поля

- `packageTag` / `masterId` / `familyVersion` / `orgMarkup` — семья сделки («Картотека»): один и тот же состав изделий заполняется один раз в мастер-КП и **раскатывается в несколько дочерних КП** от разных наших `Organization` (разные юрлица/бланки/шаблоны), каждое — самостоятельный документ со своим номером и версией, но с общим источником состава. Приоритетная функция первого релиза (см. §5).
- `parentProposalId` + `version` — история версий КП, immutable после `sent`.
- `quotationId` на заказе — **опционально**. Заказ может существовать без ссылки на КП вообще; в этом случае у Заказа собственные `isPaid`/`paidAt`, отдельная сущность-заглушка КП не создаётся.
- `counterpartyId` + `siteId` на заказе.
- `line.ownerUserId` — ответственный менеджер на строке.
- `procureConfirm {by, at}` — подтверждение закупки человеком.
- `materialsSource: own|customer` — soft-gate материалов (мягкое предупреждение, не блокирует старт цеха — см. §5).
- `priceSnapshot` на строках Contract/Quotation — immutable цены после фиксации.
- Валюта — единое поле `RUB` на денежных сущностях, финально; legacy seed `USD/EUR` в справочнике валют — удалить как техдолг.
- `statusOverride {byUserId, at, reason, previousStatus}` — для привилегированных ролей (Директор/Админ), которые могут откатывать/переопределять статус на любом шаге цепочки Заказ→Оплата→Отгрузка→Закрытие (см. §5, п.18). Пишется в Audit log.

## 3. Целостная бизнес-логика (единый сквозной процесс)

Все версии описывали куски одного и того же потока. Ниже — бесшовная склейка без дублей.

```
1. КАТАЛОГ
   Изделие/Модуль/Материал готовы (цена + себестоимость), composition[] собран
   (глубина ≤8, без циклов, Product→сырой Material запрещён).

2. КОММЕРЧЕСКОЕ ПРЕДЛОЖЕНИЕ (КП / Quotation)
   Менеджер собирает КП на «Столе» (/desk): витрина каталога слева,
   A4-предпросмотр справа, персональная наценка/скидка клиента —
   только здесь, каталог не портится.
   draft → sent (версия замораживается, immutable) → accepted / rejected.

   Семейный режим: состав изделий заполняется один раз в мастер-КП и
   раскатывается в несколько дочерних КП под разные наши юрлица
   (Organization) — быстро, без повторного ввода состава.

   Альтернативный вход: заказ создаётся напрямую, без явного КП —
   заглушка КП не создаётся; заказ существует сам по себе и несёт
   собственный признак оплаты (`isPaid`/`paidAt`).

3. ПЕРЕХОД В РАБОТУ
   accepted КП (или напрямую созданный Order) → Order (состав заказа,
   БЕЗ цены сделки — цена живёт в КП). При `isPaid=true` заказ
   автоматически уходит в производство.
   Snapshot immutability: правки каталога после этого момента
   не протекают в уже отправленные КП и созданные заказы.
   Договор (Contract) — редкий, необязательный атрибут: либо прикреплённый
   файл, либо (в будущем) документ по шаблону из данных КП. Не блокирует
   и не гейтит переход заказа в производство.

4. РАЗВИЛКА ГОТОВНОСТИ (уровень изделия в заказе)
   Изделие хорошо укомплектовано (готов состав/BOM) → система автоматически
   резервирует под него материалы на складе.
   Есть на складе → резерв закрыт → в производство по Ганту.
   Нет на складе → автоматически формируется SupplyRequest, привязанный
   именно к этому заказу и именно к этому изделию (снабжение всегда знает,
   на какой заказ/пункт заказа идёт закупка). Производство при этом может
   стартовать с предупреждением о нехватке (мягкий блок, см. п.6).
   Изделие, требующее чертежей, — обязательно проходит очередь
   проектирования прежде производства; раздел проектирования сам
   передаёт готовое изделие дальше по цепочке.
   Один или несколько изделий в заказе могут быть готовы раньше
   остальных — отгружаются отдельно (см. шаг 8).

5. СНАБЖЕНИЕ
   Потребность считается из BOM конкретного изделия в заказе → SupplyRequest
   (человек подтверждает «можно заказывать» — procureConfirm) → SupplyTask →
   приход оформляется как StockMovement (IN), привязанный к тому же заказу/
   изделию. Полноценный модуль тендеров не строится — резервируется
   минимальный набор вспомогательных полей на будущее, без выделенного UI.
   Legacy Purchase* — не используется.

6. ПРОИЗВОДСТВО
   OrderTask на Ганте (вид работы × работник × рабочий центр) →
   фиксация фактических часов → completed → авто-приход готовой продукции
   на склад. `Order.status` — единственный источник правды о стадии
   для склада/отгрузки/производства одновременно.

7. СКЛАД
   Один ledger-движок; логические разделы = именованные Warehouse
   (металл, профильная труба, дерево, метизы…) — без типов филиалов,
   без физических адресов/ячеек. Остаток = сумма движений
   (StorageItem + StockMovement). Резерв связывает Заказ ↔ Склад с момента
   подтверждения комплектации изделия (шаг 4).

8. ОТГРУЗКА
   Shipment фиксируется по заказу и конкретному изделию/модулю внутри него —
   частичная отгрузка (часть изделий заказа уехала, часть ещё в производстве)
   разрешена и фиксируется документом. Печатный документ формируется системой
   автоматически и доступен для печати менеджеру по требованию, но не
   блокирует смену статуса отгрузки. Такие документы (акты, накладные)
   можно создавать как типовые из данных заказа, а затем донастраивать
   в редакторе шаблонов (текст правится вручную и сохраняется как шаблон
   для последующих отгрузок).

9. ЗАКРЫТИЕ
   Оплата → Отгрузка → Закрытие — обязательная последовательность по
   умолчанию. Привилегированные роли (Директор/Админ) могут снимать это
   ограничение точечно и откатывать/возвращать статус назад (человеческая
   ошибка не должна «замуровывать» сделку) — действие пишется в Audit log.
   OrderClosing → сверка (ReconciliationAct) → снапшот сделки замораживается.
   Полная финансовая цепочка (Invoice/Payment/Refund/margin-аналитика) не
   строится сейчас — система только собирает и хранит необходимые для неё
   данные (архив), чтобы аналитический модуль можно было подключить позже
   без миграции.
```

### 3.1 Статусные модели

- **КП:** `draft → sent (version freeze) → accepted/rejected`. Флаг оплаты (`isPaid`/`paidAt`) — на Заказе, не на КП; КП может отсутствовать вовсе.
- **Заказ:** `new → confirmed → in_production → ready_to_ship → shipped → closed` (единый FSM, п. 1.4 #1). Переходы `paid`/`closed` доступны Директору/Админу для отката (`statusOverride`, см. §2.4).
- **ЗК (производство):** `planned → in_progress → completed → auto-приход ГП`
- **Снабжение:** `requested → approved → ordered → received → closed`

### 3.2 Бизнес-правила (канон, зафиксировано, не пересматривается)

1. Скидки/наценки живут только в КП — каталог не портится.
2. Заказ = что изготовить; цена сделки не хранится на заказе.
3. Склад — **один ledger-движок**; логические разделы = именованные `Warehouse` (металл, метизы…) без типов филиалов и без адресов/ячеек (аудит NX 2026-09-05).
4. Частичная отгрузка модулей и изделий разрешена.
5. Desktop-импорт — только propose→confirm (HITL), не прямая запись в SoT.
6. Один write-path на сущность: Desktop/MCP/UI не создают параллельных источников истины.
7. Atomic-нумерация документов (КП, Д, ЗК, ЗП, СД, АС) — через `Counter` + Mongo-транзакцию.
8. Audit log — кто/когда менял (AsyncLocalStorage → `auditPlugin`).
9. Idempotency-Key + SubmitGuard на критичных POST — двойной сабмит не создаёт дублей.
10. Soft-delete глобально (`deletedAt: null` + unique-индекс).
11. Один Контрагент = одна сущность с `roles[]` (клиент/поставщик) — не заводим дублей на одну реальную фирму.
12. Один КП → один Заказ, строго 1:1, без split/merge.
13. Нехватка материала — мягкий блок (предупреждение цеху + автоматическое SupplyRequest), не жёсткий стоп.
14. Гостевой доступ к КП без логина — не делаем, система только для внутреннего использования.
15. CRM-таймлайн взаимодействий с клиентом (звонки/встречи/письма) и полноценный движок комплаенс-проверок паспорта — не делаем; система заточена под производственный цикл, не под CRM/регламентный контроль.
16. Валюта — только RUB, окончательно.

### 3.3 Автоматизации (must-have)

- Автонумерация всех типов документов через атомарный `Counter`.
- Autosave КП (debounce 2s) с локальным бэкапом черновика.
- Snapshot при каждой конвертации КП→Заказ (и далее по цепочке).
- `completed` ЗК → авто-приход готовой продукции на склад (StockMovement IN).
- Аудит и idempotency — сквозные, не точечные.

### 3.4 Роли и экраны (рабочий контур)

| Роль | Экран | Действия |
|------|-------|----------|
| Менеджер | `/desk`, КП workspace | Сборка сделки, печать, «в работу» |
| Директор | `/packages`, отчёты | Семьи сделок, маржа |
| Проектировщик | Очередь доукомплектования | Ready на модуль/изделие |
| Снабженец | `/supply` | Confirm + реестр закупок |
| Начальник цеха | `/production` (Гант) | Распределение задач |
| Кладовщик | `/inventory` | Приход/расход, отгрузка |
| Бухгалтер | `/finance` | Сверки, закрытие |

**Доступ (закрыто, см. §5):**
- Приглашение — по инвайт-ссылке: сотрудник переходит по ссылке, регистрируется и работает под назначенной ролью; без ссылки — входа нет.
- Уровень 1 — «страница целиком»: выключенная директором страница попросту не видна роли (backend = authority, FE-гейт = UX-видимость).
- Уровень 2 — точечные capability-флаги поверх страничного доступа для критичных действий (`canDelete`, `canEditAfterPaid`, `canOverrideStatus` и т.п.), а не отдельная галочка на каждое действие в интерфейсе. Технически — фиксированный небольшой набор capability-флагов на роль, не разрастающаяся ACL-матрица.

15. Role-segmented навигация.
16. `⌘K` command palette.

## 5. Бизнес-решения PO (закрыто)

Технический слой закрыт CTO в разделе 1 и п. 1.4. Ниже — бизнес-решения PO
по всем 20 вопросам; учтены в разделах 2–4 выше. Открытых вопросов не осталось.

**Продажи**
1. КП и Договор — не одна сущность. Договор редок и необязателен: либо файл-вложение, либо (позже) генерация из шаблона по данным КП. Приоритет — КП и его версионность.
2. Контрагент = одна сущность с `roles[]` (клиент/поставщик), не два разных.
3. Один КП → один Заказ, строго 1:1.
4. `isPaid` на Заказе → автоматически в производство; Договор — необязательный статус рядом, не гейт.
5. Заглушка-КП не создаётся: Заказ может существовать без КП вовсе, неся собственный признак оплаты.
6. Семья КП (раскатка одного состава на несколько юрлиц) — приоритетная фича первого релиза, не отложенная.
7. Гостевой просмотр КП — не делаем, только внутреннее использование.
8. CRM-таймлайн взаимодействий — не делаем, фокус на производстве.

**Склад / Производство**
9. Склад — один ledger-движок; разделы = именованные Warehouse (металл, труба, дерево, метизы…), без адресов/ячеек; при укомплектованном изделии материалы резервируются (confirm), при нехватке — SupplyRequest на заказ/изделие.
10. Частичная отгрузка по изделиям заказа — да, с фиксацией в документе, что отгружено/что осталось.
11. Нехватка материалов — мягкий блок (предупреждение, не остановка).
12. Стадия проектирования/чертежей — обязательна там, где изделию она нужна.
13. Документ отгрузки формируется автоматически, печать — по требованию менеджера, не блокирует статус; типовые документы донастраиваются в редакторе шаблонов.
14. Полноценный модуль тендеров — не делаем; резерв минимальных полей на будущее.
15. Комплаенс-движок с блокировкой паспорта — не делаем, максимум мягкие предупреждения.

**Финансы**
16. Полная финансовая цепочка (Invoice/Payment/Refund) — не сейчас; собираем и храним данные впрок для будущего аналитического модуля.
17. Валюта — только рубли, окончательно.
18. Оплата→Отгрузка→Закрытие — обязательна по умолчанию, но Директор/Админ могут снимать ограничение точечно и откатывать статус назад (см. `statusOverride`, §2.4).

**Доступ**
19. Сотрудники получают аккаунт через инвайт-ссылку и работают под назначенной ролью; без ссылки — доступа нет.
20. Права — двухуровневые: страница целиком (вкл/выкл) + небольшой фиксированный набор capability-флагов на критичные действия (удаление, редактирование после оплаты и т.п.), без разрастающейся ACL-матрицы.
