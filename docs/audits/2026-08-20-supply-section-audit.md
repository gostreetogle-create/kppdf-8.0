## Исправлено в ходе аудита

1. **Цвета материала не проходили backend validation.**
   `Material.colors` существовал в schema, но отсутствовал в `CreateMaterialDto`. При включённом whitelist поле отбрасывалось, поэтому новый цвет не сохранялся после обновления страницы. Добавлены DTO-валидация и поддержка create/update.

2. **Пустая новая строка быстрого заказа получала ошибку API.**
   UI сначала создаёт пустой draft и заполняет его по форме, а сервис требовал `materialId` или `title`. Ограничение снято: пустой draft допустим до заполнения обязательных рабочих данных.

3. **Повторное «Заказано» могло создать дубликат задачи реестра.**
   `SupplyRequest.markOrdered()` теперь не spawn'ит новый `SupplyTask`, если `linkedSupplyTaskId` уже установлен.

4. **Двойная запись статуса из frontend.**
   Раньше UI отправлял полный `PATCH`, затем status-action (`/ordered`, `/received`, `/cancel`). Теперь для каждого перехода выполняется одна авторитетная запись.

5. **Попulated `categoryId` материала ломал сопоставление picker-а.**
   Маппинг API теперь принимает как строковый ObjectId, так и populated `{ _id }`.

6. **Цветовой справочник был нестабилен при повторном вводе.**
   UI и backend теперь обрезают пробелы, удаляют пустые варианты и дедуплицируют цвета без учёта регистра; выбор из списка и добавление через `+` покрыты focused-тестами.

7. **Изменения телефона/email менеджера не сохранялись.**
   Быстрый заказ теперь сохраняет правки живого `Person` через `PATCH /api/persons/:id`; populated и raw `OrganizationContact.personId` поддерживаются.

8. **Фильтрация по заказу.**
   Быстрый заказ учитывает `orderId` из контекста страницы; backend/frontend list-контракт также получил `orderId` filter.

## Стендовый smoke/e2e — 2026-08-20 (23/23 PASS)

Выполнен реальный smoke на локальном стенде (docker Mongo + запущенный backend)
скриптом `scripts/smoke/supply-smoke.mjs` (многоразовый, самоочищающийся):

- авторизация: login admin → access token; запрос без токена → 401;
- Mongo: `/api/health` up; round-trip реальных ObjectId после записи;
- склад: warehouse + inventory + storage-item материала и изделия + список;
- быстрый заказ: пустой draft → PATCH (title/артикул из материала) →
  «Заказано» → spawn `SupplyTask` в реестре, повторное «Заказано» идемпотентно;
- отгрузка: создание из заказа → фильтр по `orderId` → dispatch → in_transit;
- upload-хранилище: multipart → файл на диске в `backend/uploads` → чтение по id
  → DELETE 204 + файл удалён.

Результат: **23 PASS · 0 FAIL · 0 WARN**. Все созданные записи и файлы удалены,
коллекции не засорены (остались только предсуществующие seed-данные).

### Найденные и исправленные баги (по ходу smoke)

1. **Storage-item partial unique index ловил чужие позиции.** Частичный фильтр
   `productId: { $exists: true }` в MongoDB индексирует документ и с отсутствующим
   полем (поле трактуется как `null`), поэтому второй материал в той же зоне
   склада падал с 500 на product-индексе. Исправлено: дискриминатор
   `$type: 'objectId'` (для позиций без зоны — `zoneName: null`); индексы
   пересозданы на стенде; воспроизведение через `scripts/smoke/supply-smoke.mjs`.
2. **`StorageItemService.remove()` был silent no-op.** Метод выставлял
   `deletedAt` в схеме, где такого поля нет (Mongoose strict отбрасывает) —
   строка оставалась и блокировала unique-индексы. Заменено на hard delete.
3. **Действия «Заказано»/dispatch возвращают 201**, а не 200 — скрипт
   учитывает обе коды; UI-код работал корректно (смотрел на тело/статус 2xx).

## Архитектурный вывод по сущностям

### Не является случайным дублем

- `SupplyRequest` — редактируемая строка быстрого заказа, может существовать без заказа.
- `SupplyTask` — задача снабжения, обязательно связанная с заказом и отображаемая в реестре.
- `Shipment` — отгрузка готового результата по заказу.

Эти три сущности имеют разные жизненные циклы и не должны сливаться без отдельного решения.

### Требует отдельного решения

`PurchaseRequest`/`PurchaseOrder` — старый контур заявок на закупку. Он не используется текущей страницей быстрого заказа, но остаётся в backend рядом с `SupplyRequest` и имеет другой контракт статусов. Это не доказанный runtime-дубль, однако стратегию сосуществования или миграции нужно зафиксировать отдельным ТЗ.

## Решения владельца продукта

Вопросы Q1–Q6 из TZ-SUPPLY-312 закрыты 2026-08-20:

1. «Заказано» — фактическое размещение; связанная `SupplyTask` получает `ordered`.
2. Отгрузка создаётся из `Order`, а не из реестра снабжения.
3. Цвета остаются `Material.colors: string[]` с нормализацией и дедупликацией.
4. Новые записи снабжения должны получать organization scope; legacy-записи без scope сохраняются для совместимости.
5. `/shipping` реализован как операционный MVP.
6. Незавершённые загрузки фото очищаются при отмене модалки.

Необратное объединение коллекций не требуется; legacy `PurchaseRequest/PurchaseOrder` вынесен в отдельный стратегический backlog.
