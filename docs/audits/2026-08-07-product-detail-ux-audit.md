**PO-запрос:** одна страница = полная цепочка изделия; удобно добавлять товары/модули/материалы; видна иерархия; варианты представления.  
**Статус:** **Variant A внедрён** на Карточке изделия (`ProductBomPanel`: дерево + инспектор + add-in-context). Канон UI: `docs/pages/product-detail.page.md`.

| Плохо | Лучше (канон UI) |

| «страница товара непонятно» | **Карточка изделия** |

Route остаётся `/products/:id`. В крошках: `Каталог / <имя>`.

---

## 1. Цель экрана (как будущий пользователь)

Менеджер/технолог открыл изделие и должен **собрать и понять BOM** без прыжков по пяти URL:

1. Увидеть паспорт (фото, SKU, цены, статус).
2. Увидеть **всю иерархию** состава на одном полотне.
3. Добавить:
   - изделие → изделие (комплекс);
   - изделие → модуль;
   - изделие → деталь/метиз/покупное;
   - модуль → модуль;
   - модуль → материал (в т.ч. сырьё).
4. Менять qty, удалять строку, раскрывать узлы.
5. Паспорт/фото/себестоимость — рядом, но не мешают сборке.

---

## 2. Что уже правильно (техника)

- Модель refs + qty, не клон дерева.
- Product→Product (D1), запрет raw на Product (D2), module nesting, depth/cycles.
- API composition + tree.
- Picker из каталога (имена, не ObjectId).
- Цветовые метки изд/мод/мат в дереве (зачатки).

**Вывод:** чинить нужно **композицию UI**, не переписывать домен.

---

## 3. Что ломает ощущение иерархии сейчас

| Симптом | Почему |
|---------|--------|
| Слева паспорт / справа «ещё один редактор» | Два равноправных блока → нет «сцены сборки» |
| Корень дерева = то же изделие | Дубль имени с шапкой, путаница «где я» |
| Add всегда на корень Product | Нельзя «выбрал модуль → + материал сюда» без ухода |
| Qty-редактор отдельным списком под деревом | Два представления одних линий |
| Фото/себестоимость в том же визуальном весе | Шум рядом с главным делом |
| Нет инспектора узла | Не видно, что можно добавить *в выбранное* |

## 4. Варианты представления

### A. Tree-table состава + инспектор (рекомендуемый)

```
┌─ Карточка изделия (компактная шапка) ─────────────────────┐
│ фото · имя · SKU · бейджи · прайс · [Редактировать]       │
├──────────────────────────────┬────────────────────────────┤
│ Состав (tree-table)          │ Инспектор выбранного узла  │
│ ▸ Изделие (корень, locked)   │ Тип · qty · действия       │
│   ▸ Модуль А        ×2   [+] │ «Добавить в этот узел…»    │
│     · Деталь …      ×4       │ ссылка «открыть карточку»  │
│   ▸ Изделие-ребёнок ×1       │                            │
│   · Метиз           ×10      │                            │
├──────────────────────────────┴────────────────────────────┤
│ Вкладки: Фото | Себестоимость | Где используется          │
└───────────────────────────────────────────────────────────┘
```

**Плюсы:** одна сцена; иерархия читается; add-in-context; есть `pi-table-tree`.  
**Минусы:** нужна доработка add API call с `parentId` выбранного узла (module composition с карточки изделия).

### B. Kanban / колонки уровней

Колонки «Изделия | Модули | Материалы» с drag.  
**Минус:** плохо для глубины >2 и qty; не ERP-BOM. **Не брать.**

### C. Только аккордеоны «папка в папке»

Сейчас близко к этому. Масштабируется плохо на 30+ строк. **Не как основной.**

### D. Split: список линий слева, превью дерева справа

Дублирует данные. **Слабее A.**

### E. Полноэкранный «BOM editor» без паспорта

Паспорт уедет — PO как раз хочет всё в одном месте. **Нет.**

## 5. Рекомендация

**Вариант A: Tree-table + инспектор + вторичные вкладки.**

Правила UX:

1. Шапка = паспорт (компактно), не конкурент дереву.
2. Центр = **одно** дерево состава (не список qty отдельно).
3. Типы сущностей: цвет / иконка / колонка «Тип» (изд / мод / мат·kind).
4. **Выбранный узел** = контекст кнопки «Добавить».
5. Добавление только через каталог (поиск), никогда ObjectId.
6. Редактирование состава дочернего модуля — in-place (module composition API), уход на `/modules/:id` — вторичная ссылка.
7. Фото / себестоимость / where-used — вкладки под деревом.

---

## 6. Карта действий «кто куда кладёт»

| Действие пользователя | Родитель в API | lineType |
|----------------------|----------------|----------|
| + Изделие в комплекс | текущий Product | `product` |
| + Модуль в изделие | текущий Product | `module` |
| + Деталь в изделие | текущий Product | `material` (≠raw) |
| + Модуль в модуль | выбранный Module | `module` |
| + Сырьё/деталь в модуль | выбранный Module | `material` |
| Изменить qty / удалить | parent линии | PATCH/DELETE |

---

## 7. Что не делать в v2

- Не изобретать сущность Part.
- Не клонировать деревья при embed.
- Не возвращать ObjectId UX.
- Не тащить Гант/заказы на эту страницу.
- Не делать второй параллельный «модульный» экран обязательным для сборки.
