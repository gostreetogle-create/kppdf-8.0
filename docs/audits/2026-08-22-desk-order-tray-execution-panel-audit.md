# Аудит правой панели плитки заказа: Исполнение / снабжение / логистика

**Дата:** 2026-08-22
**Статус:** готово к продуктовому решению PO; реализация не входит в эту TZ
**Источник:** `tasks/_active/TZ-DESK-421-tray-execution-panel-audit.md`

**Связанные каноны:** `docs/PO-CANON.md`, `docs/COUPLING-MAP.md`, `docs/pages/manager-desk.page.md`, `docs/pages/orders.page.md`

## 1. Вывод

Правая часть `app-order-hub-tray` уже содержит правильные факты жизненного цикла, но сейчас подаёт их как вертикальный список одинакового веса. Менеджеру при открытии заказа нужен не ещё один dashboard, а короткий ответ на вопрос **«что делать с заказом сейчас?»**:

1. **Исполнение** — оставить открытым и главным: lane-полоса + `Готовность X из Y`.
2. **Снабжение и производство** — сворачиваемая рабочая группа с одним явным CTA и коротким статусом/счётчиками.
3. **Логистика и документы** — сворачиваемая группа; автоматически раскрывать только при активной проблеме/операции.
4. Заметки не превращать в новый чат: уже существует `/desk`-блокнот `DeskNote`; в следующей реализации его следует сделать заметнее как действие к заказу.

Это сохраняет север PO: продажи/КП → заказ → снабжение/производство → склад/отгрузка, не смешивает `boardLane`, `Order.status` и `readyForWork` и не создаёт второй write-path.

## 2. Что проверено в текущем коде

`OrderHubTrayComponent` — shared-компонент для `/desk` (`mode="desk"`) и `/orders` (`mode="hub"`), см. комментарий компонента и оба host-а в `manager-desk.page.ts`/`orders.page.ts`. Внутри:

- summary bar: `order-hub-tray.component.ts` примерно строки 86–126;
- левая группа «Состав»: примерно 129–229;
- правый stack: примерно 230–460;
- данные снабжения загружаются lazy при создании tray (`ngOnInit`, примерно 485–498), счётчики строятся локально в `countSupplyStatuses`;
- состав каталога lazy-loadится при раскрытии, а на `/desk` открыт по умолчанию;
- складские reservations получает hub-host, не сама правая панель;
- для desk уже есть отдельные события `openSupply`, `openDocs`, `createDocument`, `addLines`.

## 4. Что делать с заметками и обсуждением

Новая chat-сущность **не нужна**. Проверен существующий `DeskNote`:

- FE-контракт: `frontend/src/app/shared/services/desk-notes.service.ts` — `list({ orderId })`, `create`, `update`, `remove`;
- BE schema: `backend/src/modules/desk-note/desk-note.schema.ts` — `text`, `kind` (`note|checklist|reminder`), обязательный `anchorOrderId`, optional `anchorLineId`/`anchorModuleId`, `authorId`, `isDone`;
- BE service: `backend/src/modules/desk-note/desk-note.service.ts` — list требует `orderId`, запись привязывается к заказу, PATCH/DELETE защищены автором или `admin|director|manager`;
- `/desk` уже имеет `panel=notebook` и picker «Заказ / линия изделия» согласно `docs/pages/manager-desk.page.md` (TZ-DESK-408/415).

Рекомендация: в successor добавить в tray **один заметный вход «Блокнот»** (или компактный note-count, если такой read API уже согласован), который открывает существующий `panel=notebook`/host handler. Не показывать весь текст заметок в каждой плитке и не строить real-time chat, mentions или новую сущность без отдельной TZ.

## 5. Предлагаемая IA successor

### Default состояние

```text
┌─ Исполнение ───────────────────────────────────────────────┐
│ [Комплектация] [Проектирование] [В цехе]  Готовность 2 из 4 │  ← всегда открыто
│ • Изделие A — готово                                         │
│ • Изделие B — не готово                                      │
└─────────────────────────────────────────────────────────────┘

▸ Снабжение и производство       2 задачи · Оценка в цехе     [Открыть]
▸ Логистика и документы          1 активная бронь            [Блокнот]
```

### Правила

1. «Исполнение» — единственная постоянно открытая группа: lane status + readiness.
2. «Снабжение и производство» — collapsed по умолчанию; summary показывает число задач/ошибку; CTA «Открыть снабжение» и «Открыть производство» не прячутся после expand.
3. «Логистика и документы» — collapsed по умолчанию; active reservation/error/status `ready` — auto-open.
4. «Документы» не выделять в четвёртую большую панель: оставить subsection внутри логистической группы, две ясные кнопки.
5. `DeskNote` — отдельный компактный CTA «Блокнот», открывающий уже существующий notebook; не новый чат.
6. Использовать `button` с явным `aria-expanded`/`aria-controls` для disclosure-групп. Не менять существующие `data-test` без необходимости.
7. На узком экране группы остаются вертикальными; не делать горизонтальный carousel и не скрывать ошибки.

### Приоритет CTA

- **Primary:** `Открыть снабжение` или `Открыть производство` — по факту текущего незавершённого этапа.
- **Secondary:** `Открыть склад`, `Открыть отгрузку`, `Создать документ`.
- **Tertiary:** `Шаблоны`, переход к полной карточке заказа.
- **Всегда заметный при наличии:** ошибка снабжения/склада, `Блокнот` для фиксации контекста.

## 6. Что не меняется в этой рекомендации

Не предлагается менять набор или семантику навигации:

- `/production` (в desk сохранён `from=desk`, чтобы вернуть «На стол»);
- `/supply` (`orderId` сохраняется из tray);
- `/storage-items`;
- `/shipping`;
- `/doc-constructor/templates?source=order&sourceId=`;
- существующие desk events `openSupply`, `openDocs`, `createDocument`.

Не предлагается:

- писать `Order.status`, `OrderItem.status`, `boardLane` или `readyForWork` из tray;
- добавлять новый backend API только ради счётчика/чата;
- превращать shared tray в отдельную копию для `/desk` и `/orders`;
- менять PO visual lock без отдельного approval.

## 7. Открытые вопросы к PO

1. При каких именно условиях раскрывать «Снабжение и производство» автоматически: любой `in_production`, только `supply.total > 0`, или только ошибка?
2. Для статуса `ready` открывать «Логистика и документы» автоматически всегда или только при активной брони?
3. Достаточно ли CTA «Блокнот» с текущим notebook, или нужен компактный счётчик заметок (для него потребуется согласованный read path в host)?
4. Какой CTA считать primary, если одновременно есть незавершённое снабжение и незавершённое производство?
5. Оставлять ли текстовый факт «Оценка в цехе» до появления реальной метрики или показывать его только при наличии данных?
