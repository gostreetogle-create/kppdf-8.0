# Полный аудит KPPDF (MCP-сервер `kppdf-desktop` + наполнение данными)

> Дата: 11.08.2026 · Автор: аудит через MCP (JSON-RPC, Streamable HTTP, `http://127.0.0.1:9743/mcp`)
> Сервер: `kppdf-desktop v0.1.0`, протокол MCP 2024-11-05, бэкенд `https://kppdf-crm.ru`, сессия: `admin`
> Канон в git: этот файл + `reports/mcp-audit/AUDIT-REPORT.md`.
> Очередь фиксов: `tasks/_backlog/desktop/PROMPT-MCP-AUDIT-P0.md` (TZD-41…44).

---

## 1. Резюме

Система **работает и готова к интеграции с AI-агентом через MCP**: из 54 инструментов реально вызван и проверен 41, все основные бизнес-цепочки (каталог → спецификация → склад → продажи → документы → импорт) проходят end-to-end. Архитектура MCP-сервера **продумана и безопасна**: все записывающие операции в каталоге идут через журнал предложений (propose → confirm), необратимые действия (отгрузка, конвертация КП) требуют явного `userOk:true`, есть откат (`undo`), журнал с before/after-снимками, dry-run валидаторы и read-only «проверка целостности графа».

За время аудита система **выдержала наполнение +51 сущностью и 21 строкой спецификаций без единой ошибки целостности** (integrity suite: 55/55 после всех изменений).

Главные проблемы — не в функциональности, а в **консистентности API-поверхности для агента** (разнобой имён и форм ответов), **дырах в покрытии** (нет create/update для ряда сущностей) и **гигиене данных** (тестовый мусор в SoT).

## 4. Что работает хорошо (сильные стороны)

1. **HITL-архитектура**: каталог меняется только через предложения; `confirm_batch` (до 500) + idempotencyKey для безопасных повторов; `cancel` без SoT-эффекта; `undo_mutation` с ring-буфером 50 и before/after-снимками — отличный каркас для доверенного AI.
2. **Гейтинг необратимых действий**: отгрузка, конвертация КП в заказ/договор, подтверждение модулей — только с `userOk:true` (0 записей иначе).
3. **Валидация на бэкенде настоящая**: контрольная сумма ИНН (10/12 знаков), категория должна быть active/type=material, авто-SKU по `skuPrefix`, unit-канон (шт/м/м²/кг/л). Dry-run валидаторы материалов и продуктов отдают структурированные errors/warnings/infos.
4. **Целостность графа спецификаций**: read-only suite (55 проверок по выборке) — после +21 строки BOM 0 ошибок, 0 предупреждений. Инструмент правильный и нужный (TZD-19).
5. **Склад** не даёт уйти в минус и не создаёт движение без позиции («Для выбранного товара нет позиции на складе») — бизнес-правило на бэкенде, не на клиенте.
6. **Продажи защищены**: КП/заказ можно создать только черновиком, статусы — whitelist, КП → заказ/договор через отдельные gated-инструменты.
7. **Импорт разложен по стадиям**: классификация колонок (TZD-26) → ImportTask → AI-отчёт (set_report) → apply_plan (userOk) → подтверждение; reshape сбрасывает aiReport (принудительный re-audit) — безопасно.
8. **Документы**: AI-черновики шаблонов помечаются `[AI-DRAFT]`, никогда не default; текстовые блоки — неактивные черновики; на каждый черновик авто-создаётся todo менеджеру (TZD-29) — воронка «AI подготовил → человек доделал» работает.
9. **Самодокументация**: `get_domain_schema` с версионированием (tzd-17/27) — агент может свериться с каноном, не читая код.

## 5. Найденные проблемы и баги

**P0 — блокеры для агента:**

1. **Разнобой имён инструментов.** `kppdf_list_materials`, `kppdf_list_products`… но `kppdf_doc_types_list`, `kppdf_import_task_list`, `kppdf_inbox_list`, `kppdf_text_block_categories_list` (префикс `list` в разных местах). Агент (я) на этом спотыкался 6 раз. Нужен единый нейминг или alias.
2. **Разнобой форм ответов.** `propose_product_create` возвращает `{proposal: {proposalId}}`, `propose_material_create` — `{proposalId}` на верхнем уровне; создание контрагента — `result._id`, а список — `id`; заказ — `result.id` только через get. Из-за этого мой первый проход **не подтвердил 10 продуктов** (пропустил вложенный id). Для агента это критично: нужен единый envelope (`ok`, `data`/`result`, стабильный id) или расширение MCP-схемы с явным `outputSchema`.
3. **Пропавшее предложение (race).** «Шест для лазания ШЛ-300»: `propose` → ok, затем `confirm` → **404 (proposal not found)**. Повторный propose+confirm сработал. Похоже на гонку/истечение предложений в журнале — нужно исследовать, для AI-пайплайнов это скрытая мина.
4. **Продукт через MCP создаётся с `status: new` и без категории.** `propose_product_create` не принимает `categoryId` и `status`, в отличие от материалов (у тех авто-SKU по категории). Категории продуктов (`sport-courts`, `outdoor-workout`…) существуют, но через MCP продукт в них не положить. Разрыв «веб vs MCP».

**P1 — гигиена данных:**

5. **Тестовый мусор в SoT**: материалы «fbdb» (unit=pcs), продукты «fhfbgf», «Падел» (без категории), модуль «6565», серии «Тест ·…», «Тест ·Контрагент», КП «QTN-2026-001» от тестовых контрагентов, мой дубль-контрагент «ООО «ТестФорма»» (создан для проверки формы ответа). Нет инструмента поиска дубликатов/очистки. Рекомендация: отдельный «смоук-тенант» и тул `kppdf_cleanup_test_data` (мягкое удаление по префиксу/метке).
6. **Демо-данные не полны по правилам**: у всех продуктов `stockQty` на бэкенде 0 при наличии остатков (расхождение агрегата), `minQuantity`/`reservedQty` = 0 везде (порог заказа не используется), `roleIds` складов пусты, фото (`photoIds`) нигде нет — модуль ассетов не покрыт MCP.

**P2 — UX/качество:**

7. Ошибка склада «нет позиции на складе» не говорит, что делать (сначала `in`/`transfer`) — сообщение в стиле «Для выбранного товара нет позиции» без контекста инструмента.
8. Список КП/заказов (slim) не показывает ни суммы, ни состав — чтобы узнать, что внутри, нужно дергать get на каждый. Для сводок агенту дорого.
9. `inbox_list` пуст, а файлового загрузчика в MCP нет — классификацию колонок можно дёргать только inline (headers+sample) либо через файлы, положенные в папку инбокса вручную. Нет тула «положить файл в инбокс» (например, из URL/attachment).
10. Договор нельзя создать напрямую — только конвертацией из КП. Иногда нужен черновик договора без КП.

## 6. Пробелы покрытия MCP (чего не хватает)

Сверка с доменной моделью (README: 89 сущностей, 11 доменов):

| Домен | В MCP | Не хватает |
|---|---|---|
| Каталог | материалы/продукты/модули + BOM | **категории (create/update)**, сертификаты, атрибуты, work-types, photos/assets |
| Склад | warehouses(list), storage-items(list), movements | **create/update warehouse**, storage-items (только через движения), резервирование, инвентаризация |
| Продажи | КП/заказы/договоры (draft+конвертации), контрагенты, площадки | **persons (create/update)**, update контрагентов/площадок, КП→PDF/печать, суммы в slim-list |
| Производство | — (work-types видны в модулях) | заказы на производство, наряды, операции, себестоимость — **весь домен не покрыт** |
| Закупки | — | заявки, заказы поставщикам, счета, тендеры, РПП — **весь домен не покрыт** |
| Финансы | — | акты сверки, отчёты — не покрыто |
| Импорт | inbox, ImportTask, todos, classify | загрузка файла в инбокс, авто-SKU-предложения, batch stock-in по импорту |
| Документы | типы, категории, шаблоны (draft), текстовые блоки | готовые документы (doc-documents), PDF-генерация, таблицы шаблонов |
| Identity | ping (me) | управление пользователями/ролями (web-only) |
| Журнал | proposals, mutations, undo | просмотр/экспорт истории, фильтры по типу |

**Ключевой вывод**: MCP покрывает ~50% домена и почти весь «продажный» контур (то, что нужно агенту-менеджеру), но производственный и закупочный контуры (ядро ERP по README) полностью отсутствуют. Если цель — «агент ведёт заказ от КП до отгрузки», этого хватает; если «агент управляет производством» — нужен второй эшелон тулов.

## 8. Наблюдения по данным и качеству демо

- Демо-сиды тематически связные (спорт/воркаут/падел) — **это сильно**: цепочки материалов→модулей→продуктов→КП→заказов реально прослеживаются.
- ИНН в сидах валидные (прошли контрольную сумму) — видно, что сиды пишутся через те же валидаторы. Отлично.
- Мусорные записи («fbdb», «fhfbgf», «6565», «Тест ·…») ломают впечатление и могут быть приняты агентом за реальные данные — рекомендую вычистить или перенести в отдельный тенант.

## 9. Итог

**MCP-сервер готов к боевому использованию агентами** для контура «продажи + каталог + склад + импорт + документы»: безопасен (HITL, гейтинг, undo), самодокументирован (schemas), проверяем (integrity suite, dry-run). Перед широким запуском стоит закрыть три консистентности: нейминг, форму ответа (outputSchema) и баг confirm-404. Производство/закупки — осознанно следующий эшелон.

Все артефакты аудита: `reports/mcp-audit/` (JSON-ответы по каждому вызову, скрипты `mcp_audit.py`, `recon.py`, `seed*.py`, `verify.py` — можно переиспользовать для повторных прогонов).
