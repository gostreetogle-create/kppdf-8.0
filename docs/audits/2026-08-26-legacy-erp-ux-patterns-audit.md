# Аудит: паттерны представления данных из скриншотов старого ERP → kppdf-8.0

> Тип: docs-only, analysis-only. Код не менялся. Это входной артефакт для
> будущих mini-TZ, не сама реализация.
> Источник: `data/Скриншоты ERP/` (175 файлов, 2020–2024, дал PO 2026-08-26).
> Метод: 4 параллельных агента прочитали все 175 скриншотов, рассортировали
> копии по модулям в `data/Скриншоты ERP/_sorted/<категория>/` (оригиналы не
> тронуты) и оставили заметки по каждому файлу; отдельный agent снял срез
> текущих страниц frontend для сравнения. Полные построчные заметки — в
> расшифровке этой сессии; здесь — синтез.

## 1. Что это был за продукт

Судя по контенту скриншотов, это внутренняя ERP производителя игровых
площадок/малых архитектурных форм (качели, горки, беседки, урны, ограждения)
с сильным упором на:

- каталог изделий/деталей/модулей (BOM-иерархия) — **117 из 175** скриншотов;
- внутренний трекер задач с апрувом (аналог нашего "Рабочий стол" / desk) — 15;
- каталог-browsing с очень плотными строками — 10;
- конструктор печатных документов (спецификации, паспорта) — 7;
- закупки/цены поставщиков — 9;
- справочники — 5;
- заказы — 4.

Скриншоты содержат служебные QA-аннотации самой вендорской команды (красные
рамки/стрелки, комментарии типа «можешь вместо крестика сделать повторный
поиск?») — это тоже сигнал: они сами фиксировали баги своего UI. Часть таких
находок ниже помечена как **анти-паттерн**, а не как «взять».

## 3. Цвет: сравнение и предложение

**Наша текущая тёмная тема** (`frontend/src/styles.css`, `@media dark` /
`[data-theme=dark]`, канон Paper & Ink):

| Роль | Токен | Значение |
|---|---|---|
| Фон (paper) | `--color-paper-override` | `oklch(0.175 0.006 260)` — холодный почти-чёрный |
| Текст (ink) | `--color-ink-override` | `oklch(0.92 0.004 260)` — светлый тёплый белый |
| Акцент/CTA/фокус | `--color-gold-override` | `oklch(0.84 0.145 86)` — жёлто-золотой |
| Success/Info/Warning | `--color-success/-info/-warning` | зелёный / голубой / янтарный |
| Destructive | `--color-destructive-override` | `oklch(0.7 0.17 25)` — красный |

**Легаси-палитра** (по заметкам из 175 файлов): почти чёрный фон
(`#141414…#1e2530`), **бирюзово-циановый** как основной цвет ссылок/фокуса/
интерактива, **оранжевый** как второй, не всегда системный акцент (иногда
код артикула — teal, иногда — orange: сами это фиксировали как
непоследовательность), плюс семантика: зелёная галочка = проверено, красный =
ошибка/срочно, янтарный/оранжевый full-width баннер = «черновик/в разработке».
Тёплые тона (охра, дерево, песочный) чаще встречаются в самих фото товаров,
не в chrome интерфейса.

**Вывод:** у нас уже тёплый акцент (золото) — это ближе к «теплее и приятнее»
запросу PO, чем циан вендора. Смешивать в смысле «добавить их циан вместо
нашего золота» — не нужно, это разрушит уже согласованный Paper & Ink канон.
Что реально стоит **взять**:

1. **Развести роли акцентов.** У вендора циан = «это ссылка/данные», отдельно
   от warning/CTA. У нас золото сейчас одновременно фокус-кольцо, hover,
   активная навигация *и* потенциально бренд-акцент — это можно перегрузить.
   Предложение (не код, TZ на архитектора): проверить, не стоит ли
   использовать уже существующий `--color-info` (`oklch(0.74 0.08 230)`,
   холодный голубой) как цвет для *кликабельных перекрёстных ссылок в данных*
   (артикулы, счётчики «5 файлов», «где используется»), оставив
   `--color-gold` только под CTA/фокус/навигацию — так по роли, а не по цвету
   мы получаем то же разделение, что у вендора, без новых токенов.
2. **Full-width status-banner** для жизненного цикла записи (черновик/в
   разработке/отклонено) — токены `--color-warning`/`--color-destructive` уже
   есть, паттерна баннера в коде нет (см. §5.6). Взять форму подачи (полоса
   на всю ширину, не бейдж), не цвет — у нас `--color-warning` уже тёплый
   янтарный, вписывается в Paper & Ink без правок токенов.
3. Диагональная штриховка для «нет изображения/нет маркера» (§5.4) — вписать
   через `--color-rule` / `--surface-plaque`, тоже без новых токенов.

Итог по цвету: **новых hex/токенов заводить не нужно** — у нас уже теплее и
чище, чем у вендора. Ценность не в смешении цвета, а в **перераспределении
ролей** существующих токенов (gold = действие, info = данные/ссылки,
warning = жизненный цикл) — это отдельная тонкая mini-TZ архитектору UI, не
редизайн палитры.

## 6. Анти-паттерны — сознательно НЕ переносить

Зафиксировано либо самими вендорскими QA-заметками, либо очевидно по
скриншотам:

1. **Несистемный цвет ссылок** — один и тот же тип элемента (артикул) то
   циан, то оранжевый в разных экранах без видимой логики. У нас через
   design-tokens такого структурно быть не должно — но явно держать в уме
   при разведении ролей акцентов (§3).
2. **Плоский pill/tag-grid вместо дерева** для иерархии BOM
   (`2020-01-29_19-16-35.png`) — компактно, но плохо передаёт вложенность;
   у нас уже есть нормальное дерево (`app-composition-tree`) — не деградировать
   до плоского грида.
3. **Захламление вкладками браузера** вместо внутренней навигации по записям
   (`2020-12-21_13-01-25.png` — десятки открытых табов) — символ того, что
   в приложении не было удобного способа держать несколько записей в поле
   зрения. У нас SPA-роутинг решает это лучше — не откатываться к паттерну
   «открой в новой вкладке» как основному способу сравнения записей.
3bis **Непоследовательные состояния "нет данных"** — три разных способа
   показать отсутствие значения (текст «Нет», голый спиннер, пусто) в разных
   местах одного и того же продукта (см. §5.4) — фиксировать одну конвенцию
   и не отступать от неё.
4. **Обязательный ручной ввод причины на каждое деструктивное действие без
   исключений** — само по себе полезно как паттерн (§5.3 близко к этому), но
   у вендора это применялось шаблонно везде, включая мелкие правки — если
   переносить, ограничить только реально необратимыми операциями (снятие с
   публикации, удаление), не бытовыми правками поля.

## 7. Как использовать этот документ дальше

Это разведка и приоритизация, **не TZ на реализацию**. Следующий шаг по
контракту проекта — каждый пункт P0/P1, который PO подтвердит, оформляется
как отдельная mini-TZ в `tasks/_active/` с Claim (`agent_id`), проходит
Preflight и normальный DoD-цикл (`pnpm exec tsc`/`test`/`lint`,
`docs/pages/<name>.page.md` апдейт, FIC). Рекомендуемый порядок реализации:
§5.3 (status-banner, самое видимое и дешёвое) → §5.1 (where-used на
изделия/модули, переиспользует существующий паттерн) → §5.2 (история цены,
новый виджет, дороже всего).

### Поправки к разведке (важно до TZ)

1. **§5.1 дешевле, чем написано:** BE where-used уже есть на
   `product` / `product-module` / `work-type` (`catalogGraph.getWhereUsed`) —
   дыра в основном **FE** на detail-страницах, не «нет API».
2. **§5.2 не P0 «данные уже в БД»:** у Material только скаляр `pricePerUnit`;
   коллекции/эндпоинта истории цен **нет**. Нужен write-path (supply /
   purchase) + хранение — иначе виджет врёт. Есть готовый
   `app-pi-line-chart` (без внешней chart-lib) — пункт про «обсудить lib»
   устарел.
3. **Намерение PO #2 (структура/плотность/kit) недопокрыто:** список §5 —
   в основном новые виджеты, мало про row density, группировку полей в
   диалогах, выравнивание kit (`/kit/*`) под ту же подачу. Это отдельный
   тонкий проход, не отмена P0.

### Рекомендуемый порядок внедрения (после Да/Нет PO)

| # | Что | Тип | Зачем |
|---|-----|-----|--------|
| A | Status-banner strip (kit + 1–2 страницы) | mini-TZ UI | самый близкий к «как у них по структуре», без новой модели |
| B | Where-used на product/module detail | mini-TZ FE (+reuse API) | закрывает реальный пробел дешево |
| C | Роли акцентов: gold=CTA, info=data-links (без новых токенов) | mini-TZ UI/kit | «похожая тёмная» по ролям, не палитра вендора |
| D | Empty thumbnail hatch (одна конвенция) | micro kit | §5.4 |
| E | История цены | **не** стартовать без отдельного BE/TZ | иначе ложный P0 |

3-dot tracker (§5.7), CAD viewer — без явного запроса цеха.
