# Аудит: DGM.js (dgmjs-1.5.5) — можно ли вшить в kppdf

**Дата:** 2026-08-08  
**Источник:** локальный `dgmjs-1.5.5.zip` (~16.1 MiB, 785 файлов) + [github.com/dgmjs/dgmjs](https://github.com/dgmjs/dgmjs) + docs.dgmjs.dev  
**Вердикт:** **не внедрять в ERP сейчас.** Библиотека сильная как sketchnotes/whiteboard, но стык с Angular, **GPLv3**, и север продукта (чертежи цеха ≠ infinite canvas) делают «кнопку в меню» дорогой и рискованной.

---

## 1. Что в ZIP

Это **исходники monorepo** релиза **1.5.5**, не готовый «сайт для клика».

| Часть | Содержание |
|-------|------------|
| `packages/core` | `@dgmjs/core` — движок холста (Editor, shapes, JSON serialize) |
| `packages/react` | `@dgmjs/react` — официальные React-обёртки (`DGMEditor`) |
| `packages/export` | PNG/JPEG/WebP/SVG |
| `packages/pdf` | экспорт PDF (jspdf) |
| `packages/dgmjs-plugin-yjs` | realtime collab через Yjs |
| `apps/demo` | полноценное **демо на React+Vite+Tailwind** (тулбар, палитры, диалоги) |
| `apps/docs` | документация сайта |

Корень ZIP: `LICENSE.md` = **GNU GPLv3**. README совпадает с GitHub.

**Это не CAD и не Inventor.** Это infinite canvas со smart shapes / hand-drawn / rich text — ближе к Excalidraw / Miro-lite / sketchnotes.

Полное облачное приложение поверх библиотеки — отдельно: [DGM App](https://dgm.sh/home). Showcase ещё: Frame0, Nakso.

## 2. Можно ли «зайти с нашего сайта и рисовать»?

Технически **да**, но это **не** «подключил npm и готово».

| Вариант | Суть | Оценка для kppdf |
|---------|------|------------------|
| **A. Встроить в Angular** | `@dgmjs/core` framework-agnostic; UI-тулбар писать самим (официальный UI — React) | Тяжело: 1–2+ недели на usable редактор + галерею |
| **B. React island / iframe** | Отдельный Vite-бандл demo-подобного UI внутри `/sketches/:id` | Средне; два стека в одном продукте |
| **C. Новое окно → внешний сервис** | Кнопка открывает dgm.sh / свой хост demo | Легко; нет единой сессии/галереи без их API |
| **D. Только ссылка + вложения** | Файл PDF/PNG в карточке изделия/заказа | Уже ближе к цеху; canvas не нужен |

Наш фронт — **Angular 20 + Paper & Ink**. Официальный путь DGM — **React**. Обернуть `core` в Angular-компонент реально; красивый тулбар как в demo — почти весь `apps/demo` переписать под наш UI.

«Красивая кнопка вверху» — 5 минут. **Рабочий редактор + сохранение + галерея** — отдельный вертикальный кусок (неделями).

## 3. Нагрузка на сервер / сайт

| Что | Нагрузка |
|-----|----------|
| **Рисование** | **Только браузер** (CPU/GPU клиента). Nest/Mongo **не** крутятся на каждый штрих. |
| **Открытие страницы** | Бандл: `@dgmjs/core` ~365 KB raw / ~87 KB gzip **без** React-тулбара и TipTap. Lazy route — остальные страницы ERP не толстеют. |
| **Сохранение** | JSON документа (обычно десятки–сотни KB) → наш API/Mongo или файл. Для ~10 пользователей — пустяк. |
| **Экспорт PNG/PDF** | В браузере (`@dgmjs/export` / `@dgmjs/pdf`). Сервер не рендерит холст. |
| **Realtime collab (Yjs)** | Нужен WebSocket/signaling — **отдельная инфра**. Для цеха из ~10 чел. — **не брать в P0**. |

Итог: сайт «не ляжет» от самого рисования. Риск — **сложность продукта и лицензия**, не CPU сервера.

Новое окно vs встроенная страница: по нагрузке сервера одинаково (клиент рисует там же). Разница только в UX и в том, храним ли JSON у себя.

## 4. Галерея / сохранение — есть ли «из коробки»?

| Слой | Есть? |
|------|--------|
| JSON import/export в библиотеке | **Да** |
| Галерея файлов, ACL, список «мои холсты» | **Нет** — это наше (или DGM App) |
| Demo app | Локальный/демо UX, не ERP-CRUD |
| Multi-page, dark mode, export | В библиотеке есть |

Грамотная «галерея» у нас выглядела бы так:

1. Коллекция `Sketch` / `CanvasDoc` (title, owner, updatedAt, `docJson`, optional `productId`/`orderId`).
2. Список `/sketches` + редактор `/sketches/:id`.
3. Превью = экспорт PNG thumbnail при save.
4. Права через существующий pageKey/ACL.

Это **наша** работа поверх `@dgmjs/core`, не фича ZIP.

## 5. Лицензия — жёсткий стоп для «просто вшить»

- `@dgmjs/core` / export / pdf / yjs: **GPLv3**.
- Встраивание в закрытый коммерческий ERP обычно требует **либо** открыть исходники продукта под GPL, **либо** купить **Commercial License** ([dgmjs.dev/overview/license](https://dgmjs.dev/overview/license/), contact licensing@dgm.sh).
- PR в upstream **не принимают** («not open contribution»).

Пока нет коммерческой лицензии — **не тащить в `frontend` как зависимость**.

## 6. Стык с севером kppdf (будущий пользователь)

В продукте слово **«чертежи»** уже занято:

- `TZ-PRODUCTION-DRAWINGS-301` / YouGile gap = **очередь работ** (статусы, артикул, дедлайн), не freehand whiteboard.
- В data-model есть `drawingUrl` / Inventor-файлы — про **файлы чертежа**, не sketchnotes.

Для менеджера/цеха полезнее:

1. Канбан чертежей в cockpit (parked DRAWINGS-301).
2. Вложения PDF/DWG/фото к изделию/заказу.

Infinite canvas полезен как **доска на совещании / скетч идеи**, не как замена Inventor/паспорта. Кнопка «Холст» в топ-меню без сценария коллеги = фича ради фичи (антипаттерн PO-DIARY).

## 7. Рекомендация PO

| Вопрос | Ответ |
|--------|--------|
| Внедрять в меню сейчас? | **Нет** |
| Нагрузит сервер? | Рисование — нет; галерея JSON — нет; collab — да (и не нужна) |
| Новое окно? | Можно как эксперимент (внешний dgm.sh), без интеграции в код |
| Галерея у нас? | Только если пишем сами + решаем GPL/commercial |
| Что ближе к цеху? | DRAWINGS-301 + файловые вложения, не DGM.js |

**Если очень захочется whiteboard позже:**

1. Сначала сценарий: «кто открывает, зачем, куда крепится результат».
2. Лицензия commercial **или** MIT-альтернатива (Excalidraw и т.п.).
3. Отдельный lazy route / iframe, не раздувать каждый экран.
4. Не путать в UI с «Чертежами» производства — другое имя («Доска» / «Скетч»).

**Сейчас по северу:** не тратить очередь исполнителей на DGM; ZIP можно держать локально как reference, **не коммитить** в git (~16 MB исходников).
