## Что поправить в плане до lock (обязательно)

1. **Строка «Counterparty: нет полного CRUD на /counterparties» неточна.** Backend CRUD **полный**: `counterparty.controller.ts` — GET/GET:id/POST/PATCH/DELETE + `POST /quick`; FE-сервис `pi-counterparty.service.ts` тоже имеет методы. Дыра — только UI-слой (страница read-only, нет формы/диалога). W1 для CP — это FE-волна, backend-TZ не нужен. Если TZ напишут «сделать CRUD API» — работа задублируется.
2. **Строка «Photos: нет ролей файла» — верна, но W3 меньше, чем звучит.** Комментарий в `photo.schema.ts` («upload via multer is a TODO, metadata only») — **устарел**: `POST /photos/upload` с `FileInterceptor` уже сохраняет файлы в `./uploads/` и создаёт Photo-запись; продукт-форма и quick-create им пользуются (`PiPhotoDropzoneComponent` — переиспользуемый shared-компонент). Реальная дыра W3: поле `role`/`kind` на Photo (logo/seal/signature/background), typed-слоты в UI org, RBAC на замену. Не «строить upload», а «добавить типизацию поверх готового». Заодно почистить устаревший NOTE в схеме.
3. **W4 столкнётся с двумя существующими image-пайплайнами.** В `document-template.service.ts` уже есть: (а) `backgroundImage[]` per-template с собственным upload (лимит 5, MIME allowlist), (б) блок типа `image`, рендерящий `settings.imageUrl`/data-uri через санитайзер. План должен явно сказать: W4 = **binding org-asset в существующий image-блок + расширение registry типом `image`**, а не третий параллельный механизм картинок. Иначе исполнитель W4 изобретёт свой.
4. **Вопрос 3 (сколько Organization) — не открытый greenfield, код уже наполовину решил.** `counterparty.schema.ts`: `organizationId` + compound sparse unique `{organizationId, inn}`, list-фильтр по `user.organizationId`; миграции TZ-238/240/241. **Но**: на поле `inn` у CP одновременно висит глобальный `unique: true` — компаунд-индекс мёртвый, один клиент под двумя юрлицами невозможен. Если PO ответит «несколько юрлиц», это конфликт индексов = отдельный TZ с миграцией, план должен его назвать.
5. **«Реквизиты PDF одной кнопкой» (тема C / W4) — в коде нет ничего**, даже заготовки endpoint. Это честно новый scoped-TZ (готовый шаблон «Реквизиты» + кнопка на карточке Org), не «допилить». Не обещать PO как быстрый бонус W4 — оценивать как отдельную единицу.
6. **W1 «Org FullEditor = schema» — уточнить объём.** Текущий диалог — маленький модал; целевой kind C 1120 со всеми секциями schema (банк, паспорт ИП, photoIds) — по факту новый компонент по канону `docs/pages/ui-dialog-canon.md`. В TZ писать «новый FullEditor», иначе исполнитель будет растягивать модал.
7. **Адреса (вопрос 2): в плане не упомянут Site.** Адрес объекта клиента уже живёт в `Site` (quick-create его создаёт). Решение по legal/actual address должно явно разграничить «юр. адрес стороны» vs «адрес объекта», иначе поля задублируются.

## Ответы на открытые вопросы плана (1–7)

1. **Провайдер ИНН:** рекомендую DaData (стабильный API, suggestions по ИНН/названию), строго через backend-proxy: ключ в env, rate-limit, аудит запросов. Бесплатные гос-API (ЕГРЮЛ выгрузки, api-fns) — нестабильные ToS/SLA, не для W2. Если бюджета нет — W2 честно паркуется, checksum-only + предупреждение в UI. **Нужен вердикт PO по бюджету/ключу.**
2. **Адреса в schema:** на первый релиз (W1) — **не добавлять**; банк+ИНН+КПП достаточно, адрес объекта уже есть в Site. Добавить `legalAddress` в Org+CP в W2 вместе с lookup (провайдер его отдаёт бесплатно в том же ответе) — тогда поле появляется вместе с автозаполнением, а не как ручная обязаловка. Нужен вердикт PO только если договоры требуют юр. адрес раньше W2.
3. **Одна Organization или много:** рекомендую зафиксировать **«одна наша фирма» на прод-инстанс** (prod-политика, не удаление кода multi-org). Если PO скажет «несколько юрлиц» — сначала TZ на конфликт индексов CP.inn (см. правку 4) и на scope vault/lookup. **Нужен вердикт PO — блокирует W3 (vault per-org?) и W2.**
4. **Кто меняет печать:** только `admin`, с аудит-записью на upload/replace/delete (паттерн `@AuditAction` уже повсеместен). Manager — использует в документах, не заменяет. Вердикт PO желателен, но default безопасный.
5. **Клиентские фото сразу?** Нет. `photoIds` у CP в схеме уже есть — ничего не теряем, UI отложим. W3 — только vault нашей фирмы (logo/seal/signature/background). Сканы паспортов клиентов — это ещё и PII-вопрос, не тащить в демо.
6. **Приоритет W5 vs W3:** день менеджера (W5) важнее ежедневно, но по PO-DIARY демо-гордость — «документ выглядит по-настоящему». Компромисс: W3 и W5a (stub-КП D7 + дыры статусов) **параллельно** — conflict keys не пересекаются (org/photos vs quotation/order). Не выбирать «или-или». **Нужен вердикт PO, что показывается на ближайшем демо.**
7. **INN в quick-create заказа:** да, в W2, но не ломая скорость quick-create: поле ИНН опциональное; ввёл — lookup+prefill+подтверждение человеком; пропустил — stub как сейчас, но с видимым бейджем «ИНН временный» в карточке CP. До W2 — добавить бейдж уже в W1 (копеечная правка), чтобы менеджеры не верили стабам.

## Риски и Ban

- **Не обещать** «ИИ сам собрал юридически верное КП» и «реквизиты подтянутся сами без проверки человеком» — lookup всегда HITL (человек подтверждает перед сохранением), ошибочные реквизиты в договоре дороже ручного ввода.
- **Ключ API и деньги:** DaData платный; ключ только в backend env, никогда в FE-бандл; лог запросов без тела ключа. Без бюджета — W2 не начинать.
- **Multi-org security:** пока политика «одна фирма» не зафиксирована, не строить vault/lookup с допущением N юрлиц — и наоборот. Конфликт индексов CP.inn (глобальный unique vs compound) — мина под multi-org, обезвредить до обещаний.
- **Upload печати/подписи:** это фактически материал для подделки документов — RBAC admin, MIME/size-лимиты (паттерн background-upload уже есть), файлы не в публичной раздаче без auth. Проверить, что `/uploads/` не отдаётся без токена, до W3.
- **Stub-ИНН копятся в проде:** каждый quick-create до W2 добавляет фейковый ИНН; в W2 заложить merge/уточнение существующих CP, не только создание новых.
- Ban плана (не тащить Гант/SHIPPING/бухгалтерию, не писать код до lock) — поддерживаю без правок.
