# КП: реальные фото и безопасное редактирование строк — канон 2026-08-13

## Экран должен

Менеджер добавляет изделие, сразу видит его реальное фото и все рабочие поля строки, свободно подгоняет текст под конкретное КП, но **не меняет каталог случайным blur/autosave**. Если вариант достоин каталога — одной явной операцией обновляет исходное изделие или создаёт полноценную копию.

## Что проверено в коде

- `proposal-create-table-editor.component.ts`: описание, единица, qty/price/sum уже inputs; название является input только для `custom`, а у catalog-строки статично.
- `proposal-create.page.ts`: live build передаёт `photoUrl`; Quotation payload сохраняет `photoUrl`; кнопка-карандаш открывает `ProductFormDialog` и меняет Product SoT немедленно.
- `quotation-output.service.ts`: main saved quotation → PDF rebuild **теряет `photoUrl` и `sheetLayout`**; WIP TZ-SALES-370 уже закрывает `photoUrl`, поэтому successor обязан сначала проверить landed diff.
- `DEFAULT_KP_TABLE_LAYOUT`: поля `photo` нет, хотя `showPhotoColumn=true`; настройка фактически не может показать отсутствующую колонку.
- `table-template.service.ts` / `document-template.service.ts`: image-cell поддержан, но synthetic layout aliases не создают `photo`; относительный `/uploads/...` ненадёжен для Puppeteer `page.setContent(about:blank)`.
- `КП4` отсутствует в repo seed и является DB-шаблоном; canonical `КП — позиции` также не имеет photo-column.
- `proposal-product-rail.component.ts`: при add копирует name/sku/photo/unit/price, но не description.
- `duplicateCompositionLine()` сейчас копирует только строку-snapshot и сохраняет тот же `productId`; это **не** копия изделия каталога.
- `ProductSchema`: `(organizationId, sku)` unique; уже есть `copiedFromProductId`, но product duplicate endpoint отсутствует.
- Миграция KP3 намеренно была без фото: реальные файлы ждут `TZD-47 → TZ-MIG-303`. UI не может показать фото, которого ещё нет в `Product.photoIds`.

## Диагноз

Проблема не одна:

1. У импортированных изделий пока может не быть `photoIds` — это data gap.
2. Даже при существующем фото default КП-layout не содержит колонку `photo`.
3. Live preview и сохранённый PDF расходятся: server output не передаёт `photoUrl`.
4. Для server PDF относительный URL может не загрузиться.
5. Поля существуют, но catalog name намеренно read-only, а часть колонок можно скрыть; поэтому редактор воспринимается как нер редактируемый.
6. Текущий карандаш опаснее ожидаемого UX: он правит единый Product сразу, без выбора «только КП / обновить / копия».

## Выбранная модель

### 1. Строка КП = snapshot

Все inline-правки сначала меняют только `QuotationItem`:

- наименование;
- описание;
- артикул-snapshot;
- единицу.

Количество, цена КП, сумма, скидка и `Опц.` по-прежнему являются только коммерческими данными КП и никогда не синхронизируются в Product.

Фото выбирается из карточки/медиатеки изделия; inline upload в ячейку не добавляется этой волной.

### 2. Каталог не мутируется автоматически

У изменённой catalog-строки появляется спокойный маркер `Изменено для этого КП`. При выходе из панели таблицы показывается единый обзор только если есть нерешённые изменения:

1. **Оставить только в КП** — безопасный default; каталог не меняется.
2. **Обновить исходное изделие** — явное подтверждение, permission + optimistic conflict.
3. **Создать копию изделия** — backend создаёт новый Product, строка перепривязывается к нему.
4. `Отмена` возвращает в редактор.

Закрытие обзора крестиком эквивалентно безопасному `Только в КП`; данные строки уже autosaved в draft КП и не теряются.

Для нескольких изменённых изделий обзор показывает список и решение по каждой строке; нельзя одной кнопкой случайно перезаписать все карточки.

### 3. Настоящая копия Product

Новая копия:

- имеет новый `_id`;
- `name = "<исходное> — копия"` с разумным повторным суффиксом;
- SKU генерируется сервером (`<SKU>-COPY-1`, следующий свободный в organization scope);
- `copiedFromProductId` указывает на источник;
- переносит паспортные поля, category, description, unit, цены, composition, EAV и ссылки на Photo;
- не переносит складской остаток и системные/audit поля;
- создаётся `draft/new`, затем строка КП получает новый `productId`.

Копия строки КП без копии Product остаётся отдельным действием и должна называться `Дублировать строку`, чтобы не обещать новый товар.

### 4. Фото

- В базовом layout появляется видимая колонка `Фото`; пользователь может скрыть её явно.
- При наличии `photoIds` в строку попадает реальный thumb/medium URL.
- Live A4, browser print и server PDF используют один `photoUrl`.
- Backend нормализует URL для PDF или безопасно встраивает разрешённый локальный asset; raw внешние/file URL запрещены.
- Если у Product нет фото, показывается нейтральное `Нет фото`, а не сломанная картинка.
- Для импортированных KP3 изделий окончательная наполненность зависит от `TZD-47 → TZ-MIG-303`.

## Почему не прямое редактирование Product

Blur/autosave в таблице КП слишком легко меняет каталог для всех будущих документов. Это нарушает ожидание менеджера и историчность КП. Snapshot-first даёт быстрый рабочий поток; глобальная мутация остаётся осознанным действием.
