# Live test: Desktop/MCP Import Task flow на реальном файле заказа

**Дата:** 2026-08-22
**Источник:** прямая просьба PO — прогнать реальный импорт через локальный стек (не прод), проверить desktop-приложение вживую.
**Файл:** `tmp/test-orders/Заказ №25 Дортранссервис.xlsx` (реальный заказ клиента «Дортранссервис» от поставщика «Спортстройюг», НЕ форма каталога).
**Зона:** `desktop/mcp/src/import-task-tools.ts` (TZD-22/23), `backend/src/modules/import-task/*`, `desktop/src/importers/excel.ts` (для сравнения с тем, как парсит Desktop UI).
**Код не менялся.** Это тест + отчёт, без правок продукта.

---

## Вердикт

**Инженерный контур ImportTask → AI match+report → apply_plan работает end-to-end без единой ошибки** на реальном, «грязном» Excel-файле — не форме каталога, а живом заказе поставщика. Все шаги Variant C protocol (TZD-23) прошли, журнал mutation-journal получил 10 корректных `proposed` material.create записей, SoT (каталог материалов) не тронут — как и требовалось (стоп на `apply_plan`, без `confirm`).

**Готовность к боевой работе — частичная, с оговоркой:** сам конвейер (ImportTask/MCP/journal) надёжен и ничего не сломал. Но использование его **напрямую для файлов типа «заказ клиента»** — не по назначению: инструмент проектировался для каталога (материалы/товары), а не для строк заказа с количеством. Если менеджер вручную скормит такой файл через Desktop «Импорт», результат будет *технически корректным, но бизнес-бесполезным*: 10 новых «материалов»-заглушек без количества, без связи с заказом/КП. Ниже — детали и что нужно доделать, прежде чем показывать это менеджерам как «импорт заказов».

## Как гонялось (окружение)

1. Локальный стек поднят через `node start.mjs --no-browser` (Mongo 7 replica set через `docker-compose.yml` + backend `:3000` + frontend `:4200`, dev, НЕ прод).
2. Логин `admin@kppdf.local` / `admin123` (default dev seed) → JWT.
3. Pairing key выпущен через `POST /api/desktop/pairing-keys` (тот же путь, что использует Desktop-приложение при паринге, см. `desktop/docs/PAIRING.md`).
4. MCP host поднят вручную по «dev fallback» из `desktop/docs/MCP.md` (`cd desktop/mcp && pnpm start`, env `KPPDF_API_BASE_URL`/`KPPDF_API_KEY`) — **тот же код**, что запускает установленное Desktop-приложение при автозапуске MCP; `GET /healthz` → `toolCount: 95`, `ok: true`.
5. Вызовы `kppdf_import_task_*` сделаны напрямую в MCP host по HTTP (Streamable HTTP, `POST /mcp`, `tools/call`) — тем же протоколом, которым пользуются Cursor/LM Studio/агент.

**Не проверялось:** сама Tauri-оболочка Desktop (Svelte UI, кнопки «Разобрать»/«Создать задачу для ИИ» вручную мышкой) — у сессии нет интерактивного доступа к GUI-окну. Проверен инженерный движок один-в-один (тот же MCP host, тот же backend API), которым эта оболочка пользуется — то есть путь `/desk`→кнопка не проверялся, а путь file→ImportTask→plan→proposal проверен по-настоящему.

## Что сделано (шаги Variant C protocol, TZD-23)

| Шаг | Tool | Результат |
|---|---|---|
| 1 | `kppdf_ping` | `ok: true`, вернул профиль `admin` — MCP↔backend связь живая |
| 2 | `kppdf_import_task_create` | Создан `ImportTask id=6a893acf8cf2cb0dc5716335`, статус `ready_for_ai`, 10 строк, `proposalIds: []` |
| 3 | `kppdf_import_task_get` | Строки вернулись 1:1 с тем, что отправили — round-trip без потерь |
| 4 | AI match (вручную, best-effort, как предписывает протокол) | Поиск по `kppdf_list_materials?search=<ключевое слово>` для каждой из 10 позиций (Стойка/Ворота/Флагшток/Секция/Столб/Скоба/Сетка) → **0 совпадений** во всех случаях (локальный dev-каталог содержит только тестовый мусор вроде материалов «01», «55») |
| 5 | `kppdf_import_task_set_report` | План: **10 new / 0 skip / 0 update / 0 doubt** → статус `awaiting_user` |
| 6 | `kppdf_import_task_apply_plan` (`userOk: true`) | 10 `material.create` proposals в mutation-journal, `proposalIds` заполнены, статус `applying` |
| 7 | `GET /api/mutation-journal/:id` × 10 | Все 10 в статусе `proposed`, `expiresAt` +1ч — журнал, **не** SoT |
| 8 | `GET /api/materials?search=...` | `total: 0` — каталог **не изменился** (подтверждение того, что `confirm` не вызывался, как и просил PO) |

Полный сырой лог всех 8 вызовов (request/response) сохранён локально в
`scratchpad/flow-log.json` этой сессии (не коммитился — временный тест-артефакт, не часть репозитория).

Сверка «оригинал xlsx (10 строк, лист `Лист1`, шапка в строке 6)» ↔ «что дошло до proposal»:

| № | Наименование (оригинал, сокращённо) | Кол-во | Ед.изм. | В proposal? | Замечание |
|---|---|---|---|---|---|
| 1 | Стойка баскетбольная г-образная… | 4 | шт | ✅ name+unit точны | многострочный текст (`\n` внутри ячейки) корректно склеен в одну строку |
| 2 | Стойки волейбольные с механизмом… | 1 | компл | ✅ | unit «компл» не входит в `recommendedUnits` (шт/м/м²/кг/л), но принят как free-string — не блокер |
| 3 | Ворота мини-футбольные… | 1 | пара | ✅ | unit «пара» — та же ситуация |
| 4 | Флагшток h 6м | 3 | шт | ✅ | — |
| 5 | Металло-профильная секция ограждения 2420х1900мм | 110 | шт | ✅ | — |
| 6 | Опорный столб ограждения 80х80… | 56 | шт | ✅ | — |
| 7 | Скоба в комплекте с крепежом | 452 | шт | ✅ | — |
| 8 | Металло-профильная секция… с калиткой | 2 | шт | ✅ | — |
| 9 | Сетка волейбольная арт.040430 | 1 | шт | ✅ name; article «040430» **извлечён вручную** из текста имени | инструмент это не делает автоматически — я как AI-агент разобрал строку сам на шаге matching. Голый пайплайн (без вдумчивого AI-этапа) оставил бы артикул внутри `name` |
| 10 | Сетка для мини-футбольных ворот… | 1 | пара | ✅ | — |

**Имена и единицы измерения совпали на 10 из 10 (100%).** Единственная системная потеря — **«Кол-во» (количество) нигде не сохраняется**: схема `kppdf_import_task_*` / `material.create` proposal не имеет поля qty (`rowSchema`/`proposed` в `desktop/mcp/src/import-task-tools.ts` — только `name/unit/article/sku/notes/kind`). Это **не баг этого прогона**, а архитектурное ограничение, задокументированное в `desktop/docs/MCP.md`: «Order / коммерческое КП kinds — не этот TZ» / «Orders / Production / Gantt — out of scope here». ImportTask — это конвейер **каталога** (материалы/товары), не заказов.

## Картинки

**В исходном файле нет ни одной встроенной картинки** (проверено `openpyxl`: `ws._images` → `0` для единственного листа). Проверить «совпали ли картинки» физически не на чем — источник для сравнения отсутствует.

Отдельно, по коду: `desktop/src/importers/excel.ts` использует библиотеку `xlsx` (SheetJS) через `sheet_to_json`, которая **не читает встроенные изображения** в принципе — в парсере нет ни одной строки, работающей с картинками. Если бы в файле были картинки (частый случай для реальных заказов/КП с фото товара), **текущий Excel-импорт Desktop их бы молча проигнорировал** — ни ошибки, ни предупреждения. Фото — отдельный контур (`kppdf_propose_photo_upload`/`confirm_photo_upload`, по одному файлу за вызов, TZD-47), никак не связанный с Excel-импортом. Это стоит знать заранее, если менеджеры ждут, что «картинки в заказе попадут в карточки товаров» — сейчас это не так.

## Что сработало

- MCP host (тот же код, что и в установленном Desktop) стабильно поднимается локально, авторизуется по pairing key, отвечает 95 tools.
- Полный protocol TZD-22/23 (create → get → set_report → apply_plan) прошёл без единой ошибки на «диком» файле, не подготовленном под форму каталога — заголовок нашёлся правильно (строка 6, а не строка 1 с «шапкой» документа), пустые декоративные колонки («Вид», «Цвет») корректно остались в `raw`, но не мешали.
- HITL-гейт реально держит: `apply_plan` без `userOk:true` был бы отклонён (не проверяли отдельно в этом прогоне, но код `applyImportTaskPlan` жёстко требует `userOk`); SoT не тронут — proposals «зависли» в журнале ровно как спроектировано (TTL 1ч, ждут `kppdf_confirm_proposal`).
- Round-trip данных (create → get) без потерь символов, кириллицы, переносов строк.
- Многострочные названия (перенос строки внутри ячейки Excel) корректно нормализуются в одну строку при формировании `name`.

## Что сломалось / чего не хватает

1. **Нет извлечения количества.** Реальный кейс «менеджер закинул файл заказа» даёт 10 «материалов» без единой цифры количества — бесполезно для реальной работы с этим типом файла. Не баг конвейера, а несоответствие ожиданий: инструмент для каталога использован на заказе.
2. **Нет автоматического извлечения артикула из текста названия** (`арт.040430` осталось бы частью `name`, если бы AI-шаг не разобрал его вручную) — «best-effort matching» в протоколе полагается на агента, а не на детерминированный парсер; при слабом/невнимательном AI-агенте артикул потеряется в тексте.
3. **Картинки Excel не извлекаются вообще** (см. выше) — архитектурный пробел, не специфичный для этого файла, но релевантный для реальных заказов с фото.
4. **Нестандартные единицы измерения** («компл», «пара») проходят без предупреждения — не блокер, но `kppdf_get_domain_schema` рекомендует только шт/м/м²/кг/л; несовпадение молча остаётся в свободной строке.
5. Desktop GUI (Tauri/Svelte) в этом прогоне не кликался вручную — визуальная часть («Разобрать», предпросмотр, кнопка «Создать задачу для ИИ») не подтверждена интерактивно, только через код и то, что дергает те же MCP tools.

## Общий вывод

Инженерный фундамент (Import Task + MCP + mutation-journal) **готов и надёжен** для его прямого назначения — сборки каталога материалов/товаров из Excel. Он **не готов** заменить собой полноценный импорт заказов клиента (нет количества, нет связи с Order/Quotation entity — что и так задокументировано как «out of scope» в `desktop/docs/MCP.md`). Прежде чем давать этот путь менеджерам как «импорт заказа», нужно либо (а) явно предупреждать в UI, что Excel-импорт кладёт строки в каталог материалов без количества, либо (б) сделать отдельный TZ на Order/Quotation-line импорт с сохранением qty — вне рамок этого теста.

## Артефакты теста

- Локальный стек: поднят и остановлен в рамках этой сессии (Mongo/backend/frontend через `start.mjs`, MCP host через `desktop/mcp`), прод не затронут.
- Созданный `ImportTask` (`6a893acf8cf2cb0dc5716335`) и 10 `proposed` mutation-journal записей остались в **локальной dev БД** (не прод) в статусе `proposed`/`applying` — они истекут по TTL (1ч) или их можно отменить вручную (`kppdf_cancel_batch`) при следующей сессии на этом стенде.
- Код не менялся: diff по продуктовым файлам — пустой.
