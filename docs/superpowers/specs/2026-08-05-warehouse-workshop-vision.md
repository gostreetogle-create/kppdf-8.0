## 1. Что хочет PO (своими словами → правило)

1. **Склады — живой справочник**, не «два захардкоженных имени».
   - Создаю склад → вписываю **название** (Трубы / Листовой металл / Деревянный цех / …).
   - Список редактируемый: переименовать, выключить, зоны.

2. У склада есть **ответственный** (сотрудник / роль).
   - **Смотреть** остатки/движения могут многие (у кого есть доступ к разделу Склад).
   - **Вести** (приход/расход/корректировка, правка карточки склада) — ответственный (+ admin/manager).

3. Материал **не «прибивается» к одному складу навсегда**.
   - Каталог материалов = «что покупаем».
   - Остаток = `StorageItem` на конкретном складе (труба может лежать и на «Трубах», и на «Производстве»).
   - С материалов ссылка «Склад →» уже ведёт на остатки с фильтром `materialId` — это правильно; dropdown «домашний склад» на материале — опционально позже, не SoT.

4. В будущем у сотрудника может быть **узкий вход**: видит только «свой» склад (как Excel-таблицу цеха), без остального ERP. Это отдельная ACL-фаза после карточки склада + приход/расход UI.

## 2. Как сейчас (as-built)

| Слой | Факт |
|------|------|
| `Warehouse` | API CRUD есть; seed: «Главный склад», «Производственный цех». Поля: `name`, `type`, `zoneNames`, `roleIds[]` (**не enforcement**) |
| `StorageItem` | Остаток material/product × warehouse × zone — **канон количества** |
| `StockMovement` | `in/out/transfer/adjust` на бэке атомарно меняют qty |
| FE `/inventory`, `/storage-items`, `/stock-movements` | **только чтение** + фильтры-чипы |
| FE create/edit склада | **нет** |
| FE приход/расход формы | **нет** |
| `Material.stockQty` | legacy, не SoT |

Итог: названия **не захардкожены в коде** — просто **нет экрана**, чтобы их создавать/править, и seed даёт два дефолта.

## 3. Модель доступа (целевая)

```
Warehouse
  name, type, zones, isActive
  ownerPersonId? | ownerUserId?   ← ответственный (новое поле; сейчас только roleIds[])
  roleIds[]                       ← опционально: роли с правом вести этот склад

Правила:
  warehouse:read  → видит списки/остатки (все склады или scoped — фаза 2)
  warehouse:write → правит карточку + движения (admin/manager ИЛИ owner склада)
```

Фаза 1 (минимум для PO сейчас): admin/manager ведут все склады; owner — подсветка «кто отвечает».  
Фаза 2: enforcement `owner` / `roleIds` на PATCH movements + UI hide чужих CTA.  
Фаза 3: worker login → только `/storage-items?warehouseId=mine` (+ движения своего склада).

## 4. UI в разделе «Склад» (целевой TOC)

| Чип TOC | Назначение |
|---------|------------|
| Дашборд | сводка / low-stock (как сейчас) |
| Остатки | qty по складам (фильтр-чипы складов) |
| Движения | журнал + **форма приход/расход** (фаза после реестра) |
| **Склады** *(новое)* | таблица складов: создать / переименовать / ответственный / зоны / активен |

Не дублировать реестр складов в «Справочники» — дом в **Склад**.

## 5. Поля — что добавить когда дойдём до кода

**Warehouse (дополнить):**
- `ownerUserId` или `ownerPersonId` (FK → User / Person) — ответственный
- оставить `type` (main/production/…) или заменить/дополнить `workshopKind` — по желанию PO при первой реализации
- `roleIds` — включить в guard, не оставлять мёртвым

**Не делать:**
- обязательный `warehouseId` на `Material` как единственный SoT остатка (ломает multi-warehouse)
- хардкод имён складов во frontend

**Material (опционально, низкий приоритет):**
- `defaultWarehouseId?` — только подсказка для формы прихода, не остаток
