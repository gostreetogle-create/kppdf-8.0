## 0. Контекст и причины появления

TZ-257 (Admin module) формально закрыт — read-only slice shipped
на `/api/admin/users` (list + getById) и `/api/admin/roles` (list + getById).
Backend typecheck PASS, frontend typecheck PASS, both DTO mappers
verified NE-LEAK passwordHash, LastAdminGuard spec green (8/8).

Однако TZ-257 §ШАГ 1 explicitly lists mutations как «scoped to a TZ-257.A
follow-up». Этот follow-up собирает:

1. **Admin mutation endpoints** — create / patch / change-password / activate
   / deactivate / soft-delete for users; create / patch (with isSystem-readonly
   enforcement) / delete (refuse if isSystem) for roles.
2. **Frontend action buttons + dialogs** — TZ-232.G form-dialog pattern.
3. **LastAdminGuard per-method** — was DELETED at class level in TZ-257 mainline
   (where it's a no-op because GET :id doesn't mutate); now applies to
   `POST /:id/deactivate`, `DELETE /:id` mutators.
4. **Mass-assignment protection** — user schema has `permissions`, `role`,
   `isActive`. A naive `Object.assign(user, dto)` would let the client
   self-promote. TZ-257.A MUST enforce explicit DTO whitelist per mutation
   endpoint.

## 1. Acceptance criteria

### 1a. Backend user mutations

| Endpoint | Permission | Role | Body DTO | LastAdminGuard |
|----------|------------|------|----------|----------------|
| `POST /api/admin/users` | `user:admin` | `admin` | `CreateUserDto` (whitelist: username, email, displayName, role ∈ {user, manager}, permissions[]) | n/a (creates, not last-admin issue) |
| `PATCH /api/admin/users/:id` | `user:admin` | `admin` | `UpdateUserDto` (whitelist: displayName?, role?, isActive?, permissions?) | YES if target.role='admin' |
| `POST /api/admin/users/:id/change-password` | `user:admin` | `admin` | `{ newPassword: string }` (server bcrypts) | NO (admin can change any non-admin password; if last-admin attempted self-bump-refresh, log out self) |
| `POST /api/admin/users/:id/activate` | `user:admin` | `admin` | n/a | YES if target is currently inactive-admin (counterintuitive — releasing an inactive admin back to active means check) |
| `POST /api/admin/users/:id/deactivate` | `user:admin` | `admin` | n/a | YES (the canonical last-admin case) |
| `DELETE /api/admin/users/:id` | `user:admin` | `admin` | n/a | YES (the canonical last-admin case) |

### 1b. Backend role mutations

| Endpoint | Permission | Role | Notes |
|----------|------------|------|-------|
| `POST /api/admin/roles` | `role:admin` | `admin` | Body: `{ name, description?, permissions: PermissionKey[] }`. Always `isSystem: false`. |
| `PATCH /api/admin/roles/:id` | `role:write` | `admin` | Body: `{ description?, permissions? }`. `isSystem=true` → refuse with 403. |
| `DELETE /api/admin/roles/:id` | `role:admin` | `admin` | `isSystem=true` → refuse with 403. |

### 1c. DTO whitelist (CRITICAL mass-assignment concern)

Each DTO MUST use class-validator + class-transformer `@Exclude()`
or `Pick<>` to whitelist fields. Specifically:

`backend/src/modules/admin/dto/create-user.dto.ts`:
- Pick: `username`, `email`, `displayName`, `role`, `permissions`.
- Validator: `role ∈ {'user','manager'}` (NOT `admin` — DB seed handles admin).
- Validator: `permissions: PermissionKey[]` (validated against PERMISSIONS catalog).

`backend/src/modules/admin/dto/update-user.dto.ts`:
- Pick: `displayName?`, `role?`, `isActive?`, `permissions?`.
- All-optional partial DTO.

### 1d. Frontend action buttons + dialogs

`frontend/src/app/shared/services/admin-users.service.ts`:
- `create(dto)`, `patch(id, dto)`, `changePassword(id, newPassword)`,
  `activate(id)`, `deactivate(id)`, `delete(id)`.
- Returns `Observable<ClientUser>` / `Observable<void>` / etc.

`frontend/src/app/shared/services/admin-roles.service.ts`:
- `create(dto)`, `patch(id, dto)`, `delete(id)`.

Pages use `PiEntityList`/TZ-232.G form-dialog pattern. Each action posts
to the server, refreshes the list on success, surfaces toast via
existing inline error UI.

### 1e. LastAdminGuard per-method wiring

- `POST /api/admin/users/:id/deactivate` → `@UseGuards(LastAdminGuard)`
- `DELETE /api/admin/users/:id` → `@UseGuards(LastAdminGuard)`
- `POST /api/admin/users/:id/activate` → `@UseGuards(LastAdminGuard)`
- Other endpoints → no LastAdminGuard

## 2. TransactionMiddleware integration

When `admin` mutation happens in a multi-step flow (e.g. role change +
permission array change both in PATCH), race conditions can compound.
When TZ-120 ships the Mongo session middleware, this TZ should rewire
the mutators to use `runInSession` for serializable isolation. Until
then, mark this as TOCTOU-known in the LastAdminGuard docstring.

## 4. Критерии приёмки

1. `POST /api/admin/users` whitelists fields; client cannot set `passwordHash`
   or `refreshTokenVersion` (verify via curl + integration test).
2. `PATCH /api/admin/users/:id` — last-admin invariant blocks the last admin
   from deactivating themselves (functional test).
3. `POST /api/admin/users/:id/change-password` — bcrypt-hashes on server,
   invalidates refresh tokens via `refreshTokenVersion++`.
4. `POST /api/admin/roles` — refuses to create with `isSystem: true`
   (acceptance test).
5. `PATCH /api/admin/roles/:id` with `isSystem=true` returns 403.
6. `DELETE /api/admin/roles/:id` with `isSystem=true` returns 403.
7. Frontend dialogs wired to admin-users / admin-roles services.
8. Audit log records every successful admin mutation (TZ-05 integration).
