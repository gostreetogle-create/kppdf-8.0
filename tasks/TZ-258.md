# TZ-258 — Protected-page onboarding и RBAC regression contract

**Статус:** READY / обязательная документационная задача после TZ-254/255; выполняется до массового добавления новых ролей и admin pages.

**РОЛЬ АГЕНТА:** Architecture Documentation + QA Engineer

**ЗАВИСИМОСТИ:** TZ-254, TZ-255 и TZ-256.

**LAYER:** 4

**CONFLICT KEYS:** `docs/add-new-page.md`; `docs/DEVELOPMENT-PATTERNS.md`; `docs/AI-AGENT-GUIDE.md`; `docs/pages/_template.md`; `frontend/src/app/app.routes.spec.ts`; `backend/test/**`; `backend/src/**/*.controller.ts`; `.github/workflows/ci.yml`

## Цель

Сделать добавление любой будущей CRM-страницы предсказуемым для человека и ИИ: authorization policy должна появляться одновременно с route, nav, API и тестами, а не «потом в админке».

## Что сделать

1. Добавить в page checklist обязательные поля: capability key, read/write/admin policy, server decorator/guard, route metadata, nav visibility, empty/403 state, audit action и tests.
2. Создать статический или тестовый audit, который выявляет protected controller methods без policy metadata и operational routes без базового auth guard.
3. Добавить шаблон permission-aware page spec: authenticated allowed role, authenticated denied role, direct URL, API 403, loading/error/empty states.
4. Документировать границу: backend policy — security, frontend visibility — UX, object ownership — service-level policy.
5. Связать DSL page/entity template с authorization metadata, но не заставлять generic `PiEntityList` самостоятельно принимать security decisions.

## Файлы для изменения

- Файлы документации из CONFLICT KEYS.
- Backend/frontend audit tests.

**Не изменять:** production authorization semantics — они задаются TZ-254/255; не добавлять новые бизнес-роли.

## Критерии приёмки

1. `docs/add-new-page.md` содержит полный authorization checklist с примером новой страницы.
2. CI/test audit показывает protected endpoints без policy metadata и выдаёт понятный путь исправления.
3. Есть готовые test templates для allow/deny, direct URL и API 403 сценариев.
4. AI-agent guide явно запрещает считать скрытие меню защитой и запрещает создавать новые role strings без matrix update.
5. Документационные проверки и существующие frontend/backend tests проходят.

## Ограничения

Это не новая security platform и не генератор enterprise policy. Цель — не допускать архитектурного дрейфа при добавлении страниц.
