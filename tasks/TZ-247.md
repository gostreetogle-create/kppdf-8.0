**Дата создания:** 2026-07-31 (canonical security/RBAC Wave-3 batch)

## 0. Цель

Любой mutating request (POST/PUT/PATCH/DELETE) с одинаковым `Idempotency-Key` должен создать **ровно один** side-effect; повторный запрос вернёт сохранённый результат. Тот же key с другим request-fingerprint → 409. Mongo TTL index держит записи ограниченное время. **Не** кэшировать пароли, токены, файлы, большие тела. Не применять к `/auth/login`, `/auth/refresh`, `/auth/logout`, `/health` без отдельного обоснования.

---

## 1. Контекст (проблема)

Frontend SubmitGuard (TZ-232.N) уже умеет двойной клик блокировать на UI-уровне, но это не заменяет backend enforcement. Сетевые retry, browser retry, multi-tab, mobile suspend/resume могут отправить идентичный запрос дважды — Mongo запишет дубль.

## 2. Архитектурное решение

### ШАГ 1: Storage schema + service

`backend/src/common/idempotency/idempotency-storage.schema.ts`:
- ключ: `idempotencyKey: string` (index unique sparse)
- `requestFingerprint: string` (CHMAC-SHA256(method+path+sorted-body-bytes))
- `cachedResponse: { status: number; body: object; storedAt: Date }`
- TTL index на `storedAt` (24h default; configurable через env `IDEMPOTENCY_TTL_HOURS`)
- не хранить: пароли (если в body), любые `token` / `refreshToken` поля → redact перед сохранением
- файловое содержимое / uploads (> X Б) не кешировать → fallback `cacheable: false`

### ШАГ 2: Middleware (NestExpress)

`backend/src/common/idempotency/idempotency.middleware.ts`:
1. Method ∈ {POST, PUT, PATCH, DELETE}? Иначе next()
2. Header `Idempotency-Key` present? Иначе next() (header optional, но если есть — enforce)
3. Exclude list: `/auth/login|register|refresh|logout|/health` → next() без проверки
4. Хеш fingerprint request body (skip для body > 256KB)
5. Lookup document по key:
   - **NOT FOUND**: continue, capture response, persist на успехе
   - **FOUND + fingerprint MATCH**: return cached response (status + body, fast-path)
   - **FOUND + fingerprint MISMATCH**: 409 Conflict, body `{code: 'IDEMPOTENCY_KEY_REUSED', message: 'Idempotency-Key reused with different payload'}`
6. Response interceptor — на 2xx и 4xx persist в storage
7. Forward `req.idempotencyKey` и `req.idempotencyFingerprint` для downstream logging

### ШАГ 3: Wiring

`backend/src/main.ts`:
- Register middleware после `cookieParser` (TZ-252) и до `NestFactory.create()`
- В Dev режиме (`NODE_ENV !== production`) — расширенный logging (debug)

### ШАГ 4: Tests

- backend: `idempotency.middleware.spec.ts` (unit) — 6 cases: no key, replay with match, replay with mismatch, large body > 256KB skip, exclude list, redact-secret
- backend: `idempotency.e2e-spec.ts` — POST /products дважды с одним key → одна запись; другой fingerprint → 409
- regression: existing tests pass (no middleware on GET)

## 4. Критерии приёмки

1. POST /products с одним `Idempotency-Key` ×2 → ровно 1 запись в Mongo, второй 200 с теми же данными (cached).
2. POST /products с повторным key, но изменённым body → 409 `IDEMPOTENCY_KEY_REUSED`.
3. POST /products без `Idempotency-Key` → продолжает работать (header optional).
4. /auth/login с key в заголовке → НЕ применяется (exclude list).
5. POST с body > 256KB → НЕ кэшируется (header silently ignored).
6. Storage TTL 24h → записи удаляются (тест с фейк-таймстампом).
7. return cached response зашифрован в Mongo, не plaintext (no passwordHash).
8. `pnpm test` exit 0; `pnpm e2e` exit 0; `pnpm typecheck` exit 0.
