# TZ-247 — Backend idempotency middleware

**Статус:** READY / отдельный cross-cutting backend фундамент.

**РОЛЬ АГЕНТА:** Backend Reliability + Security Engineer

**ЗАВИСИМОСТИ:** TZ-249 обязательно для исключения конфликта с auth/throttling bootstrap-файлами. Выполнять после проверки текущего frontend `Idempotency-Key` interceptor; frontend-часть не переписывать в этой TZ.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/common/idempotency/**` (NEW); `backend/src/app.module.ts`; `backend/src/main.ts`; `backend/src/database/**` (только idempotency schema/index registration); `backend/test/**`; `docs/DEVELOPMENT-PATTERNS.md`

## Цель

Закрыть dangling dependency из `tasks/TZ-232.md` и `tasks/TZ-236.md`: повторная доставка одного mutating request после network timeout не должна создавать дубли в MongoDB. Frontend-only `SubmitGuard` не является достаточной защитой от повторного запроса после перезапуска или потери ответа.

## Что сделать

1. Реализовать NestJS/Mongo idempotency storage для `POST/PATCH/DELETE` с ключом `Idempotency-Key`, request fingerprint и TTL index. Не применять автоматически к GET.
2. Для одинакового ключа и одинакового fingerprint вернуть сохранённый результат; для того же ключа с другим fingerprint вернуть `409 Conflict`; для параллельных одинаковых запросов дождаться одного владельца операции и вернуть единый результат.
3. Ограничить scope безопасными mutating API; login, refresh, logout и health не помещать в общий cache без отдельного обоснования.
4. Обеспечить bounded body/fingerprint policy: не сохранять пароли, токены, файлы и большие body в открытом виде; хранить только необходимый hash/response metadata по безопасной схеме.
5. Добавить cleanup/TTL index, structured logging без payload secrets и integration tests для concurrent/replay/mismatch/error cases.

## Файлы для изменения

- Новые idempotency module/service/schema/interceptor files в `backend/src/common/idempotency/**`.
- Регистрация в app/database только по необходимости.
- Backend tests и связанные docs.

**Не изменять:** frontend auth, `SubmitGuard`, production credentials, текущий builder UI; не выполнять live migration или production purge без отдельного согласования.

## Критерии приёмки

1. Два последовательных одинаковых mutating requests с одинаковым ключом дают один side effect и согласованные responses.
2. Два параллельных одинаковых requests дают один side effect; второй не запускает handler повторно.
3. Reuse ключа с другим fingerprint получает 409.
4. TTL index существует, response/fingerprint не раскрывают password/token/file contents.
5. Requests без ключа имеют явно задокументированную policy и не получают ложную защиту.
6. Backend tests, build и lint проходят; ссылки из TZ-232/TZ-236 на TZ-247 разрешаются существующим task-файлом и не требуют изменения чужих TZ в рамках этой задачи.

## Ограничения

Не добавлять Redis, Kafka или distributed lock service. Для текущего Mongo deployment достаточно одной Mongo collection с TTL и bounded in-flight coordination.
