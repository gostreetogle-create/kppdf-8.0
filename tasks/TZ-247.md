## ИСХОДНОЕ СОСТОЯНИЕ

**Pre-TZ-247:**
- Frontend (TZ-232.N) прикрепляет `Idempotency-Key: <uuid>` header на все state-changing requests.
- Frontend SubmitGuard обеспечивает Level 1 + 2 защиту (debounce 300ms + in-flight map + 5min completedCache).
- **Но:** network drop между fetch и response → frontend повторяет submit → backend создаёт duplicate record. Frontend cache Level 3 не достигает сервера.
- Backend не имеет idempotency middleware. Каждый POST/PATCH/DELETE выполняется без проверки на replay.

**Проблема (per TZ-232.N archive notes):**
> "Backend-side TZ-247 не реализован — frontend защита работает только в happy path. Network drops между fetch и response → пользователь повторяет submit → backend создаёт duplicate record (frontend cache Level 3 не достигает сервера)."

## ЧТО ДЕЛАТЬ

### Архитектурное решение (per thinker design)

**Interceptor vs Middleware:**
- Middleware (NestMiddleware) runs BEFORE APP_GUARD → `req.user` not yet populated → user-scoped idempotency impossible
- **Interceptor (NestInterceptor)** runs AFTER guards → `req.user` available → can scope by userId ✅
- Interceptor can use RxJS `tap` operator to capture response AFTER handler completes → can REPLAY cached response

**Execution chain:**
```
Request
  → RequestIdMiddleware (sets X-Request-Id)
  → JwtAuthGuard (validates JWT, sets req.user)
  → **IdempotencyInterceptor** (NEW; reads req.user + replays)
  → UserContextInterceptor (AsyncLocalStorage → Mongoose $locals)
  → AuditInterceptor (writes AuditLog)
  → RouteHandler
```

### Implementation

1. **IdempotencyRecord schema** with MongoDB TTL index (5 min default):
   ```typescript
   @Schema({ collection: 'idempotency_records', timestamps: { createdAt: true, updatedAt: false } })
   export class IdempotencyRecord {
     @Prop({ required: true, index: true }) key!: string;
     @Prop({ type: Types.ObjectId, index: true }) userId?: Types.ObjectId;
     @Prop({ required: true }) endpoint!: string;
     @Prop({ required: true }) payloadHash!: string;  // SHA-256({body,query})
     @Prop({ required: true, enum: ['IN_PROGRESS', 'COMPLETED'] }) status!: IdempotencyStatus;
     @Prop() statusCode?: number;
     @Prop({ type: Object }) responseBody?: Record<string, unknown> | unknown[];
   }
   IdempotencyRecordSchema.index({ key: 1, userId: 1 }, { unique: true });  // race-condition guard
   IdempotencyRecordSchema.index({ createdAt: 1 }, { expireAfterSeconds: 300, name: 'idempotency_ttl' });
   ```

2. **IdempotencyInterceptor** — atomic upsert flow:
   ```typescript
   const existing = await this.model.findOneAndUpdate(
     { key, userId },
     { $setOnInsert: { key, userId, payloadHash, status: 'IN_PROGRESS' } },
     { upsert: true, returnDocument: 'before' },
   );
   if (!existing) { /* WE ARE FIRST — run handler, capture response */ }
   else if (existing.payloadHash !== currentHash) { /* 409 Conflict */ }
   else if (existing.status === 'IN_PROGRESS') { /* 409 Race */ }
   else { /* REPLAY cached response */ }
   ```

3. **IdempotencyModule** — wires schema + interceptor + config:
   ```typescript
   @Module({
     imports: [
       ConfigModule,
       MongooseModule.forFeature([{ name: 'IdempotencyRecord', schema: IdempotencyRecordSchema }]),
     ],
     providers: [
       IdempotencyInterceptor,
       { provide: IDEMPOTENCY_CONFIG, useFactory: (cfg) => ({...}) },
     ],
     exports: [IdempotencyInterceptor, MongooseModule],
   })
   export class IdempotencyModule {}
   ```

4. **AppModule wiring** (3 edits):
   ```typescript
   // 1. Import IdempotencyModule
   imports: [..., IdempotencyModule, ...],
   // 2. Register APP_INTERCEPTOR between UserContext and Audit
   providers: [
     { provide: APP_INTERCEPTOR, useClass: UserContextInterceptor },
     { provide: APP_INTERCEPTOR, useClass: IdempotencyInterceptor },  // NEW
     { provide: APP_INTERCEPTOR, useClass: AuditInterceptor },
     ...
   ]
   ```

5. **Env vars** (in `env.validation.ts`):
   ```typescript
   IDEMPOTENCY_ENABLED: Joi.boolean().default(true),
   IDEMPOTENCY_TTL_SECONDS: Joi.number().integer().min(60).max(86400).default(300),
   IDEMPOTENCY_MAX_BODY_BYTES: Joi.number().integer().min(1024).default(5 * 1024 * 1024),
   ```

## КРИТЕРИИ ПРИЁМКИ (11 measurable items)

1. ✅ `Idempotency-Key` header attaches to POST/PATCH/DELETE responses, identical body twice within TTL → same response (no double DB write)

## ПОДСКАЗКИ ДЛЯ PO

### Что даёт TZ-247

**End-to-end double-submit protection:**
1. **Frontend** (TZ-232.N): SubmitGuard + Idempotency-Key header → защита от rapid double-click
2. **Backend** (TZ-247): IdempotencyInterceptor → защита от network drop retry
3. Together: пользователь не может создать duplicate ни при каких обстоятельствах

**Когда использовать `@SkipIdempotency()`:**
- Auth endpoints (login/refresh/logout) — `req.user` not yet populated
- Streaming responses (SSE, file downloads) — body нельзя кэшировать в BSON
- Oversized responses (>5MB) — BSON limit

**Когда НЕ используется:**
- GET/HEAD/OPTIONS — interceptor bypasses automatically
- Missing Idempotency-Key header — bypass (frontend always attaches for mutations)
