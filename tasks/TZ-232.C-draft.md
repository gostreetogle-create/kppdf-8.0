# TZ-232.C — Wave B: pi-entity-list + pi-entity-form Family (DRAFT)

> **Статус:** DRAFT (architectural sketch, не зафиксированный TZ).
> **Дата:** 2026-07-27
> **Преамбула:** TZ-232.A + TZ-232.N + TZ-232.B (Wave A) — фонд готов (`createLookupTable` + `createMutation` + `paramsToHttpParams` + `SubmitGuard` + `defineEntity` factory). Wave B собирает из этих примитивов более крупные DSL-компоненты для типовых list-page и form-dialog.

---

## 🎯 Цель Wave B

Сократить boilerplate каждой list-page и form-диалога до **< 100 LOC** net new code per page, при:

1. **Единая source of truth для каждой entity** — page знает только свой `EntityService<T, P>` от `defineEntity()`, всё остальное — общий компонент.
2. **Встроенная защита** — double-submit protection (через `createMutation`), error-banner (через inline `error()` signal), debounced search (через `createSearchState`).
3. **Темизация и a11y — централизованные** — focus ring (`pi-focus-ring`), zebra-rows, ARIA labels. Никакой кастомной стилизации per-page.
4. **Mapping сырых типов в UI-friendly форму** — `createLookupTable` для FK-резолва, `createClientSearchState` для client-side фильтрации.
5. **Zero дублирования** — page-specific код только: список колонок (`ColumnDef<T>[]`), form-группы (form fields конфиг), action permissions.

## 🏗️ Архитектура: 2 больших компонента + 4 helper'a

### B1. `<pi-entity-list>` — обёртка над `<app-pi-table>` для list-pages

**Файл:** `frontend/src/app/shared/ui/pi-entity-list.component.ts`

**Props (минимум для 80% страниц):**

```ts
@Component({ selector: 'app-pi-entity-list', standalone: true, changeDetection: OnPush })
export class PiEntityList<T extends { _id?: string }> {
  @Input({ required: true }) service!: EntityService<T, { page: number; limit: number; search?: string }>;
  @Input({ required: true }) cols!: ColumnDef<T>[];
  @Input() pageSize = 50;
  @Input() searchPlaceholder = 'Поиск…';
  @Input() ariaLabel!: string;
  @Input() rowActionsTpl?: TemplateRef<{ $implicit: T }>;
  @Input() createButtonLabel?: string;
  @Output() create = new EventEmitter<void>();
  @Output() rowEdit = new EventEmitter<T>();
  @Output() rowDelete = new EventEmitter<T>();
  @Input() canCreate = true;
  @Input() canEdit = true;
  @Input() canDelete = true;
}
```

**Под капотом:**

- `httpResource` для server-side pagination + error/loading signals (через `extractErrorMessage`)
- `createSearchState(300)` для debounced server search
- `createLookupTable` опционально для FK-резолва в column templates (если `col.lookupKey?`)
- Inline `<pi-row-actions>` для edit/delete
- Delete через `AlertDialogComponent` + `onDialogCloseOnce` + service.remove
- Toolbar: search input + create button + total counter via `pluralize(formArray)` + reload

**Page consumers:** zero HTTP boilerplate. Page only declares `cols` + handles `rowEdit` event → открывает `<pi-entity-form>` dialog.

**LOC reduction:** с ~482 LOC (materials.page.ts) до ~100 LOC for typical page.

### B2. `<pi-entity-form>` — обёртка над PiDialogComponent для form-dialogs

**Файл:** `frontend/src/app/shared/ui/pi-entity-form.component.ts`

**Props:**

```ts
@Component({ selector: 'app-pi-entity-form', standalone: true, changeDetection: OnPush })
export class PiEntityForm<T, C = Partial<T>> {
  @Input({ required: true }) service!: EntityService<T, unknown>;
  @Input() entity: T | null = null;          // null = create mode, T = edit mode
  @Input({ required: true }) formGroup!: () => FormGroup;   // factory for fresh form per open
  @Input() submitLabel = 'Сохранить';
  @Input() injectAdditional?: (form: FormGroup) => Record<string, unknown>;  // for cross-fields validation
  // Output: ref.close(result) handled internally — emits via DialogRef<Result> to PI_DIALOG_REF
}
```

**Под капотом:**

- `NonNullableFormBuilder` injection + formGroup factory-функция (per-dialog-instance form)
- `inject<T extends EntityService<T, …>>(service)` is used inside the factory: `createMutation(this.service.create/update)` — protection from double-submit встроена
- `errorMessage` signal для inline form errors + `extractErrorMessage` для backend errors
- `hasError(name)` / `errorFor(name)` методы (уже паттерны из `pages/materials/material-form-dialog.component.ts:91-104`)
- Lifecycle: form.reset() on init, markAllAsTouched() on submit invalid

### B3-B6. Helpers (opt-in, по необходимости)

- **`createEntityListConfig<T>(...)`** — fluent builder для типовой column-definition с lookup-резолвом вместо ручного `cols: ColumnDef<T>[]`
- **`createEntityFormConfig<T>(...)`** — fluent builder для form fields с auto-validation rules
- **`useEntityMutations<T>(service)`** — обёртка вокруг createMutation для batch-operations (multi-delete, bulk-update)
- **`pi-table-templates.service.ts`** — fragment cache для table templates per-entity (cell renderers → save LOC when re-using)

## 🎨 Builder Decomposition (TZ-232.C.7)

`builder.page.ts` (~1800 LOC) — это god-компонент. Декомпозиция (не BlockRenderer DSL):

- **`<pi-builder-canvas>`** — `<app-pi-table>`-style сетка полей документа + DnD зоны
- **`<pi-builder-inspector>`** — панель свойств выбранного блока (form + lookup)
- **`<pi-builder-tool-pane>`** — левая панель инструментов и блоков (reuses `<pi-entity-list>` для catalog'а available blocks)
- **`<pi-block-renderer>`** — atomic компонент для каждого типа блока (text/image/table/etc.)

Внутри builder.page.ts остается: **composable state machine + interactions** (drag/drop state, selection state, multi-select via TZ-113). Никакой rendering logic.

**Migration wave order (для builder'а):**

1. Вынести `<pi-block-renderer>` для text blocks (самый простой) → ~200 LOC вынесено
2. Вынести `<pi-block-renderer>` для image blocks → ~300 LOC
3. Вынести `<pi-builder-inspector>` как отдельный standalone component → ~500 LOC
4. Вынести `<pi-builder-tool-pane>` → ~400 LOC
5. Вынести `<pi-builder-canvas>` с DnD state machine → ~600 LOC
6. **Validation после каждой волны** — открыть `/builder` page → drag/select/edit/delete → screenshot test

## ⚠️ Designer Decisions (DD-C) — нужно согласовать перед Wave B

### DD-C1 — Granularity `<pi-entity-list>` props

- **(a)** Жёсткий schema — все props обязательны (current proposal)
- **(b)** Variant pattern с использованием `<pi-entity-list [config]>` где config — `PiEntityListConfig<T>` объект
- **Рекомендация:** (a) — emits are explicit, easier to refactor per-page

### DD-C2 — Form-handling strategy

- **(a)** Per-instance form via factory function (current proposal: `@Input formGroup: () => FormGroup`)
- **(b)** Host component управляет формой и передаёт control templates — компонент только обёртка
- **Рекомендация:** (a) — encapsulated, less boilerplate, matches `pages/materials/material-form-dialog.component.ts` pattern

### DD-C3 — Search strategy

- **(a)** Server-side debounced search (через `createSearchState`) — для большинства страниц (canonical 5-method)
- **(b)** Client-side filter (через `createClientSearchState`) — для небольших справочников (< 200 items)
- **(c)** Auto-detect (default к server-side, client при `clientSearch: true` prop)
- **Рекомендация:** (c) — declarative, default sane

### DD-C4 — Migration scope

- **(a)** Big-bang: мигрировать ВСЕ 16 list-pages за один TZ (рискованно)
- **(b)** Итеративно: сначала 4 простые, потом 4 средние, потом builder
- **Рекомендация:** (b) — matches existing TZ-115/116/117 patterns + validation per-wave
