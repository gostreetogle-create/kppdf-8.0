# TZ-256 — Capability-aware routes и навигация

**Статус:** READY / подключаемый frontend-модуль после серверного RBAC.

**РОЛЬ АГЕНТА:** Angular Authorization UX Engineer

**ЗАВИСИМОСТИ:** TZ-254 и TZ-255; для token contract учитывать TZ-252.

**LAYER:** 3

**CONFLICT KEYS:** `frontend/src/app/core/auth.service.ts`; `frontend/src/app/core/auth.guard.ts`; `frontend/src/app/app.routes.ts`; `frontend/src/app/layout/app-layout.component.ts`; `frontend/src/app/shared/ui/menu/pi-nav-dropdown.component.ts`; `frontend/src/app/shared/**`; `frontend/src/app/**/*.spec.ts`

## Цель

Добавить единый frontend-механизм для видимости разделов и маршрутов по capabilities, не создавая иллюзию, что UI заменяет backend authorization.

## Что сделать

1. Расширить auth state типизированным `hasPermission()`/`hasAnyPermission()` или эквивалентным capability service, использующим effective permissions из `/auth/me`.
2. Описывать permission requirement рядом с route metadata и nav item config, а не размножать `if (role === 'admin')` по компонентам.
3. Добавить route-level denial: недоступный route не показывается в навигации и при прямом URL даёт единый 403/forbidden экран или redirect без утечки данных.
4. Оставить `/kit/*` публичным только для безопасного UI showcase; operational routes должны оставаться под auth guard и backend policy.
5. Для actions внутри страниц использовать shared structural directive/helper только для UX visibility; API errors 401/403 обрабатывать единообразно.

## Файлы для изменения

- Файлы из CONFLICT KEYS.
- Shared UI tests и route tests.
- Документация по добавлению новой страницы.

**Не изменять:** backend authorization policy; не дублировать permission catalog вручную в каждом page component.

## Критерии приёмки

1. Новая страница подключается через один route/nav capability config без ручных role-условий в layout.
2. Недоступный пункт отсутствует в меню, а прямой URL не открывает защищённую страницу.
3. UI корректно различает auth loss (redirect/login) и forbidden (403 state).
4. `authGuard` остаётся базовой проверкой login; backend остаётся authority при ручном запросе.
5. Route, nav, capability и regression tests проходят; frontend typecheck, lint и build проходят.

## Ограничения

Не создавать отдельный frontend RBAC framework. Достаточно небольшого typed helper/directive и metadata-конвенции поверх существующих Angular routes и Paper & Ink UI.
