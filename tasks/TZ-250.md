# TZ-250 — Безопасные file uploads и static assets

**Статус:** READY / будущая задача. Только постановка работ.

**РОЛЬ АГЕНТА:** Backend File-Handling Security Engineer

**ЗАВИСИМОСТИ:** TZ-248 обязательно. TZ-249 не является обязательной зависимостью; выполнять параллельно с TZ-249 только после проверки CONFLICT KEYS.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/main.ts`; `backend/src/common/filters/multer-exception.filter.ts`; `backend/src/modules/document-template/document-template.controller.ts`; `backend/src/modules/document-template/document-template.service.ts`; `backend/src/modules/photos/photos.controller.ts`; `backend/src/modules/photos/photos.module.ts`; `backend/src/modules/inventor-file/inventor-file.controller.ts`; `backend/src/modules/inventor-file/inventor-file.module.ts`; `backend/src/modules/inventor-file/inventor-file.service.ts`; `backend/src/modules/import-jobs/import-jobs.controller.ts`; `backend/src/modules/product-photo/*`; `backend/test/**`

## Цель

Сделать все upload endpoints одинаково безопасными против oversized payloads, опасных расширений, MIME spoofing и stored XSS через публично доступные `/uploads/*`.

## Что сделать

1. Составить полный inventory всех `FileInterceptor`, `MulterModule`, `diskStorage`, `memoryStorage` и путей, которые раздаются через static assets.
2. Для каждого endpoint определить разрешённые типы, размер и назначение. Проверять не только расширение и заявленный MIME, но и сигнатуру/содержимое там, где это возможно.
3. Запретить SVG/HTML/скриптовые форматы для пользовательских фото и документов, если они не нужны функциональности. Имена хранения генерировать сервером; path traversal исключить.
4. Проверить, что загрузки не сохраняются в исполняемый web-root и что `/uploads/*` не позволяет браузеру выполнить пользовательский HTML/SVG на основном origin. Для файлов, которые должны скачиваться, выставить безопасный content disposition/type либо отдельный download path.
5. Добавить единый размерный лимит на уровне приложения и reverse proxy, понятные 400/413 ошибки и негативные tests.

## Файлы для изменения

- Файлы из CONFLICT KEYS.
- `docker-compose*.yml` и deployment docs только при необходимости согласовать upload volume/limits.
- Backend upload tests.

**Не изменять:** PDF rendering behaviour без regression test; не добавлять antivirus-сервис или object storage.

## Критерии приёмки

1. Каждый upload endpoint перечислен в тесте/inventory и имеет явные limits + allowlist.
2. Переименованный `.html`, SVG с активным содержимым, oversized file и path traversal не принимаются как безопасные пользовательские файлы.
3. Раздача `/uploads/*` не приводит к исполнению загруженного HTML/SVG на origin CRM.
4. Existing PNG/JPEG/WebP background/photo uploads и PDF workflow продолжают работать.
5. Ошибки размера/типа не раскрывают локальные пути и получают ожидаемые 4xx статусы.
6. Backend tests, build и lint проходят.

## Ограничения

Не внедрять WAF, antivirus sandbox или внешнее файловое хранилище для десяти пользователей. Нужны allowlist, content/size checks, безопасная раздача и тесты.
