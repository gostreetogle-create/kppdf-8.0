# TZ-257 — Admin module: users, roles и permissions

**Статус:** READY / подключаемый бизнес-модуль, не блокирует текущий конструктор документов.

**РОЛЬ АГЕНТА:** Full-stack Admin Module Engineer

**ЗАВИСИМОСТИ:** TZ-254, TZ-255, TZ-256 и TZ-258; TZ-251 для object-level checks; TZ-252 для auth session contract.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/modules/user/*`; `backend/src/modules/role/*`; `backend/src/modules/permissions/*`; `frontend/src/app/pages/admin/**`; `frontend/src/app/app.routes.ts`; `frontend/src/app/layout/app-layout.component.ts`; `frontend/src/app/shared/services/**`; `frontend/src/app/shared/dsl/**`; `frontend/src/app/pages/admin/**/*.spec.ts`

## Цель

Добавить админку как изолированный CRM-модуль: управление сотрудниками, ролями и permissions. Она должна использовать существующий DSL/UI kit и authorization contract, а не становиться новым параллельным framework.

## Что сделать

1. Создать admin section с отдельными страницами Users, Roles и Permissions/каталога capabilities по существующим `PiPageHeader`, `PiEntityList`, form-dialog и shared services.
2. Реализовать user lifecycle: create/invite, activate/deactivate, reset/change password, assign role. Не отображать passwordHash, refresh state и другие внутренние поля.
3. Реализовать role lifecycle: list/create/edit custom roles; system roles read-only по invariant; permission selection только из canonical catalog.
4. Защитить опасные операции: нельзя удалить последнего admin, отключить самого себя без recovery path, изменить system role так, чтобы исчез admin access.
5. Добавить audit events для изменения users/roles/permissions и UI для просмотра только согласно audit permission.
6. Подключить admin routes и navigation через TZ-256 capability metadata; не зашивать проверки только в шаблоны.

## Файлы для изменения

- Новые `frontend/src/app/pages/admin/**` и соответствующие backend files.
- Existing shared DSL/UI only через documented extension points.
- Component/integration tests и docs.

**Не изменять:** бизнес-страницы без необходимости; не создавать второй UI kit или отдельные ad-hoc form primitives.

## Критерии приёмки

1. User/manager без admin permission не видит admin section и получает 403 при прямом API/URL доступе.
2. Admin может создать сотрудника и назначить только canonical role/permissions; passwordHash и tokens никогда не возвращаются.
3. System roles нельзя удалить; последний admin не может быть удалён/деактивирован/разжалован.
4. User/role/permission mutations попадают в audit log с actor, action, target и timestamp.
5. Все admin pages используют существующие Pi/DSL primitives и проходят component/integration tests.
6. Backend tests/build/lint и frontend tests/typecheck/lint/build проходят.

## Ограничения

Не добавлять multi-tenancy, SSO, LDAP, workflow approval, сложные policy editors или массовое управление пользователями до появления реальной потребности.
