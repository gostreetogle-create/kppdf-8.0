# TZ-238 — User.organizationId + JWT propagation (Multi-Tenant foundation)

**Дата создания:** 2026-07-31 (audit от multi-tenant readiness review)
**Автор:** senior-architect audit (TZ-238..241 batch)
**Приоритет:** CRITICAL (dependency для TZ-239, TZ-240, TZ-241; без него enforced isolation невозможен)
**Связь:** FOUNDATION для `TZ-239 (OrgContextGuard)`, `TZ-240 (Reference Data Scoping)`, `TZ-241 (Counterparty + isActive check)`
**Скоуп:** Backend schema + JWT payload + Auth flow + one frontend AuthUser field. **Никаких** changes в business services (это в TZ-239..241).

---

## 0. TL;DR для PO

**Цель:** Привязать каждого User к одной (или нескольким в будущем) Organization — чтобы архитектурно стало возможным multi-tenant data isolation, которое сейчас ENFORCED-НЕТ в services (по audit от 2026-07-31).

**Что НЕ делаем:** никаких изменений в data-access services. Этот TZ — чистый foundation: schema + JWT + один propagation. Business-services changes придут в TZ-239 (org-scope interceptor) и TZ-240 (per-collection scoping).

**Объём внедрения:**
- ~80 LOC backend (User.schema + 1 migration + JWT payload + Auth flow)
- ~15 LOC frontend (AuthUser interface + service)
- 1 MongoDB migration script
- 3 backend unit-tests + 2 frontend unit-tests

---

## 1. Контекст (проблема)

### 1.1 Фактическое состояние (audit verification)

- `User.schema` (TZ-04) НЕ содержит `organizationId` field
- Login возвращает `user: AuthUser` без `organizationId`.
- 10+ коллекций уже имеют `organizationId` (contract, document-template, generated-document, order, quotation, reconciliation-act, order-closing, cart-session, organization-contact, tender) — но service-методы НЕ фильтруют по нему (см. `contract.service.ts`, `document-template.service.ts`).
- `req.user` после JWT validation содержит `{id, username, role, permissions, version}` — нет `organizationId`.

### 1.2 Последствия

- Manager из Орг-A через direct-URL `GET /api/contracts/<id-Org-B>` получит 200 + данные Орг-B (текущее поведение).
- Counterparty Орг-A видны Орг-B (TZ-241 fix).
- Multi-tenant будущая фича невозможно внедрить без миграции всех 19 feature-модулей одновременно с риском сломать prod-данные.

### 1.3 Почему MUST-DO NOW

- Каждый TZ который multi-tenant (TZ-239..241) требует organizationId в User как prerequisite.
- Без этого TZ multi-tenant retrofit через год будет кросс-энтёрпрайз болью с data-migration всех существующих users + потенциальной потерей данных.

## 2. Архитектурное решение

### 2.1 User.schema + Prop organizationId

```typescript
// backend/src/modules/user/user.schema.ts
@Prop({ required: false, sparse: true, index: true })
organizationId?: Types.ObjectId; // ref: 'organizations'
```

**Важно:** `required: false` + `sparse: true` — system users (bootstrap admin) могут не иметь orgId. ValidationPipe при application-level enforce через user creation path.

### 2.2 JWT payload (extending TZ-04)

```typescript
// JWT payload: добавить orgId
{ sub, orgId, username, role, version }
// - sub: user._id (existing)
// - orgId: user.organizationId.toString() НЕ null/undefined (REQUIRED for non-system)
// - username: existing
// - role: existing
// - version: refreshTokenVersion (existing)
```

### 2.3 AuthenticatedUser interface (backend decorator)

```typescript
// backend/src/common/decorators/current-user.decorator.ts
export interface AuthenticatedUser {
  id: string;
  username: string;
  role: string;
  permissions?: string[];
  version?: number;
  /** TZ-238: required for non-system users; nullable для bootstrap admin.*/
  organizationId?: string | null;
}
```

### 2.4 AuthFlow propagation

- `auth.service.ts` `login()` → reads user.organizationId → JWT sign payload includes orgId
- `jwt.strategy.ts` `validate(payload)` → возвращает `{id, username, role, permissions, version, organizationId: payload.orgId}`
- `UserContextInterceptor` (TZ-04) → AsyncLocalStorage context уже передаёт userId; добавить `organizationId` в context для optional use в TZ-239 pre-query plugin

### 2.5 Frontend AuthUser

```typescript
// frontend/src/app/core/auth.service.ts
export interface AuthUser {
  id: string;
  username: string;
  email: string;
  displayName: string;
  role: string;
  permissions: string[];
  /** TZ-238: required for non-system users; null для bootstrap admin. */
  organizationId?: string | null;
}
```

- AuthService.user() signal содержит AuthUser с organizationId после /auth/me response
- AuthService.login() → save to localStorage (НЕ persist orgId sensitive — ставим из /auth/me fetch на bootstrap)

### 2.6 Admin seed update

`backend/src/common/seed/admin.seed.ts`: bootstrap admin (TZ-04) НЕ получает organizationId (system user) → `organizationId === null` в AuthUser. Admin может потом attach'нуть себя к org через отдельный admin endpoint (TZ-241+ follow-up).

`backend/src/database/migrations/2026-07-31-TZ-238-user-organizationId.ts`:

## 5. Критерии приёмки

1. Свежий User без organizationId → POST /users возвращает 400 (ValidationPipe).
2. User с organizationId в БД → POST /auth/login → JWT payload содержит `orgId` (можно проверить через `jwt.io` decode).
3. GET /auth/me response содержит `organizationId` field для non-system users.
4. JWT decode показывает `orgId` claim; для system admin → null.
5. «MIgration script» re-runnable: 2x прогон scripts без ошибок.
6. Frontend: после login, `authService.user()?.organizationId` populated.
7. `pnpm tsc --noEmit` exit 0 в backend и frontend.
8. Существующие backend e2e tests (TZ-91 smoke-style) — passes (могут потребовать `me.organizationId` в assertions → small fixture update).

## 9. Risks & open questions

- **R1:** organizationId в JWT payload leaks через audit logs / introspection — mitigate: orgId is public-ish (для system admin) и для multi-tenant не критично leak внутри Orga. Если хочется большей privacy — OrgIdClaim нужно хешировать. **Decision:** keep raw — простота > privacy для MVP.
- **R2:** Migration script assumes «first organization» as default. Если в проекте нет ни одной Organization — script noops + log. Если есть только system org → скрипт не имеет смысла. Mitigate: добавить README pre-condition check.
- **R3:** Frontend localStorage cleared on bootstrap? Нет — мы только добавляем поле. Существующие user tokens в localStorage будут valid до истечения. На bootstrap /auth/me обновит organizationId.
- **Open question:** нужны ли multiple organizations per user (multi-org client switcher)? — OUT of scope для TZ-238. Возможный TZ-238-extension follow-up.
