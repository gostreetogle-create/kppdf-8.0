# TZ-248 — Production secrets и credential hygiene

**Статус:** READY / будущая задача. Этот файл только ставит работу; в рамках его создания код и инфраструктура не изменяются.

**РОЛЬ АГЕНТА:** Backend Security Engineer + Deployment Maintainer

**ЗАВИСИМОСТИ:** Нет. Выполнить первым среди security-TZ.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/config/defaults.ts`; `backend/src/config/env.validation.ts`; `backend/src/config/configuration.ts`; `backend/src/common/seed/admin.seed.ts`; `backend/src/common/seed/admin-password-drift-detector.ts`; `docker-compose.prod.yml`; `deploy/synology/DEPLOY.md`; `deploy/synology/RUNBOOK.md`; `deploy/synology/CREDENTIALS.example.md`; `.gitignore`

## Цель

Исключить возможность войти в production по известным из репозитория значениям и убрать реальные-looking ключи/пароли из документации. Секреты, найденные в истории или документах, считать скомпрометированными и ротировать, а не просто маскировать.

## Что сделать

1. Провести inventory всех JWT-, database-, admin- и deployment-секретов в tracked-файлах, документации, compose-файлах и примерах. Не копировать значения секретов в отчёт или новые файлы.
2. Удалить из versioned-документации реальные значения секретов, SSH-паролей и production-паролей; оставить только placeholders и безопасные команды генерации.
3. Проверить git history на ранее закоммиченные секреты. Если секрет когда-либо был доступен в репозитории, зафиксировать обязательную ротацию соответствующего значения на deployment host; очистку истории выполнять только отдельным согласованным operational-планом.
4. В production сделать JWT/JWT-refresh/Mongo/admin credentials обязательными и непредсказуемыми. Известный demo-default не должен запускать приложение в production; безопасный вариант — fail fast, а не только warning.
5. Сохранить development/test defaults только в явном non-production пути и покрыть guard тестом.

## Файлы для изменения

- Перечисленные в CONFLICT KEYS — только если аудит подтвердит необходимость.
- `backend/test/**` — тесты production guard.

**Не изменять:** текущий frontend production-срез справочников, `tasks/*` кроме этого файла, `_templates/*`, секретные `.env`-файлы.

## Критерии приёмки

1. В текущем tracked-дереве нет реальных JWT/database/admin/SSH секретов; placeholders не являются рабочими credentials.
2. Для каждого секрета, найденного в git history или deployment-документации, зафиксирована ротация на deployment host; очистка history не маскируется как выполненная этой задачей.
3. Production bootstrap завершается ошибкой при отсутствующем, слишком слабом или известном default-секрете.
4. Есть автоматический тест, подтверждающий отказ production-конфигурации с demo admin password и слабым JWT secret.
5. Deployment-документация описывает генерацию и ротацию значений, но не содержит самих секретов.
6. `.env` и deployment credential files остаются ignored и не попадают в diff.
7. Backend tests, build и lint проходят.

## Ограничения

Не добавлять Vault, SIEM, WAF или новую систему управления секретами. Для команды до 10 человек достаточно env secrets на deployment host + ротация + fail-fast guard.
