Проверено: `database.module.ts:20` — `autoIndex: !isProd`, то есть **на стенде Mongoose
не создаёт новые и не убирает исчезнувшие индексы**; они остаются с прежних версий схемы.
Канонические индексы сейчас: `number` unique (`quotation.schema.ts:65–66`) и
`{ masterId: 1, organizationId: 1 }` unique sparse (`:181–184`); всё остальное — не unique.
Есть готовый образец guarded-миграции: `backend/src/database/migrations/2026-08-08-TZ-PARTY-301-party-hygiene.ts`
(`listIndexes` → `dropIndex` только по факту наличия) + spec к ней.
Симптом с самопроверки WAVE-KP-USABLE (2026-08-09): после удаления КП создание нового
черновика падало по дубликату ключа; исполнитель починил **только локальную тестовую базу**,
в код и документы это не попало — на стенде мина осталась.

ЧТО ДЕЛАТЬ
═══════════════════════════════════════════════════════════════

1. **Снять факт, не гадать**
   - Написать миграцию, которая читает `db.collection('quotations').listIndexes()` и
     логирует найденное (имя + ключи + unique/sparse) одной строкой на индекс.
   - Каноническим считать только: `_id_`, `number_1` (unique),
     `masterId_1_organizationId_1` (unique + sparse) и не-unique вспомогательные.

2. **Удалить лишние уникальные индексы, идемпотентно**
   - Любой **unique** индекс на `quotations`, которого нет в каноническом наборе, удалить
     через `dropIndex`, обёрнутый в try/catch (как PARTY-301): нет индекса — просто пропуск.
   - Не-unique индексы не трогать: они не блокируют запись.
   - Миграция должна безопасно запускаться повторно и на пустой базе.

3. **Мягкое удаление не должно мешать созданию**
   - Проверить, что soft-delete (`isActive` / `deletedAt`) не конфликтует с оставшимися
     уникальными ключами: удалённое КП сохраняет `number`, поэтому новый документ обязан
     получать новый номер из счётчика, а не переиспользовать старый.
   - Если найдётся уникальный индекс, который делает удалённые записи «занимающими место»,
     — сделать его `partial` по `isActive: true` вместо unique-по-всем.

4. **Тест, повторяющий боль PO**
   - e2e: создать КП → мягко удалить → создать ещё два КП подряд → все три успешны,
     номера различны, список показывает только живые.
   - unit к миграции: при наличии лишнего unique индекса `dropIndex` вызывается,
     при его отсутствии — нет (образец: `2026-08-08-TZ-PARTY-301-party-hygiene.spec.ts`).

5. **Заметка для стенда**
   - В `docs/pages/proposals-create.page.md` одна строка: индексы `quotations` приводит в
     порядок миграция, потому что `autoIndex` в проде выключен.

ИЗМЕНЯТЬ: новую миграцию + spec, подключение миграции, e2e квотаций, одну строку page-doc.
НЕ ИЗМЕНЯТЬ: `quotation.schema.ts` (канон индексов уже верный), логику soft-delete,

known_limitation: чистка касается только `quotations`; общий аудит устаревших индексов по
всем коллекциям — отдельная задача.
