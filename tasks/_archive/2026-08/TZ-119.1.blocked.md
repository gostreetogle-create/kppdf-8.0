## Failure reason (BLOCKED)

**Three hard constraints from the user (autonomous continuation message) cannot be satisfied simultaneously with the existing codebase:**

1. **Mass adoption requires service-signature refactor** — applying existing `IsObjectIdPipe` (return type `Types.ObjectId`) to 30+ controllers would force 60+ LOC change across services to change `findById(id: string)` → `findById(id: Types.ObjectId)`. The user instruction 'Не делай массовый refactor service signatures без отдельного обоснования' forbids this without a separately justified TZ (e.g. TZ-119.2 with one-call-site-at-a-time review).
2. **Partial adoption creates false safety** — adopting `IsObjectIdPipe` in only a few controllers would `return data 400` on invalid input for those routes, while 27+ remaining controllers continue to crash on invalid input at the Mongoose layer with `BSONError: input must be a 24 character hex string`. The user instruction 'не делай частичный adoption, который создаёт ложное чувство защиты' explicitly forbids this pattern.
3. **Third pipe-class disallowed** — the alternative of a validate-only pipe (returns `string`) was rejected by code-reviewer in the previous continuation (see `progress.md` §REVERTED) because it does not change the caller's responsibility: service code still has to do `new Types.ObjectId(id)` and is still vulnerable if a controller is bypassed or accepts a string at a non-`:id` boundary. The user instruction 'Не создавай третий pipe-класс' forbids this path forward.

These constraints are mutually exclusive without further breaking scope.
