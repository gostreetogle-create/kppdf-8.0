## ⚠️ Ключевой контекст: две параллельные модели геометрии (корень пунктов 259.4 и 259.6)

В конструкторе сосуществуют **два независимых механизма геометрии блока**:

| Механизм | Где хранится | Кто рендерит | Ресайз мышью |
|---|---|---|---|
| **Flow** (легаси) | `settings.width` / `settings.marginLeft` | canonical-ветка НЕ рендерит; flow-ветка рендерит | `.block-renderer__resize-side--left/right` (есть, но только в flow-ветке) |
| **Positioned** (канонический) | `layout.x/y/width/height` (в % страницы) | canonical-ветка (`isPositioned` = `layout !== undefined`) | **НЕТ ХЭНДЛОВ ВООБЩЕ** |

Каждый **новый** блок получает `layout` через `defaultBlockLayout()` (`builder.page.ts` → `buildBlockFromPayload` → `template-block-layout.ts:123`) и рендерится в canonical-ветке `block-renderer.component.ts` — где **нет ни одного** resize-handle. При этом поля инспектора «Ширина / Отступ слева / Отступ справа» (`builder-inspector.component.ts:601,626`) пишут в `settings.width/marginLeft` — то есть в flow-модель, которая на positioned-блок не влияет. Отсюда «свойства есть, но не работают».

**Стратегия (предлагается принять до 259.4):** для positioned-блоков единый источник истины — `layout`; поля инспектора и ресайз-мышью должны работать с `layout`, а `settings.width/marginLeft` остаются только для flow-легаси.

## 259.1 — Диалог «Настройка шаблона» не закрывается после «Создать» (баг)

**Симптом (пользователь):** после нажатия «Создать» в диалоге настройки шаблона окно диалога остаётся на экране; за ним открывается редактор документа. Требуется лишний клик в любом месте или по крестику.

**Файлы:**
- `builder.page.ts` — `onCreateTemplate()` (открывает диалог, `onDialogCloseOnce` → создание → `router.navigate`)
- `template-setup-dialog.component.ts` — `onConfirm()` → `this.ref.close({pageSize, orientation})`
- `pi-dialog.service.ts` — `close()` → `closedSig.set` + `isClosed.set(true)` + `overlayRef.dispose()` (синхронно)
- `on-dialog-close-once.ts` — подписка на `ref.closed` через `toObservable`

**Гипотезы (нужна репродукция и проверка DOM):**
1. `queueMicrotask → requestAnimationFrame → overlayRef.updatePosition()` в `pi-dialog.service.ts` — RAF может сработать ПОСЛЕ `dispose()` и заново дёрнуть удалённый overlay (или заказдить ошибку, прервав закрытие).
2. В `onCreateTemplate()` не передаётся `parentDestroyRef` — если навигация разрушает страницу раньше, чем диалог успевает закрыться, overlay-контейнер CDK может остаться в DOM.
3. Возможно, остаётся **backdrop** (`pi-overlay-backdrop`), а не сам диалог — проверить `document.querySelectorAll('.cdk-overlay-container, .pi-overlay-backdrop')` после «Создать».

**Acceptance:**
- Клик «Создать» закрывает диалог мгновенно и сразу переходит в редактор.
- В DOM после закрытия не остаётся ни одного `.cdk-overlay-container` / `.pi-overlay-backdrop` с этим диалогом.
- Повторный клик/крестик не требуется.

## 259.2 — Кнопки «Редактор / Превью» не работают — реализовать или убрать

**Симптом (пользователь):** непонятно, зачем две кнопки; «они сейчас не работают».

**Корень (верифицировано):** `viewMode` сигнал есть в `builder.page.ts` (TZ-211) и кнопки в тулбаре есть, но **`viewMode` никуда не передаётся** — у `BuilderCanvasComponent` (`builder-canvas.component.ts`) нет input `viewMode`, поведение холста не меняется вообще.

**Решение (рекомендация — реализовать, не удалять):** режим превью имеет глобальный смысл для конструктора документов — увидеть документ «как в печати», без редакторского мусора. Превью должно:
- скрывать grid-слой (`.canvas-builder__grid-layer`) и guides;
- скрывать весь selection-chrome (resize-хэндлы, кнопку удаления, checkbox, шапку блока);
- запрещать drag/перетаскивание (positioned / flow / overlay);
- вернуться к редактированию — мгновенно.

**Acceptance:** переключение в «Превью» скрывает сетку и все хэндлы, блоки не перетаскиваются; «Редактор» восстанавливает всё. Если после реализации покажется лишним — удалить обе кнопки отдельным коммитом.

## 259.4 — Ресайз блоков мышью + двойной клик (текст / таблица / фото / отступ) — ядро фидбека

**Симптом (пользователь):** раньше ширина и отступы менялись мышью, сейчас «ничего не происходит»; в свойствах поля есть, но не работают; двойной клик не работает; хочется: выделил → потянул за край/угол → изменил размер, либо двойной клик → ввод размеров.

**Корень (верифицировано, см. контекст выше):**
- canonical-ветка (`block-renderer.component.ts`, `@if (state.isPositioned())`) **не имеет resize-хэндлов вообще**;
- resize-хэндлы (`onResizeStart`, `.block-renderer__resize-side--left/right`) существуют только в **flow-ветке**; corner-resize (`onCornerResizeStart`) — только в **overlay-ветке** (изображения);
- инспектор пишет в `settings.width/marginLeft` (flow-модель) → на positioned-блок не влияет;
- фото вставляется с `layout` (`onPhotoFileSelected` → `defaultBlockLayout`) → рендерится в positioned-ветке → угловой ресайз из overlay-ветки недоступен.

**Объём работ:**
1. Добавить в canonical-ветку resize-хэндлы: **края** (left/right/top/bottom) и **углы** (corner) → drag меняет `layout.x/y/width/height` (клампы: min-width/height, границы страницы, `boundaryPadding`).
2. Переиспользовать/расширить чистую математику: `computeSideResize` / `computeCornerResize` из `block-renderer-state.service.ts` (сейчас они оперируют flow/overlay-моделью) — добавить вариант для layout-координат.
3. **Двойной клик** по блоку → мини-форма ввода ширины/высоты (px) → применяется к `layout`.
4. Поля инспектора «Ширина / Отступ» для positioned-блока перевести на `layout` (или отображать layout-значения и писать в layout).
5. Персист: через существующий `onLayoutChanges` → `updateLayouts` (batch, уже есть в `builder.page.ts`).

**Acceptance:** любой блок (текст, таблица, фото, отступ) можно ресайзить мышью за край/угол и через двойной клик; инспекторные поля ширины/отступов работают на positioned-блоках; изменения сохраняются.

## 259.5 — Магнитная цепкость / отталкивание блоков (таблица ↔ текст)

**Симптом (пользователь):** подвожу таблицу к текстовым блокам — она налегает, нет «магнитной цепкости», блоки не отталкиваются и не цепляются; выровнять невозможно.

**Корень (верифицировано):**
- `snapToBlockEdges` в `block-renderer-state.service.ts` **есть**, но вызывается только из `computeOverlayDrag` — т.е. работает **только для overlay-изображений**;
- positioned-drag (`onPositionedDragStart` в `block-renderer.component.ts`) использует только `clampLayoutDelta` — **никакого снапа к соседям и никакой коллизии**;
- alignment-guides (`computeGuidesForCurrentDrag` в `builder-canvas.component.ts`) фильтруют только `isOverlayBlock` — для positioned-блоков гайдов нет.

**Объём работ:**
1. Распространить магнитный снап на positioned-блоки: при drag за края/центры соседних блоков — притягивание (расширить `snapToBlockEdges` для layout-координат или новый чистый helper в `snap-engine.ts`).
2. Рисовать alignment-guides при перетаскивании positioned-блока (расширить `computeGuidesForCurrentDrag` за пределы overlay; `snap-engine.ts` уже умеет collapse + детерминированную сортировку).
3. Опционально — **отталкивание/коллизия**: при пересечении прямоугольников блоков выдавливать перетаскиваемый блок до минимального зазора (чистая функция в snap-engine, переиспользование `Rect`).
4. Связано: мультивыделение-drag с магнитным снапом — отложено в TZ-237.E (см. TODO-маркер в `builder-canvas.component.ts`).

**Acceptance:** перетаскивая таблицу рядом с текстовым блоком, видно притягивание к краям/центрам + гайды; блоки не налегают (если включена коллизия); снап работает в обе стороны (x и y).
