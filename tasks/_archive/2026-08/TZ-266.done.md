═══════════════════════════════════════════════════════════════
ИСХОДНОЕ СОСТОЯНИЕ
═══════════════════════════════════════════════════════════════

1. `GeneratedDocumentController` помечен `@RequireOrgScope()` и `@UseInterceptors(OrgScopeGuardInterceptor)`, но этот механизм фильтрует уже сформированный ответ после выполнения handler. Для методов с `@Res()` handler возвращает `void`, поэтому interceptor не видит отправленный документ.

2. `DELETE /api/generated-documents/:id` вызывает `GeneratedDocumentService.remove(id)`. Сервис загружает документ только по ID и выставляет `isActive = false`; до побочного изменения не проверяется `organizationId` аутентифицированного пользователя. `GeneratedDocument` не содержит `createdBy`, поэтому подтверждённый риск здесь — обход границы организации, а не отдельная проверка владельца. Возвращаемое значение `void` не содержит документ, поэтому post-response interceptor не может остановить удаление чужого документа.

3. `GET /api/generated-documents/:id/html` вызывает `service.findById(id)` и напрямую отправляет `doc.html` через `@Res()`. Поскольку handler возвращает `Promise<void>`, post-response interceptor не может отфильтровать чужой документ; cross-org read может раскрыть HTML.

4. `POST /api/generated-documents/from-template/:templateId` также выполняет генерацию и запись до того, как interceptor сможет проверить ответ. Нельзя считать response-фильтрацию защитой от cross-organization side effects.

5. Доказательство: `backend/src/modules/generated-document/generated-document.controller.ts` — handlers `@Get(':id/html')`, `@Post('from-template/:templateId')`, `@Delete(':id')`; `backend/src/modules/generated-document/generated-document.service.ts` — `findById()` без org filter и `remove()` без scope check; `backend/src/common/interceptors/org-scope.interceptor.ts` — фильтрация после `next.handle()`. Номера строк намеренно не фиксируются: исполнитель должен сверить актуальные якоря перед изменением.

6. Риск: обычный пользователь с `organizationId` одной организации, имеющий или угадавший ID документа другой организации, может прочитать HTML и выполнить мутацию чужого tenant-документа. Это P1: данные изменяются неправильно и security boundary обходится. Административный system/bootstrap bypass должен остаться отдельным, явно подтверждённым контрактом.

═══════════════════════════════════════════════════════════════
ЧТО ДЕЛАТЬ
═══════════════════════════════════════════════════════════════

ШАГ 1: Зафиксировать авторизационный контракт мутаций

Определить один явный server-side путь проверки scope до любого write:
- пользователь с `organizationId` может генерировать/удалять только документы и шаблоны своей организации;
- `system/bootstrap` user без `organizationId` сохраняет действующий административный bypass только если это подтверждено текущим RBAC-контрактом;
- cross-organization запрос завершается безопасным `404` (не раскрывать существование ресурса) либо другим уже принятым в проекте кодом, но одинаково для generate и delete;
- `dto.organizationId` не принимается на доверии как способ назначить результат в чужую организацию: организация выводится/проверяется относительно authenticated context и template.

Не полагаться на post-response `OrgScopeGuardInterceptor` как на единственную защиту side effect.

ШАГ 2: Применить проверку до мутации

Изменить controller/service contract так, чтобы authenticated user context и организация передавались в проверку до:
- отправки HTML в `GET /:id/html`;
- создания generated document в `generate`;
- `isActive = false` в `remove`.

Проверить также template source для generate: нельзя сгенерировать документ из чужого template только потому, что ID известен. Переиспользовать существующий org-scope/RBAC contract и решения TZ-239/TZ-241, не создавать вторую несовместимую модель авторизации или новую `createdBy`-ownership модель для GeneratedDocument.

ШАГ 3: Добавить regression-тесты

Добавить unit/integration tests для:
- same-org generate и delete — PASS;
- cross-org HTML read — отказ до отправки `doc.html`;
- cross-org generate — отказ до `model.create`;
- cross-org delete — отказ до `save`;
- system/admin bypass — поведение соответствует документированному контракту;
- неизвестный/невалидный ID — безопасный 404.
