## 1. Цель (recap)

Создать два custom ESLint правила enforcing code hygiene в frontend:

1. **`kppdf-frontend-architecture/no-raw-http-in-components`** — запрет `HttpClient`
   import + `this.http.<verb>(...)` calls в `*.page.ts` + `*.component.ts`.
   HTTP в components только через `defineEntity()` services (TZ-232.B) или `httpResource()` signals.
2. **`kppdf-frontend-architecture/no-implements-oninit-in-pages`** — запрет
   `implements OnInit/OnDestroy/OnChanges/AfterViewInit/...` lifecycle interfaces в `*.page.ts`.

---

## 2. Архитектурное решение: CJS not TS

Original plan был CommonJS+.ts sources с `@typescript-eslint/utils` import. **Node CommonJS
`require()` в `eslint.config.js` не может runtime-load `.ts` файлы** (ts-node не в deps, его
добавление потянуло бы optional dev-dep). Принятое решение: rule sources — **`.cjs`
(plain JS CommonJS)**.

Trade-off: теряем TS typecheck coverage на rule logic. Компенсация:
- `Linter` spec files ≥ 5 test cases × 2 rules = 10 PASS (positive + negative).
- `eslint.config.js` plugin block декларирует `meta.name` + `meta.version` — нет
  "plugin without name" warning.
- `pnpm lint` показал **20 NEW warnings** в реальных файлах
  (`users-admin.page.ts`, `builder.page.ts`, `templates.page.ts`, и т.д.) — правила
  правильно интегрируются и работают на TypeScript source code.
