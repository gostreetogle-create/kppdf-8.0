# TZ-OPS-318: бэкап Mongo + uploads — сам по расписанию, сам чистит старое

> Решение PO (2026-08-22, эта сессия): бэкапы нужны, но без захламления диска —
> сами сохраняются по расписанию и сами удаляют старые копии через N дней.
> Снимки самой VM у PO уже есть отдельно (защита от смерти диска целиком) — эта
> TZ про **прикладной** бэкап (можно откатить только базу/файлы, не всю машину).

РОЛЬ АГЕНТА: ops / backend scripts engineer

ЗАВИСИМОСТИ: Нет

LAYER: repo-scripts + прод VM (см. СТОП — установка cron на сам сервер требует SSH-доступа, который есть не у каждого executor)

CONFLICT KEYS: `deploy/synology/backup.sh` ; `deploy/synology/README.md` ; `deploy/synology/RUNBOOK.md`

Проверено (эта сессия, 2026-08-22):
- `deploy/synology/backup.sh` уже существует и умеет: `mongodump` в `${DATA_DIR}/backups/mongo-{дата}`
  + копию `${DATA_DIR}/uploads` в `${DATA_DIR}/backups/uploads-{дата}`. Но: запускается
  **только вручную** (`RUNBOOK.md`: `ssh … && sudo bash backup.sh`), и **не удаляет** старые копии —
  при регулярном запуске место на диске будет расти бесконечно.
- `docker-compose.prod.yml`: `${KPPDF_DATA_DIR}/mongodb` и `${KPPDF_DATA_DIR}/uploads` — это
  volume'ы **на хосте**, вне контейнеров. Обычный передеплой (`docker compose up -d --build`)
  их не трогает — база и загруженные файлы **уже переживают** обычный передеплой без TZ.
- Единственное, что реально удаляет данные — `deploy.py wipe_remote()`
  (`rm -rf $data_dir/mongodb/* $data_dir/uploads/*`), и это **только** по явному флагу
  `--wipe` / `WIPE=true`, уже задокументировано как «backup.sh сначала, потом явное
  разрешение PO» (`RUNBOOK.md`, `docs/ops/DANGEROUS-OPS.md`). Эта часть уже безопасна
  по процессу — TZ её не меняет, только фиксирует, что она уже так работает.

## ЧТО ДЕЛАТЬ

### ШАГ 1: Ротация в `backup.sh`

Добавить в конец `backup.sh` (после успешного создания новой копии) удаление
копий старше `BACKUP_RETENTION_DAYS` (env, дефолт 14 дней — PO может поменять
в `config.env`):

```bash
RETENTION_DAYS="${BACKUP_RETENTION_DAYS:-14}"
find "$BACKUP_ROOT" -maxdepth 1 -type d -name "mongo-*" -mtime "+${RETENTION_DAYS}" -exec rm -rf {} \;
find "$BACKUP_ROOT" -maxdepth 1 -type d -name "uploads-*" -mtime "+${RETENTION_DAYS}" -exec rm -rf {} \;
```

Логировать, что именно удалено (имя папки), не удалять молча.

### ШАГ 2: Расписание (cron)

Добавить в `deploy/synology/RUNBOOK.md` / `README.md` готовую строку для
установки (не выполнять самому — установка на сам прод-сервер требует SSH,
см. СТОП):

```text
# crontab -e (на самом VM, от root или пользователя с доступом к docker):
0 3 * * * cd /opt/kppdf-8.0 && bash deploy/synology/backup.sh >> /var/log/kppdf-backup.log 2>&1
```

Каждую ночь в 03:00, лог — отдельным файлом, не в консоль.

### ШАГ 3: Явно задокументировать «обычный деплой не трогает данные»

В `README.md` (deploy/synology) — одна секция: «uploads и mongodb — это volume
на хосте, обычный деплой их не удаляет; удаляет только явный `--wipe`». Это
снимает беспокойство «новый деплой всё перекатит с нуля» — по факту он этого
не делает уже сейчас, просто нигде явно не написано.

### ШАГ 4 (важно, отметить, не обязательно чинить в этой TZ)

Бэкап в `${DATA_DIR}/backups` лежит **на том же диске**, что и сама база — если
диск сервера умрёт целиком, бэкап умрёт вместе с ним. Снимки VM (у PO уже есть)
частично это закрывают, но снимки обычно нечастые/ручные. В отчёте — одна
строка-рекомендация: желательно, чтобы `backups/` время от времени копировался
куда-то ещё (второй диск / другой сервер / облако) — не делать это в рамках
этой TZ, просто зафиксировать как открытый вопрос для PO.

## СТОП

- Установка `crontab` на прод-VM — это изменение живого сервера, не файла в
  репозитории. Делать **только** если у executor есть SSH и PO явно сказал
  «настрой на сервере» в чате. Если доступа/разрешения нет — подготовить
  строку в доке (ШАГ 2) и написать PO, что установка ждёт SSH/разрешения.

## КРИТЕРИИ ПРИЁМКИ

1. `backup.sh` после запуска не оставляет копии старше `BACKUP_RETENTION_DAYS`.
2. Удаление залогировано (видно, что именно удалено).
3. `RUNBOOK.md`/`README.md` содержат готовую cron-строку + пояснение про volume.
4. `bash -n deploy/synology/backup.sh` (синтаксис-чек) — PASS.
5. Ротация НЕ применяется к бэкапам моложе retention (проверить вручную:
   создать тестовую папку с датой в имени старше и младше порога — младше должна выжить).

known_limitation: реальная установка cron на прод-VM — вне scope без SSH/разрешения PO
(см. СТОП); офсайт-копия бэкапов (ШАГ 4) — отдельное решение PO, не эта TZ.
