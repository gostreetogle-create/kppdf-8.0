# TZ-OPS-319: проверка кода перед отправкой на GitHub (без облака)

> Решение PO (2026-08-22, эта сессия, делегировано архитектору): облачная
> проверка (GitHub Actions) НЕ включаем — есть явное решение PO от 2026-08-21
> «GitHub = только хранилище, без Actions/dependabot» (`docs/agent-checklists/_NOW.md`).
> Вместо неё — усилить то, что уже есть локально: сейчас проверка стоит только
> на `pre-commit` (lint-staged + supply-gate), перед самой отправкой на GitHub
> (`git push`) ничего не гоняется. Эта TZ закрывает именно этот пробел, не
> нарушая решение PO — ничего никуда в облако не уходит.

РОЛЬ АГЕНТА: Backend/Frontend tooling engineer

ЗАВИСИМОСТИ: Нет

LAYER: repo config (husky), безопасно, не Layer 3 в обычном смысле

CONFLICT KEYS: `.husky/pre-push` (новый файл) ; `package.json` (root, только секция scripts, если нужен новый script)

Проверено (эта сессия):
- `.husky/pre-commit` существует: `lint-staged` + `scripts/smoke/supply-gate.mjs`.
  Комментарий в файле прямо говорит: полная проверка (tsc + ng build + jest)
  **намеренно не в pre-commit** — «слишком медленно» для каждого коммита.
- `.husky/pre-push` — **не существует**. Между «закоммитил» и «улетело на
  GitHub, стало общей правдой для всех агентов» проверок нет вообще.

---

## ЧТО ДЕЛАТЬ

### ШАГ 1: `.husky/pre-push`

Новый хук, запускается редко (перед push, не перед каждым commit) — можно
себе позволить быстрый typecheck на оба контура:

```bash
#!/usr/bin/env sh
. "$(dirname "$0")/_/husky.sh"

echo "[pre-push] typecheck backend + frontend…"
(cd backend && pnpm exec tsc -p tsconfig.build.json --noEmit) || exit 1
(cd frontend && pnpm exec tsc -p tsconfig.app.json --noEmit) || exit 1
echo "[pre-push] OK"
```

Не добавлять сюда полный jest/ng build — это уже точно "слишком медленно" на
каждый push (ng build — минуты). Typecheck — секунды/десятки секунд, приемлемо.

### ШАГ 2: Явный обход для форс-мажора

Задокументировать (`docs/GIT-POLICY.md`, одна строка): если hook блокирует
экстренный push — `git push --no-verify`, но такой push обязателен к
самопроверке потом вручную (не молчаливая практика по умолчанию).

### ШАГ 3: Проверить, что хук реально срабатывает

`git push --dry-run` не запускает hooks — нужен реальный тестовый push в
черновую ветку или ручной вызов `.husky/pre-push` с фейковыми аргументами,
чтобы убедиться, что скрипт синтаксически верный и падает при реальной ошибке
типов (временно сломать тип в тестовом файле, проверить, что hook блокирует,
откатить).

---

## КРИТЕРИИ ПРИЁМКИ

1. `.husky/pre-push` существует, исполняемый (`chmod +x`), вызывает оба tsc.
2. Push с реальной ошибкой типов — блокируется (проверено вручную, см. ШАГ 3).
3. Push без ошибок — проходит, занимает разумное время (секунды-десятки секунд,
   не минуты).
4. `docs/GIT-POLICY.md` содержит строку про `--no-verify` для форс-мажора.
5. Никаких изменений в `.github/` — это явно вне scope и запрещено политикой PO.

known_limitation: это защита только для того, кто пушит с этой машины с
установленным husky (`pnpm install` ставит хуки через `prepare` script —
проверить, что `package.json` это уже делает, иначе хук не установится у
executor'а после свежего `git clone`/`pnpm install`).
