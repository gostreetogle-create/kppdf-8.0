═══════════════════════════════════════════════════════════════
ИСХОДНОЕ СОСТОЯНИЕ
═══════════════════════════════════════════════════════════════

1. Страница `doc-constructor/templates` показывает loading и empty state, но не имеет отдельного `error` signal/ошибочного состояния для начальной загрузки. В `reload()` при `SilentResult.ok === false` код только выключает loading и не сообщает пользователю об ошибке; в результате 401/403/5xx может выглядеть как «Нет шаблонов».

2. В том же файле несколько операций обходят заявленный проектный HTTP-контракт `silent-*`: `this.http.get/post` внутри `createWithSettings()` (строки 289–292, 308–321), `this.http.post` для set-default (строка 373) и duplicate (строка 394). Эти вызовы используют вложенные `subscribe({ next, error })`; часть действий при ошибке лишь выключает флаг или молча оставляет старое состояние, без единого видимого error state.

3. Дополнительные silent-service операции также не показывают ошибку при отрицательном результате: `onToggleActive()` и `onDelete()` обрабатывают только `res.ok === true`, а при `res.ok === false` не дают toast/error state. Это делает отказ API неотличимым от успешного действия для пользователя.

4. Доказательство: `frontend/src/app/pages/doc-constructor/templates/templates.page.ts` строки 226–242 (`reload()`), 285–359 (`createWithSettings()`), 361–368 (`onToggleActive()`), 373–380 (`onSetDefault()`), 388–417 (`onDuplicate()`), 424–438 (`onDelete()`). Проектный контракт явно требует `silentGet/Post/Patch/Delete` и обработки `res.ok` в `docs/AI-AGENT-GUIDE.md` §2.4 и `docs/DEVELOPMENT-PATTERNS.md` §1.

5. Это P2: основной реестр может показывать ложное пустое состояние и не объяснять отказ сохранения/удаления, хотя typecheck и unit tests проходят. Браузерное подтверждение не выполнялось в этой сессии, поэтому acceptance обязан включать локальный ручной сценарий с тестовым API-ответом 401/403/500.

═══════════════════════════════════════════════════════════════
ЧТО ДЕЛАТЬ
═══════════════════════════════════════════════════════════════

ШАГ 1: Добавить явные состояния страницы

Добавить signal ошибки для initial list load и action-level error handling. Разделить состояния «загрузка», «ошибка загрузки», «пусто без поиска» и «пустой результат поиска». При ошибке загрузки показывать доступное сообщение и действие повторной загрузки; не выдавать ошибку за пустой список.

ШАГ 2: Привести HTTP-пути к проектному boundary

Для JSON-запросов реестра использовать существующие сервисы, где endpoint уже покрыт сервисом, и существующий `silent-*`/`silentWrap`-контракт для нестандартных вложенных endpoint-ов (`organizations`, `doc-types`, `set-default`, `duplicate`). Не добавлять второй HTTP-helper и не менять глобальный `silent-http.ts`. Все операции create, set-default, duplicate, toggle-active и delete должны явно обрабатывать `res.ok === false`, показывать понятный toast/error и корректно возвращать `creating`/`loading`/action flags в исходное состояние.

Сохранить существующие бизнес-правила: создание отсутствующих организации/типа документа, inactive-by-default template и переход в builder после успешного создания. Не считать операцию успешной при частично неудавшейся цепочке.

ШАГ 3: Зафиксировать регрессии тестами

Расширить существующий `templates.page.spec.ts` тестами на:
- начальный `SilentResult` с ошибкой: отображается error state, а не empty state;
- отрицательный результат update/delete/set-default: вызывается error toast и локальные данные не объявляются успешно изменёнными;
- ошибка любой стадии create flow сбрасывает creating и не вызывает navigate;
- успешные create/delete сценарии сохраняются.

КРИТЕРИИ ПРИЁМКИ

5. Успешный initial load, create, set-default, duplicate, toggle-active и delete сохраняют текущий пользовательский результат.
6. Добавлены unit-тесты на initial load error, action error и create-flow failure; frontend tests проходят.
7. `cd frontend && pnpm exec tsc -p tsconfig.app.json --noEmit` завершается с exit code 0.
8. `cd frontend && pnpm exec jest --no-coverage --runInBand` проходит, `git diff --check` чистый.
9. Ручной локальный сценарий: открыть `/doc-constructor/templates`, подменить ответ списка на 403 и проверить error state; повторить для неудачного delete/create без изменения production-базы; затем проверить успешный путь на тестовых данных.
