# TZ-252 — Auth token storage and refresh contract

**Дата создания:** 2026-07-31
**Автор:** senior-orchestrator
**Приоритет:** HIGH (XSS-safe token transport)
**ЗАВИСИМОСТИ:** TZ-249
**LAYER:** 4 (backend) + Layer 3 (frontend) — допустимо параллельно если соблюдены файловые boundaries
**CONFLICT KEYS:**
- backend/src/modules/auth/auth.controller.ts (+ cookie setting)
- backend/src/modules/auth/auth.service.ts (+ cookie issuance, + access cookie)
- backend/src/main.ts (own region: cookie-parser + CORS allowlist; sequential co-edit with TZ-253 banner/HTTPS/body-size/trust-proxy block — from user’s Wave 4 these should run serially to avoid two agents editing the same file in the same layer)
- frontend/src/app/core/auth.service.ts (in-memory token вместо localStorage)
- frontend/src/app/core/auth.interceptor.ts

---

## 0. Цель

- Один refresh transport: HttpOnly Secure SameSite cookie.
- Refresh token не хранится в JS-доступном слое вообще.
- Access token — in-memory signal только; НЕ localStorage.
- CORS — только явно whitelisted frontend origin.
- Concurrent 401 вызывает один refresh (single-flight уже реализован в TZ-91 + TZ-232.N).
- Не должно быть ДВУХ параллельных refresh-механизмов.

---

## 1. Контекст

Сейчас TZ-91 + TZ-232.N дают двойную refresh-логику (frontend SubmitGuard + interceptor + auth.service.refresh). Access token хранится в localStorage (`kppdf.access`, `kppdf.refresh`). Это НЕ XSS-safe для refresh token. Cookies — единственный безопасный канал для невозможности извлечения JS.

Сравнение фактического кода с описанием старого TZ-127 — TZ-127 не реализован полностью (cookie issuance не присутствует в authService, только header scheme).

---

## 2. Архитектурное решение

### ШАГ 1: Backend cookie issuance

`backend/src/modules/auth/auth.service.ts`:
- Lоgin response: `Set-Cookie: kppdf_refresh=<token>; HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=7d`
- HttpOnly — JS can't read.
- Path=/api/auth — только этот endpoint видит (browserautomatically attaches).
- SameSite=Strict — снижает CSRF (strict mode blocks cross-origin attaches).
- Secure — только HTTPS в prod (env-flag).
- Production: `Secure` обязателен (TZ-248 fail-fast если connection不好).

### ШАГ 2: Backend refresh flow

`backend/src/modules/auth/auth.controller.ts`:
- `POST /api/auth/refresh` — читает refresh из cookie (`req.cookies.kppdf_refresh`), НЕ из body.
- Verify token, signature, alg, version.
- Если валиден → новая access cookie + обновлённый refresh cookie (rotation optional).
- Если invalid → 401; clear cookies (Set-Cookie with expired).

### ШАГ 3: Backend logout

`POST /api/auth/logout`:
- bump `user.refreshTokenVersion` (existing TZ-91 pattern).
- Clear both cookies via `Set-Cookie: ...; Max-Age=0`.

### ШАГ 4: Frontend in-memory access

`frontend/src/app/core/auth.service.ts`:
- Access token: signal `accessToken` (in-memory) **ТОЛЬКО**.
- Удалить `localStorage.setItem(ACCESS_KEY, ...)` calls.
- Persisted target 0 bytes (NONE).
- При browser refresh — silent lose access → 401 → авто-refresh (cookie auto-send) → восстановление in-memory signal.

### ШАГ 5: Cookie-based silent refresh

`frontend/src/app/core/auth.interceptor.ts`:
- При 401 (НЕ на /auth/login|me|refresh|logout) →`authService.refresh()` → interceptor (credentials: 'include' plugin).
- `withCredentials: true` для всех requests → cookies автоматически отправляются.

### ШАГ 6: CORS allowlist

`backend/src/main.ts`:
- `CORS_ORIGIN` envvar explicit (not wildcard).
- `app.enableCors({origin: <single origin or narrow list>, credentials: true})`.
- Если production И `origin === '*'` → throw на boot (TZ-248 spirit).

### ШАГ 7: Force single refresh mechanism

- audit всех interceptors, guards, services на наличие "refresh logic".
- Единственный author — `AuthService.refresh()` + `AuthInterceptor`. Никаких alt-путей.
- TZ-232.N (SubmitGuard double-submit guard) остаётся — это **другая** concern (form-level), не дубликат.

### ШАГ 8: Tests

- backend: `auth-cookie.spec.ts` — login response sets refresh cookie correctly; refresh endpoint reads from cookie; logout clears cookies.
- backend: `cors-restrict.spec.ts` — wildcard CORS rejected on prod boot.
- frontend: `auth.service.spec.ts` — access token NOT in localStorage; refresh works via cookie-credentials.
- e2e: full auth cycle login→access→refresh→logout→cookies cleared.

## 4. Критерии приёмки

1. Login response: `Set-Cookie: kppdf_refresh=...; HttpOnly; Secure; SameSite=Strict`.
2. Frontend: `localStorage.getItem('kppdf.access')` returns null after successful login.
3. Frontend: `localStorage.getItem('kppdf.refresh')` returns null after login.
4. `POST /api/auth/refresh` — reads refresh from `req.cookies.kppdf_refresh`.
5. Browser network tab: refresh request has Cookie header, but no Authorization header on refresh itself.
6. logout → Set-Cookie with Max-Age=0.
7. Multi-tab refresh: only one POST /auth/refresh для N concurrent 401.
8. CORS allowlist: production с wildcard origin → boot fails (TZ-248).
9. WithCookie=true and CORS=rejectwildcard HARD-assertion in tests.
10. `pnpm test` + e2e pass.
