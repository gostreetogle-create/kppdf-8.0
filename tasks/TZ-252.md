# TZ-252 — Auth token storage и refresh contract

**Статус:** READY / будущая задача. Создание задачи не меняет frontend auth.

**РОЛЬ АГЕНТА:** Full-stack Authentication Security Engineer

**ЗАВИСИМОСТИ:** TZ-248 и TZ-249. Перед началом сверить фактический код с архивным описанием TZ-127: статус в документации не считать доказательством реализации.

**LAYER:** 4

**CONFLICT KEYS:** `frontend/src/app/core/auth.service.ts`; `frontend/src/app/core/auth.interceptor.ts`; `frontend/src/app/core/auth.interceptor.spec.ts`; `backend/src/modules/auth/auth.controller.ts`; `backend/src/modules/auth/auth.service.ts`; `backend/src/modules/auth/strategies/*`; `backend/src/main.ts`; `backend/src/app.module.ts`; `frontend/src/app/app.config.ts`

## Цель

Устранить несоответствие между заявленным HttpOnly refresh-cookie flow и фактическим клиентским контрактом. Access token не должен быть доступен любому XSS-коду через localStorage, а refresh endpoint должен иметь один ясный transport contract.

## Что сделать

1. Зафиксировать текущий runtime contract: где реально лежат access/refresh tokens, какие cookie flags выставляются, какой transport читает refresh strategy и какие requests отправляет interceptor.
2. Перевести refresh token на HttpOnly cookie с `Secure`, `SameSite` и узким path; access token хранить только в памяти приложения, если это не ломает требование session persistence.
3. Настроить `credentials: include`/CORS только для конкретного frontend origin и проверить logout/refresh после reload.
4. Если auth остаётся cookie-based для мутирующих requests, добавить минимальную CSRF-защиту; если access Bearer-only остаётся основным auth, документировать почему CSRF не применим к этим requests.
5. Добавить browser/unit tests на отсутствие token в localStorage, cookie flags, refresh rotation/revoke и concurrent 401 single-flight.

## Файлы для изменения

- Файлы из CONFLICT KEYS.
- Auth tests и минимальная документация auth contract.

**Не изменять:** бизнес-страницы; не оставлять два параллельных refresh механизма.

## Критерии приёмки

1. В runtime существует один документированный refresh transport; legacy header/body path удалён или ограничен миграционным периодом.
2. Refresh token не читается JavaScript-кодом и не сохраняется в localStorage/sessionStorage.
3. Cookie имеет `HttpOnly`, `Secure`, `SameSite=Lax/Strict`, узкий `Path` и ожидаемый срок жизни.
4. После reload валидная сессия восстанавливается через refresh, logout отзывает её, а параллельные 401 вызывают один refresh request.
5. CORS не использует `*` и не разрешает credentials неизвестным origin.
6. Frontend typecheck/tests/lint и backend tests/build проходят.

## Ограничения

Не внедрять SSO, MFA, Redis session store или enterprise identity provider. Это точечное исправление browser token exposure и contract drift.
