# TZ-251 — Object-level authorization и IDOR audit

**Статус:** READY / будущая задача. Аудит и тесты будут выполнены позже; код сейчас не меняется.

**РОЛЬ АГЕНТА:** Backend Authorization Engineer + QA

**ЗАВИСИМОСТИ:** TZ-249 и TZ-254 обязательно. Выполнять после фиксации RBAC/shared-vs-owned policy; server-side permissions enforcement идёт после этого аудита.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/common/guards/jwt-auth.guard.ts`; `backend/src/common/guards/roles.guard.ts`; `backend/src/common/decorators/roles.decorator.ts`; `backend/src/modules/*/*.controller.ts`; `backend/src/modules/*/*.service.ts`; `backend/test/**`

## Цель

Доказать, что изменение `:id` в URL не позволяет обычному сотруднику выполнить запрещённое действие над чужой или системной записью. В текущей корпоративной модели общие справочники могут быть доступны всем сотрудникам, поэтому ownership не добавлять автоматически — сначала явно разделить shared resources и user-owned resources.

## Что сделать

1. Составить endpoint matrix для всех `GET/PATCH/DELETE/:id`, upload/download и admin routes: authentication, required roles, resource type, ownership/shared policy.
2. Проверить серверные guards и service-level checks. Скрытие кнопки на Angular не считать защитой.
3. Для user-owned ресурсов добавить проверку `resource.ownerId === currentUser.id` либо корректную policy service; для shared corporate data явно закрепить role-based policy.
4. Защитить системные записи, audit/rate-limit/config endpoints и поля role/isActive/permissions от manager/user mutation.
5. Добавить integration tests минимум для user, manager и admin: чужой ID, отсутствующий ID, системная запись, попытка повысить роль, read vs write.

## Файлы для изменения

- Конкретные controllers/services только после endpoint matrix.
- `backend/test/**` для regression/integration tests.

**Не изменять:** frontend route guards как единственный security fix; не менять бизнес-модель ownership без отдельного решения PO.

## Критерии приёмки

1. Endpoint matrix покрывает все resource controllers и хранится в test/documentation artifact.
2. Для каждого user-owned endpoint есть отрицательный test на чужой ID.
3. Для shared справочников policy явно описана и role guard проверяется на сервере.
4. User/manager не могут менять role, permissions, isActive или системные записи.
5. Неавторизованный запрос получает 401, недостаточная роль — 403, несуществующий/недоступный объект не раскрывает лишние данные.
6. Backend tests, build и lint проходят.

## Ограничения

Не внедрять полноценный enterprise policy engine. Достаточно guards + небольших service-level ownership checks и тестовой матрицы.
