## 0. Цель

Корпоративная CRM с **разными** resource ownership modes:
- **user-owned**: документы, личные настройки, drafts, photos — только owner может mutate
- **shared corporate data**: Counterparties, products catalog, warehouses — все authed users могут читать; mutations по RBAC (TZ-254)

Endpoint matrix должен корректно отражать:
- user kan GET/POST/PATCH/DELETE **свои** ресурсы
- user может GET shared resources при RBAC
- admin может всё (per `wildcard '*'`)

---

## 1. Контекст

Сейчас `@Roles('admin','manager')` на `/api/contracts/:id` **позволяет любому manager edit anything** — это IDOR брешь, потому что manager из Org-A не должен редактировать contract из Org-B. Даже в single-org deploy: один оператор ЕОП может временно стать «manager» и неконтролируемо редактировать чужие заявки.

(Отметка: multi-org enforcement — отдельный вышестоящий concern; здесь — IDOR защита ВНУТРИ trusted group.)

---

## 2. Архитектурное решение

### ШАГ 1: Resource ownership classification

В каждой Schema (TZ уже varies) — добавить `ownerField: 'createdBy' | null` метаданные.
- Document, Draft, PersonalNote: `ownerField: 'createdBy'`
- Counterparty, Product, Material, Order, Contract, Warehouse: `ownerField: null` (shared)
- AuditLog: `ownerField: null` (read только admin, но internal resource)

`backend/src/common/contracts/rbac-contract.ts` (TZ-254 — добавить constraints) экспортирует список:
```typescript
export const OWNERSHIP_BY_ENTITY = {
  documentTemplate: 'createdBy',
  generatedDocument: 'createdBy',
  photo: 'createdBy',
  // ...
  counterparty: null,
  product: null,
  // ...
};
```

### ШАГ 2: Ownership decorator + guard

`@OwnerOnly('documentTemplate')` decorator — для user-owned resources. Static metadata key.

`OwnershipGuard`:
- Для operation ∈ {GET-by-id, PATCH, DELETE} на user-owned resource:
  - Загрузить document по ID.
  - Если `req.user.role === 'admin' И req.user.permissions.includes('*')` → allow.
  - Else если `document.createdBy.toString() === req.user.id` → allow.
  - Else → 404 (НЕ 403; не leak существование).
- Для shared resources: применить `@Permissions` (TZ-255) и НЕ ownership check.
- Если resource не найден → 404.

### ШАГ 3: Endpoint matrix

Один общий файл `backend/test/object-authz.e2e-spec.ts` для validation:

| Endpoint | Resource | Mode | Test |
|---|---|---|---|
| GET /api/document-templates/:id | documentTemplate | owned | user-A CAN; user-B → 404 |
| GET /api/document-templates/:id | documentTemplate | owned | admin CAN |
| GET /api/counterparties/:id | counterparty | shared | user CAN (если read perm) |
| PATCH /api/counterparties/:id | counterparty | shared | user WITHOUT write perm → 403 |
| DELETE /api/document-templates/:id | documentTemplate | owned | user-A CAN (own); user-B → 404 |

### ШАГ 4: 401 vs 403 vs 404 semantics

- **401 Unauthorized** — no JWT / refresh-token expired: `JwtAuthGuard` через `@UseGuards`.
- **403 Forbidden** — JWT валиден, но RBAC/Role запрещает: `RolesGuard` или `PermissionsGuard`.
- **404 Not Found** — Resource НЕ НАЙДЕН ИЛИ не yours: OwnershipGuard (latter приоритет по выбору).

Security rationale 404 for ownership:
- Не leak: «exists but not yours»;
- Bypass attempts не дают инфу enumeration.

### ШАГ 5: Tests

- E2E matrix (см. ШАГ 3).
- Unit OwnershipGuard — admin wildcard case; ownership match case; mismatch case; missing resource case.
- Уточнение: CRLF / Method override / cacheable headers — not in scope.

## 4. Критерии приёмки

1. user-A → PATCH /api/document-templates/:id (own) → 200.
2. user-B → PATCH /api/document-templates/:id (user-A's) → 404.
3. admin (с '*' perm) → PATCH любой → 200.
4. user на shared resource БЕЗ permissions → 403.
5. user на shared resource с permissions → 200.
6. regression: existing functional tests pass.
7. `pnpm test` exit 0; backend typecheck exit 0.
