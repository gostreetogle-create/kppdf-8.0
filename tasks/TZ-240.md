# TZ-240 — Reference Data Scoping (Product, Material, Category per-Org)

**Дата создания:** 2026-07-31 (audit от multi-tenant readiness review)
**Автор:** senior-architect audit (TZ-238..241 batch)
**Приоритет:** HIGH (закрывает cross-org ref-data bleed: цены, материалы, категории)
**Связь:** REQUIRES `TZ-238 (User.organizationId)` для fork-JWT propagation; RECOMMENDS `TZ-239 (OrgScopeGuard)` для enforced isolation
**Скоуп:** Add `organizationId` to 3 reference collections (Product, Material, Category). Service-layer filter в find/CRUD операциях. **Не трогает** TZ-239 transactional controllers — applied in parallel/conjunction.

---

## 0. TL;DR для PO

**Цель:** Сделать номенклатуру каждой Org независимой. Изменение цены материала в Орг-A не сломает Орг-B. System-record pattern: shared reference data (TZ-seeded) остаются global.

**Архитектурный pattern:**
- `organizationId?: ObjectId` (sparse index) на Product, Material, Category.
- Service `.findAll()` filter: `{ $or: [{ organizationId: userOrgId }, { organizationId: null, isSystem: true }] }`.
- Creation: DTO enforce `organizationId` для non-system referees.
- Migration: existing prod data → assign к bootstrap org.

**Объём:**
- ~180 LOC backend (3 schema additions + 3 service filters + 3 DTO changes + 1 migration script)
- 2-3 e2e tests (cross-org ref-data isolation)
- 0 frontend changes (data comes scoped by default post-TZ-238)

---

## 1. Контекст (проблема)

### 1.1 Audit verification

Проверено: `Product.schema`, `Material.schema`, `Category.schema` НЕ содержат organizationId. При multi-tenant scenario:

- Org-A меняет цену ламината → Org-B заказы используют ту же цену (data bleed).
- Категория «Корпусная мебель» в Org-A налоговая ставка 20% → в Org-B 0% — нет разделения.
- Counterparty 'Поставщик X' зависит от per-org setup, но ссылки на Product[] одинаковые.

### 1.2 Cross-tenant bleed scenarios

- Multi-org: один instance kppdf-8.0 для двух разных компаний.
- White-label SaaS: разные tenants имеют разный price-list.
- Department isolation: филиальная сеть видит свой product catalog.

### 1.3 Почему не глобально-обязательно organizationId

- Некоторые reference данные — **shared справочники**: те же ВАЛЮТЫ (RUB, USD, EUR), UNIT (шт, м, кг), DOCUMENT TEMPLATE PATTERNS. Эти TZ-seeded как `isSystem:true` и остаются global (TZ-240 applies только NEW schema fields).
- `unit`, `currency`, `document-table-type`, `doc-type`, `attribute-definition`, `work-type` — Global reference data. TZ-240 НЕ трогает.
- `Role`, `Permission`, `Status`, `Setting`, `FeatureFlag` — глобальные.

## 2. Архитектурное решение

### 2.1 Schema additions

```typescript
// backend/src/modules/product/product.schema.ts
@Prop({ required: false, index: true, sparse: true })
organizationId?: Types.ObjectId; // null for system records (TZ-seeded shared)

// backend/src/modules/material/material.schema.ts (same)
// backend/src/modules/category/category.schema.ts (same)
```

Композитный индекс: `(organizationId: 1, sku: 1) sparse unique` — обеспечивает UNIQUE-sku-per-org (SKU может повторяться между orgs).

### 2.2 Service-layer filter

Pattern, applied к product/material/category service `.findAll()`:

```typescript
async findAll(filter: ProductFilter, user: AuthenticatedUser): Promise<Product[]> {
  const baseFilter: FilterQuery<Product> = { ...filter, deletedAt: null };

  // System admin without org → see everything (for cross-org admin UI).
  if (!user.organizationId) {
    return this.model.find(baseFilter).lean().exec();
  }

  // Org-scoped query: record belongs to user's org OR is a system (shared) record.
  baseFilter.$or = [
    { organizationId: new Types.ObjectId(user.organizationId) },
    { organizationId: { $exists: false } }, // legacy records (pre-migration)
    { organizationId: null, isSystem: true },
  ];
  return this.model.find(baseFilter).lean().exec();
}
```

### 2.3 DTO enforcement

```typescript
// product.dto, material.dto, category.dto
@IsOptional()
@IsObjectId()
organizationId?: string; // optional в MVP — system records могут существовать

@IsOptional()
@IsBoolean()
isSystem?: boolean; // explicitly mark as system-shared record
```

ValidationPipe whitelist: if `me.organizationId` && `!dto.isSystem` → reject `organizationId: null`.

### 2.4 FK integrity (counterparty/contract linking)

Контракты и orders link на Product/Material by ObjectId. Cross-org reference breaking? — **Decision:** allowed. Если Org-A ссылается на Product из Org-B (через прямой id) — возвращает 404 (TZ-239 enforced). Org-A не может случайно "перейти" в Org-B catalog. Это **само-защитная** семантика.

### 2.5 Migration script

`backend/src/database/migrations/2026-07-31-TZ-240-refdata-scoped.ts`:

1. Если есть Organizations → first org = default для всех существующих Product/Material/Category без orgId.
2. Seeding: НЕ меняем unit/currency/etc (TZ-seeded isSystem=true).
3. Re-runnable: idempotent.

### 2.6 Admin UI для cross-org catalog

OUT OF scope TZ-240. TZ-238-extension может добавить `/admin/cross-org` для super-admin.

## 4. Критерии приёмки

1. Product_orgA не появляется в OrgB `GET /products` listing (org-scoped filter).
2. Product с `isSystem: true` (system seed) виден обоим orgs.
3. Composite index `(organizationId, sku)` unique — нельзя создать дубликат SKU внутри одного org, но можно в разных.
4. POST /products без organizationId (non-system) → 400 для non-admin user.
5. Cross-org link (контракт Org-A ссылается на ProductOrg-B) — findByReferences возвращает 404 (TZ-239+junction).
6. Migration script re-runnable без ошибок.
7. `pnpm tsc --noEmit` exit 0; `pnpm test` exit 0.

## 5. Тесты

1. **unit per-service spec** — findAll() filter returns scoped queries correctly:
   - system admin: all products
   - OrgA user: OrgA products + shared isSystem products only
   - OrgA user: не видит OrgB products
2. **e2e `refdata-org-isolation.e2e-spec.ts`** — multi-org scenario:
   - create OrgA + OrgB + ProductA + ProductB + isSystem ProductShared
   - OrgA user GET /products → [ProductA, ProductShared] (нет ProductB)
   - OrgB user GET /products → [ProductB, ProductShared] (нет ProductA)
   - system admin GET /products → [ProductA, ProductB, ProductShared]
3. **composite index e2e** — create OrgA+ProductA(sku='X'), OrgB+ProductB(sku='X') → both succeed; OrgA+ProductA2(sku='X') → duplicate error.
4. **migration e2e** — pre-state: 5 products без orgId, 1 organization. Run: 5 products → first orgId. Re-run: idempotent.

## 8. Risks

- **R1:** Composite unique index уникальности по (orgId, sku) — если существующие данные имеют для нескольких orgs один sku, миграция падает. Mitigation: preflight migration script.
- **R2:** `isSystem:true` — баг-prone. Mitigation: enforce через DTO + service-level reject creation with isSystem from non-admin.
- **R3:** Composite index performance impact — additional index per collection. Mitigation: index size small (~200 byte per docs, filtered by org).
- **R4:** Frontend не знает что products теперь org-scoped — UX-leak (ProductA виден OrgB user в autocomplete). Mitigation: TZ-242 (frontend guards) + autocomplete fetches уже return scoped.
- **R5:** Adm-tool FROM OrgA видит чужие catalog через direct URL — same as TZ-239 risk, mitigated через OrgScopeGuard.
