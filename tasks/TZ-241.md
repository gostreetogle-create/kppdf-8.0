**Дата создания:** 2026-07-31 (audit от multi-tenant readiness review)
**Автор:** senior-architect audit (TZ-238..241 batch)
**Приоритет:** CRITICAL (close security-auth gap: deactivation should immediately block; counterparty data privacy)
**Связь:** REQUIRES `TZ-238 (User.organizationId)` для propagation; COMPOSITE OF (counterparty scoping pattern from TZ-240) + (auth-time isActive enforcement)
**Скоуп:** Backend-only: (a) Counterparty schema + service filter mirror TZ-240 pattern; (b) JWT auth-time check `user.isActive && role.isActive` через JwtAuthGuard с встроенным 30s cache.

## 0. TL;DR для PO

**Цель:** Две соседние правки, общая ткань:
1. **Counterparty scoping:** Поставщики/клиенты Орг-A не видны Орг-B (финансовая конфиденциальность).
2. **Auth-time activity check:** Заблокированный юзер (`isActive:false`) или удалённая роль (`role.isActive:false`) НЕ ДОЛЖЕН иметь доступ даже с валидным JWT — сейчас пробрасывают в access на 24h+ после отключения.

**Объём:**
- ~30 LOC backend Counterparty schema + service (TZ-240 mirror).
- ~30 LOC backend JwtAuthGuard extension + RoleModel cache.
- 1 migration script.
- 3 backend unit tests + 2 e2e tests.

## 1. Контекст (проблема)

### 1.1 Counterparty audit

`Counterparty.schema` НЕ содержит organizationId. Контрагенты — это financial parties (customer/supplier/contractor). В multi-tenant — каждая org должна иметь свой namespace. Сейчас cross-org:

- Manager из Org-A делает `GET /api/counterparties/<OrgB-id>` → returns Org-B counterparty с INN, ОГРН, банковскими реквизитами.
- Risk: financial data breach, GDPR-style, IRS-style нарушение.

### 1.2 isActive auth gap

Audit видит:

```typescript
// backend/src/common/guards/jwt-auth.guard.ts (current)
override handleRequest<TUser = unknown>(
  err: unknown,
  user: TUser,  // уже пассивно пробрасывает user из DB
  info: unknown,
): TUser {
  if (err || !user) { ... 401 }
  return user;  // ⚠️ Не проверяет user.isActive ИЛИ role.isActive!
}
```

После login() user.has валидный access (15min TTL). JWT гейтится только expiration signature — **не** `user.isActive`. После admin-действия `user.isActive=false`, юзер продолжает работать 15-25 мин до access-expiry + до следующего /auth/refresh (через refresh = 7d → user ещё дольше живёт если refresh не invalidated).

Реально risk меньше потому что **TZ-04 refreshTokenVersion bump on logout/change-password** invalidate refresh-tree. **Но:** если admin делает `POST /api/users/:id/change-password` — user.refreshTokenVersion bump'ится, но этот **самый action не инвалидирует текущий активный access token**, который истечёт через <15min. Окно утечки <15min — приемлемо для MVP.

**Real gap:** `role.isActive===false` НЕ bump'ит refreshTokenVersion. Если admin удалит роль, все её members могут продолжать работу через re-login с cached refresh token. **Это OK для MVP** для manual admin actions (rare event), **но** для automatic role deactivation (Phase C — ScheduledJobs) это будет unacceptable.

**TZ-241 близкий фикс:** Добавить **auth-time check** в JwtAuthGuard: на каждом hydration из БД, verify `user.isActive && role.isActive`. Cache 30s для perf. Это closes deactivation window completely.

### 1.3 Why NOT invalidate active access tokens on user deactivation

- Active access tokens в circulation (microseconds-scale) — invalidation невозможна stateless.
- Mitigation: shorten access TTL до 60s (TZ-91 extension); bump refreshTokenVersion на deactivation (existing); TZ-241 fix — auth-time hydration check.

### 2.1 Counterparty schema

Composite index `(organizationId: 1, inn: 1)` sparse unique — same pattern as TZ-240 for SKU uniqueness.

### 2.2 Counterparty service filter

Mirror TZ-240: `.findAll()` filter applies scoped query:

```typescript
async findAll(filter: CounterpartyFilter, user: AuthenticatedUser): Promise<Counterparty[]> {
  const baseFilter: FilterQuery<Counterparty> = { ...filter, deletedAt: null };

  if (!user.organizationId) return this.model.find(baseFilter).lean().exec();

  baseFilter.$or = [
    { organizationId: new Types.ObjectId(user.organizationId) },
    { organizationId: null, isSystem: true },
    { organizationId: { $exists: false } }, // legacy pre-migration
  ];
  return this.model.find(baseFilter).lean().exec();
}
```

Controller apply `@RequireOrgScope()` из TZ-239 — общий pattern, но **counterparty service-level filter handles independently** — defensive in depth.

### 2.3 CounterpartyRole / OrgRole справочники — global

CounterpartyRole справочник (customer/supplier/contractor/manufacturer roles) — global. OrgRole справочник (our-company/partner/holding/branch) — global. Уже isSystem:true seeds. TZ-241 НЕ меняет.

### 2.5 JwtAuthGuard isActive check

```typescript
// backend/src/common/guards/jwt-auth.guard.ts (extended)
override async canActivate(context: ExecutionContext): Promise<boolean> {
  const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [...]);
  if (isPublic) return true;

  const ok = await super.canActivate(context);
  if (!ok) return false;

  // TZ-241: verify active статус auth-time.
  // Already hydrated req.user by JwtStrategy.validate() — re-fetch fresh data
  // OR use a slightly stale 30s cache to avoid DB round-trip per request.
  const req = context.switchToHttp().getRequest<{ user: AuthenticatedUser | undefined }>();
  const userId = req.user?.id;
  if (!userId) throw new UnauthorizedException('No user context');

  const activity = await this.activityCache.getOrFetch(userId, async () => {
    const user = await this.userModel.findById(userId).lean().exec();
    if (!user || user.isActive === false) {
      return { active: false, reason: 'user_inactive' };
    }
    if (user.role) {
      const role = await this.roleModel.findOne({ name: user.role }).lean().exec();
      if (!role || role.isActive === false) {
        return { active: false, reason: 'role_inactive' };
      }
    }
    return { active: true };
  });

  if (!activity.active) {
    throw new UnauthorizedException(`User access revoked: ${activity.reason}`);
  }

  return true;
}
```

**Cache implementation:**

```typescript
// backend/src/common/guards/user-activity-cache.ts (NEW file, scoped to JwtAuthGuard)
class UserActivityCache {
  private readonly cache = new Map<string, { result: ActivityCheck; expiresAt: number }>();
  private readonly TTL_MS = 30_000; // 30s — balance freshness vs DB load

  async getOrFetch(userId: string, fetch: () => Promise<ActivityCheck>): Promise<ActivityCheck> {
    const cached = this.cache.get(userId);
    if (cached && cached.expiresAt > Date.now()) return cached.result;

    const result = await fetch();
    this.cache.set(userId, { result, expiresAt: Date.now() + this.TTL_MS });
    return result;
  }

  invalidate(userId: string): void { this.cache.delete(userId); }
}
```

**Cache invalidation on user/role mutations** — emitted by UserService.update() / RoleService.update() → call `activityCache.invalidate(userId)`. TZ-241 includes the wiring.

### 2.6 Trade-off: 30s window после deactivation

После admin disables user via `PATCH /users/:id { isActive:false }`, user продолжает работать ~30s до cache expiry. После refresh: /auth/me → bootstrap flow rehydrates → guard always fresh.

Документировано в TZ-241. Acceptable for MVP. Если нужно instantaneous — отдельный TZ-241-extension инвалидирует cache on every privileged mutation.

## 4. Критерии приёмки

1. **Counterparty:**
   - OrgB user → GET `/counterparties/<OrgA-id>` → 404 (TZ-239 by composite org-scope).
   - OrgA user → GET `/counterparties` → only OrgA counterparties.
   - System admin → all counterparties.
   - Composite index `(organizationId, inn)` unique enforced.
2. **isActive (counterparty/org-scope guard):**
   - Disable user (`isActive:false`) → next request (within 30s cache TTL) → 401. After 30s → block.
   - Disable role → next request (within 30s TTL or after) → 401.
   - Re-enable user → cache invalidated or TTL passed → access restored.
3. **Cache invalidation:**
   - PATCH /users/:id → invalidate cache immediately.
   - PATCH /roles/:id → invalidate all members cache.
4. **Regression:**
   - existing functional tests pass (same-org access unchanged).
5. **Backend:** `pnpm tsc --noEmit` exit 0; `pnpm test` exit 0.

## 8. Risks

- **R1:** Cache TTL 30s means ~30s window of inactivity после admin-disable. Mitigation: documented; alternative is shorter TTL (1s) with DB load — out of scope.
- **R2:** UserService.update вызов invalidate cache → race condition если cache.invalidate происходит после concurrent request reading cache. Mitigation: invalidate AFTER DB write committed; worst case duplicate read returns fresh data next request.
- **R3:** RoleService.update массовый invalidate — если роль имеет 1000 users, и сразу следующие requests массивные logs в DB. Mitigation: rate-limited audit log OR bulk cache flush.
- **R4:** Composite index `(organizationId, inn)` sparse unique — legacy data может иметь несколько orgs с одним INN (теоретически). Mitigation: preflight migration script.
- **R5:** CounterpartyRole / OrgRole roles already global — но они seeded как `isSystem:true`. Миgration script НЕ трогает справочники (verified).
