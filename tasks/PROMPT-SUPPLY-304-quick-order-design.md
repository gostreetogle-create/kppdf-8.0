## Промпт (копировать отсюда)

Ты — **снабженец небольшого цеха** (~10 человек). Каждый день ты получаешь заявки от производства и сам ищешь поставщиков: подшипники, заглушки, фрезы, цанги. Сейчас ты вынужден вести Excel, потому что в ERP создать одну заявку — это 4 экрана: сначала поставщик, потом материал/продукт, потом снова снабжение, потом задача. Завтра ты покажешь экран коллегам — стыдно за кашу нельзя.

### Контекст «как сейчас» (факт kppdf-8.0)

1. **`/supply`** — реестр `SupplyTask` в **таблице**: заказ → qty → 4 жёстких статуса (Черновик / Подтверждено / Заказано / Получено). Подходит для контроля, **не** для быстрого ввода 10 позиций за утро.
2. **`/desk`** — рабочий стол менеджера: очередь заказов, expand-in-row tray. Workflow chip **«Снабжение»** сейчас ведёт на `/supply` (таблицу). Flyout `panel=supply` — заглушка.
3. **Справочники:** единицы измерения (`/dictionaries/measurements`), категории каталога (`/categories`). Статусы снабжения **не** в справочниках — захардкожены. `EntityStatus` в backend есть, но к SupplyTask не подключён.
4. **Поставщик** = `Organization` с type `supplier`. Отдельной страницы «Поставщики» нет — только общий список организаций.
5. **«Наша компания»** в Excel (СИЮ) = `Organization` — наше юрлицо, не клиент.

### Боль (суть)

- Нет **одного места**, где за 30 секунд набить «что заказать, у кого, сколько, срочно или нет».
- Нельзя начать ввод, пока не созданы все справочные сущности в других разделах.
- Табличный реестр `/supply` остаётся нужен для обзора — но **не** как точка входа для ежедневного ввода.

### Задача

Спроектируй **рабочее место «Быстрый заказ»** — отдельный режим снабжения, куда попадаешь с workflow chip **«Снабжение»** на `/desk` (и с `/supply` через chip «Быстрый заказ»).

**Паттерн UI (обязательный ориентир):** как expand-in-row на столе/заказах — **длинные плитки-строки**:
- **Свёрнуто:** одна строка-сummary (дата · категория · наименование · qty · статус-badge · приоритет-color · поставщик коротко).
- **Развёрнуто:** форма по **блокам-категориям** (не простыня из 16 полей подряд).
- **«+ Создать»** → новая плитка **сразу развёрнута**, курсор в главное поле; после заполнения — сворачиваешь, идёшь дальше.
- **Статус** — один выпадающий список (из справочника, редактируемого админом). **Без** канбана/комбайна перемещений.
- **Приоритет** — выпадающий список с цветовой подсветкой (Срочно / Обычный / Низко — как в Excel: красный / нейтральный / зелёный).

### Поля v1 (из реальной Excel-таблицы PO)

| Блок | Поля | Примечание |
|------|------|------------|
| **Что заказать** | Категория, Наименование*, Артикул, Цвет, Фото (thumb + upload), Кол-во*, Ед. изм.* | *обязательные минимум для сох-save черновика |
| **Откуда купить** | Поставщик (select + «+ новый» inline: название, сайт), Ссылка на товар (URL) | Не заставлять идти в «Организации» |
| **Контекст** | Наша компания (select), Заказчик / кто просил (select или текст: «Производство», ФИО), Связь с заказом (optional), Нужно к (дата) | «Заказчик» часто = подразделение |
| **Статус и приоритет** | Статус (dropdown из справочника), Приоритет (dropdown), Примечание (контакты, телефоны, коды MAX) | Статус по умолчанию «В работе» |

### Полезные доп. поля (предложи, если логично)

- Ориентировочная цена / сумма строки
- Фактическая дата заказа у поставщика
- Ответственный снабженец (текущий user)
- Метка «из Excel / ручной ввод» — не показывать в UI, только для миграции

Не раздувай v1 — лучше 2–3 поля в блоке «Ещё», чем 16 колонок как в Excel.

### Навигация и IA

- Workflow chip **«Снабжение»** на `/desk` → **`/supply?view=quick`** (или эквivalent — предложи канон URL).
- На `/supply` — **два chip** в одной sticky строке: **«Быстрый заказ»** (default) | **«Реестр»** (текущая таблица SupplyTask — не ломать).
- Dense workspace как у `/desk` — без лишней шапки.
- Toolbar: поиск по наименованию/артикулу/поставщику; фильтр статус + приоритет; счётчик «N заявок»; «+ Создать».

### Жёсткие ограничения

- Язык UI — **русский**.
- Дизайн: **Paper & Ink**, цеховой ERP kppdf — спокойно, плотно, без «SaaS-dashboard» карточек и фиолетовых градиентов.
- Не предлагать править каталог материалов **до** сохранения заявки — свободный текст + артикул достаточно для v1.
- Не предлагать канбан/drag статусов на v1.
- Не предлагать второй write-path поверх SupplyTask registry — это **новый режим** (позже привяжем API; сейчас про UX).
- Табличный реестр `/supply` **остаётся** — не заменять, а дополнить.
- Light + dark — оба читаемы.

### Как думать (обязательно)

1. Пройди сценарий: утро → 5 заявок от производства → 3 срочных → нашёл поставщика profrezi.ru → вбил 2 фрезы и цангу → свернул → переключился на «Реестр» → нашёл «Заказано».
2. Пройди сценарий: поставщика нет в списке → «+ новый» прямо в строке → сохранил черновик без ухода со страницы.
3. Сравни со **свёрнутой строкой заказа** на `/desk` — та же логика «summary → expand», но контент про закупку.
4. Явно раздели **Быстрый заказ** vs **Реестр** — зачем два режима одному человеку.

### Формат ответа (строго)

1. **Одной фразой** — север: что такое «Быстрый заказ» для снабженца.
2. **IA** — chips, URL, откуда вход (desk / supply / order tray «Открыть»).
3. **Макет страницы** — ASCII или блочная схема сверху вниз (toolbar → список плиток → empty state).
4. **Плитка свёрнута / развёрнута** — два макета рядом; блоки полей с RU-подписями.
5. **Inline-create** — где «+ новый» для поставщика/категории; что в модалке vs inline.
6. **Справочники** — какие списки нужны в админке (статусы, категории заявки, приоритеты); дефолтные значения RU.
7. **Связь с Реестром** — когда строка попадает в таблицу SupplyTask / PurchaseRequest (концептуально, без API).
8. **Антипаттерны** — 5 вещей, которых нельзя делать.
9. **Критерии приёмки дизайна** — 10–12 проверяемых пунктов «готово показать цеху».
10. **Порядок внедрения** — 3 шага: (1) UI mock, (2) API + справочники, (3) синхрон с реестром.

Не пиши код. Не предлагай микросервисы. Думай как человек, который 8 часов в день заказывает метизы и оснастку.
