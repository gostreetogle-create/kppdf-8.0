## ЦЕЛЬ

PO выбирает шрифт и размер текста в документе — и то же самое должно оказаться в PDF. Сегодня не оказывается:
рендер жёстко прибивает `font-family: 'Times New Roman', serif` на `body` (`document-render.service.ts:82`), а
типографика существует только внутри TipTap-HTML в `content`. Значит выбранный шрифт живёт до перезагрузки страницы
и умирает на выводе.

Эта TZ — **только backend и только схема с рендером**. UI-тулбар шрифтов приходит в срезе S4; если сделать его раньше
схемы, сохранённый в S3 текст придётся переписывать миграцией.

## ГЛАВНОЕ РЕШЕНИЕ: один источник правды для стиля

Гибрид «поля на блоке + произвольный inline-CSS» даёт двойной источник правды и расхождение экрана с PDF, поэтому
правило жёсткое и не обсуждается на реализации:

| Что | Где живёт | Inline-HTML внутри абзаца |
|---|---|---|
| гарнитура, размер, цвет, выравнивание, межстрочный | **только `block.style`** | вырезается при сохранении |
| жирный, курсив, подчёркивание, ссылка | inline-HTML | остаётся |

То есть `block.style` побеждает всегда, потому что конкурента у него не остаётся физически — не «по приоритету CSS»,
а потому что конфликтующие inline-объявления не доходят до базы.

## ИСХОДНОЕ СОСТОЯНИЕ (проверено)

- `TemplateBlock`: `type` (header|text|table|image|signature|spacer) `:132`, `content?` `:141`, `columns[]` с
  собственным `fontSize` `:111-151`, `layout?` `:164`, `locked` `:182`, `dataBinding?` `:189`. Поля стиля **нет**.
- `templateId` всё ещё `required: true` (`:121`) при незакрытом dual-read cutover — в этой TZ **не трогать**,
  только не ухудшать.
- Рендер: `@page{margin:0}` + `body{font-family:'Times New Roman',serif}` (`:79,82`); второй путь рендера —
  `:222` с `.doc-content{padding:20px}` (`:231`). Колонки получают только `font-size` из `columns[].fontSize` (`:135`).
- Валидация DTO в проекте с `forbidNonWhitelisted`: новое поле, не описанное в DTO, вернёт 400.

## ЧТО ДЕЛАТЬ

### Шаг 1 — подсхема `BlockStyle`

Добавить необязательное поле `style?: BlockStyle` на `TemplateBlock` со своей Mongoose-подсхемой:

- `fontFamily?: string` — **только из белого списка** (шаг 2), иначе 400.
- `fontSizePt?: number` — целое, 6..96.
- `color?: string` — hex `#rgb`/`#rrggbb`, валидация регуляркой.
- `align?: 'left' | 'center' | 'right' | 'justify'`.
- `lineHeight?: number` — 0.8..3.

Поле **необязательное, миграции нет**. Блок без `style` рендерится ровно как сегодня (Times New Roman 14pt) — старые
документы не должны измениться ни на пиксель. Это отдельный критерий приёмки.

### Шаг 2 — белый список шрифтов, привязанный к реальности рендера

Главная ловушка: PDF рисует headless-браузер на сервере, и если выбранной гарнитуры в контейнере нет, подстановка
произойдёт молча — оператор увидит на экране один шрифт, а в PDF другой. Поэтому:

1. Завести один экспортируемый список допустимых гарнитур в модуле `template-block` (константа + тип), на него же
   ссылается валидация DTO. Фронт в S4 обязан брать список отсюда, а не хардкодить свой.
2. Для каждой гарнитуры из списка **доказать доступность в рендере**: либо шрифт есть в образе, либо в HTML-шаблон
   рендера добавляется `@font-face` с файлом из репозитория. Способ выбрать сам, но результат зафиксировать в
   чеклисте и в `docs/pages/document-studio.page.md`.
3. Начать с минимума, который реально нужен коммерческому документу: Times New Roman, Arial, Calibri или их
   метрически совместимые аналоги, доступные в образе. Список из 20 гарнитур «на будущее» — не заводить.

### Шаг 3 — sanitize при сохранении

В сервисе создания и обновления блока (оба parent'а: шаблон и studio-документ) вычищать из `content`:

- объявления `font-family` и `font-size` в атрибутах `style`;
- объявления `color`;
- пустые `<span>`, оставшиеся после вычистки.

Сохранять: `b`/`strong`, `i`/`em`, `u`, `a[href]`, `br`, `p`, списки, и уже существующие токены подстановки
`{{путь.к.полю}}` — их формат ломать нельзя (`document-render.service.ts:37-50`). Sanitize должен быть чистой
функцией с юнит-тестами, а не regexp'ом внутри контроллера.

### Шаг 4 — рендер читает стиль блока

1. Убрать хардкод гарнитуры с `body` в пользу дефолта, равного текущему поведению, и применять `block.style` на
   уровне блока (inline-`style` на его контейнере) в **обоих** путях рендера (`:82` и `:222`).
2. `columns[].fontSize` оставить как есть, но блочный `style.fontSizePt` должен работать для колонок как значение по
   умолчанию, когда `fontSize` у колонки отсутствует.
3. Экранирование значений стиля обязательно: `color` и `fontFamily` попадают в CSS — CSS-инъекция через поле
   недопустима. Значения не из белого списка до CSS не доходят.

### Шаг 5 — DTO и тесты

1. Описать `style` в DTO создания и обновления блока для шаблона и для studio-документа (иначе `forbidNonWhitelisted`
   вернёт 400 и фронт в S4 не сможет ничего сохранить). Частичное обновление не должно затирать `style` целиком, если
   пришло одно поле.
2. Тесты (jest, co-located):
   - sanitize: вырезает family/size/color, сохраняет bold/italic/link и токены `{{…}}`;
   - валидация: шрифт вне белого списка → 400; `fontSizePt` вне 6..96 → 400; кривой hex → 400;
   - golden HTML: блок со стилем → в HTML есть ровно этот шрифт/размер/цвет/выравнивание;
   - **регресс**: блок без `style` даёт HTML, побайтово совпадающий с текущим (защита старых документов);
   - PATCH одного поля стиля не сбрасывает остальные.

## КРИТЕРИИ ПРИЁМКИ

1. `style` сохраняется и возвращается для блоков и шаблона, и studio-документа.
2. Шрифт вне белого списка, размер вне 6..96, кривой цвет — 400 с внятным сообщением.
3. Inline `font-family`/`font-size`/`color` не доживают до базы; bold/italic/ссылки и токены `{{…}}` доживают.
4. HTML и PDF используют шрифт из `block.style`; для каждой гарнитуры белого списка доказано, что рендер её реально
   рисует, а не подставляет молча.
5. Блок без `style` рендерится побайтово как до волны — доказано регресс-тестом.
6. PATCH одного поля стиля не затирает остальные.
