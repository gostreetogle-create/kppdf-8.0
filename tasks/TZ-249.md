# TZ-249 — Auth entry points и anti-automation baseline

**Статус:** READY / будущая задача. Создание задания не изменяет auth-код.

**РОЛЬ АГЕНТА:** Backend Authentication Security Engineer

**ЗАВИСИМОСТИ:** TZ-248 обязательно. Выполнять до backend idempotency-среза и не параллельно с задачами, меняющими auth/throttling bootstrap.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/modules/auth/auth.controller.ts`; `backend/src/modules/auth/auth.service.ts`; `backend/src/modules/auth/dto/register.dto.ts`; `backend/src/common/guards/throttler-behind-auth.guard.ts`; `backend/src/app.module.ts`; `backend/src/main.ts`; `backend/src/modules/auth/*.spec.ts`; `deploy/synology/DEPLOY.md`

## Цель

Закрыть публичные точки входа от автоматического создания привилегированных аккаунтов и перебора credentials, не ломая работу десяти корпоративных сотрудников.

## Что сделать

1. Принять продуктовое решение для `/auth/register`: для production отключить публичную регистрацию либо оставить только создание обычного `user` через контролируемый invite/admin flow. Публичный запрос не должен сам назначать `manager`.
2. Сохранить единое нейтральное сообщение об ошибке login и текущий лимит login по IP/ключу throttler; проверить, что лимит действительно применяется к anonymous requests.
3. Проверить общий API throttling и отдельно ограничения на login/register/refresh. Убедиться, что `DISABLE_THROTTLE=1` доступен только в test/development и не может незаметно включиться в production.
4. Проверить доверие к `X-Forwarded-For`: throttler должен использовать реальный client IP только через доверенный reverse proxy, а не принимать произвольный заголовок от внешнего клиента.
5. Добавить backend tests для публичной регистрации, role escalation, login burst и production throttle configuration.

## Файлы для изменения

- Файлы из CONFLICT KEYS.
- `backend/test/**` или auth spec рядом с модулем.

**Не изменять:** frontend UI-kit и страницы справочников; не добавлять CAPTCHA, MFA или внешнюю anti-bot платформу без отдельного решения.

## Критерии приёмки

1. Production public registration либо выключена, либо создаёт только `user`; `manager` создаётся только контролируемым серверным flow.
2. 6-я попытка login в пределах configured minute window получает throttled response, а успешные запросы после окна снова работают.
3. Burst к обычному API также ограничен; тест подтверждает, что `DISABLE_THROTTLE=1` не активируется в production.
4. Поддельный внешний `X-Forwarded-For` не позволяет обходить лимит; proxy trust явно задокументирован.
5. Login не раскрывает существование username/email.
6. Backend tests, build и lint проходят.

## Ограничения

Не добавлять enterprise WAF/SIEM, CAPTCHA для внутренних пользователей или 2FA для всех. 2FA можно оставить отдельным будущим улучшением для admin.
