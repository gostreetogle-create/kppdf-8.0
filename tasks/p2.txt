### TZ-232.A — Исправление утечки в `lookup-table.ts`

**Проблема:** `frontend/src/app/shared/util/lookup-table.ts` использует прямой `subscribe()` без `takeUntilDestroyed`, что приводит к утечке подписок при уничтожении компонента.

**Твоя задача:**
1. Переписать `createLookupTable` так, чтобы подписка автоматически отписывалась при уничтожении компонента. Используй паттерн с `DestroyRef` и `takeUntilDestroyed()`.
2. Сигнатура функции должна остаться обратно совместимой: `createLookupTable<T>(fetcher: () => Observable<SilentResult<T[]>>, keyFn?: (item: T) => string)`.
3. Возвращаемое значение — сигнал `Record<string, T>`. При вызове `fetcher` результат преобразуется в объект-словарь, ключ — значение из `keyFn` (по умолчанию `item._id`).
4. Убедись, что при повторных вызовах `fetcher` (например, при смене параметров) старые подписки корректно завершаются.
5. НЕ используй `this.http` и НЕ добавляй новых зависимостей от `HttpClient`.
6. После реализации запусти `pnpm typecheck` и `pnpm lint`, убедись, что нет ошибок. Существующие юнит-тесты в `shared/util/lookup-table.spec.ts` (если есть) должны проходить. Если тестов нет — создай минимальный тест, проверяющий корректную отписку при уничтожении компонента.

**Acceptance (из плана):**
- [ ] `lookup-table.ts` не содержит прямых `subscribe()` без отписки.
- [ ] При уничтожении компонента подписка завершается (проверить можно в тесте).
- [ ] Обратная совместимость — существующие потребители (формы с lookup) продолжают работать без изменений.

### TZ-232.N — SubmitGuard + Idempotency middleware (клиентская часть)

**Проблема:** Двойной клик по кнопке сабмита формы может создать дубликат записи. Нужна трёхуровневая защита: фронтенд-гард, HTTP-интерцептор с ключом идемпотентности и клиентский кэш.

**Твоя задача — создать три файла:**

1. **`frontend/src/app/shared/dsl/submit-guard.ts`** — сервис `SubmitGuard` (providedIn: 'root'). Реализуй в точности как описано в Master Plan §1.1. Основные моменты:
   - `guard<T>(opts: { formKey: string; url: string; method: 'POST'|'PATCH'|'DELETE'; debounceMs?: number; fetcher: () => Observable<SilentResult<T>> }): Promise<SilentResult<T>>`
   - Внутренний `Map` для хранения активных ключей идемпотентности (составной ключ `method|url|formKey`).
   - Второй `Map` для кэша завершённых запросов с TTL 5 минут для успешных, 60 секунд для 5xx, 4xx не кэшируются.
   - Логика дебаунса (300ms по умолчанию) и защиты от повторного вызова: если запрос с таким ключом уже выполняется, возвращать `{ ok: false, error: ... }` со статусом 429.
   - Фоновая очистка кэша через `setInterval` каждые 60 секунд.
   - Метод `getActiveKey(url: string, method: string): string | null` для интерцептора.
   - При реализации точно следуй логике из плана: **регистрировать ключ в Map только ПОСЛЕ дебаунса**, непосредственно перед вызовом `fetcher`. Генерация UUID через `crypto.randomUUID()`.

2. **`frontend/src/app/core/idempotency.interceptor.ts`** — функциональный HTTP-интерцептор. Читает активный ключ из `SubmitGuard.getActiveKey()` для текущего URL и метода. Если ключ есть — добавляет заголовок `Idempotency-Key`. Если нет — генерирует новый UUID (для сервисных вызовов вне форм). НЕ должен самостоятельно создавать записи в Map. Убедись, что интерцептор не вмешивается в GET-запросы и запросы, уже имеющие заголовок `Idempotency-Key`.

3. **`frontend/src/app/core/idempotency-cache.ts`** — (если требуется отдельно, но основная логика кэша уже в SubmitGuard; можно просто реэкспортировать или оставить как часть SubmitGuard). Фактически, весь кэш инкапсулирован в SubmitGuard, отдельный файл не обязателен. Но в плане упоминается. Создай файл с реэкспортом или краткой документацией, если считаешь нужным.

4. **Подключи интерцептор** в `app.config.ts` через `provideHttpClient(withInterceptors([idempotencyInterceptor]))`. Убедись, что он стоит ПЕРЕД auth-интерцептором.

5. **Напиши unit-тесты** для `SubmitGuard`:
   - Проверка, что повторный вызов с тем же ключом в течение дебаунса отклоняется.
   - Проверка, что после успешного запроса результат кэшируется и повторный вызов возвращает кэш.
   - Проверка, что 4xx не кэшируются, 5xx кэшируются на 60 секунд.
   - Проверка, что интерцептор добавляет заголовок `Idempotency-Key`.
   - Проверка, что подписки и интервалы очищаются корректно.

**Acceptance:**
- [ ] Двойной клик по сабмиту не приводит к дублирующему HTTP-запросу (проверяется тестом).
- [ ] Успешный ответ кэшируется и при повторном запросе возвращается из кэша без обращения к серверу.
- [ ] Заголовок `Idempotency-Key` присутствует в POST/PATCH/DELETE запросах.
- [ ] Все существующие тесты и сборка проходят (`pnpm test`, `pnpm typecheck`, `pnpm lint`).

   ```ts

     schema: EntitySchema<T, P>

Интерфейс EntitySchema:

ts
export interface EntitySchema<T extends { _id?: string }, P = unknown> {
  readonly endpoint: string;
  readonly idKey?: keyof T & string; // default '_id'
}

list(params: P): Observable<SilentResult<PaginatedResponse<T>>>

create(payload: Partial<T>): Observable<SilentResult<T>>

update(id: string, payload: Partial<T>): Observable<SilentResult<T>>

remove(id: string): Observable<SilentResult<void>>

Внутри inject() используй инжектирование HttpClient и API_BASE_URL (из core/api.tokens.ts), а также silentGet/Post/Patch/Delete из core/silent-http.ts. Методы должны корректно строить URL: list — ${baseUrl}${schema.endpoint}, findById — с /${id}, и т.д.
