# Бэклог: код-дельты из MASTER-CORE канона (закрыт PO 2026-08-30)

> Источник решений: [`docs/architecture/MASTER-CORE.md`](../../../docs/architecture/MASTER-CORE.md) §5.
> Это **не TZ** — punch-list, чтобы решения PO не потерялись. Каждый пункт
> становится отдельной TZ только по явному указанию PO на вертикальный срез
> (PO-CANON п.7). Не брать в работу списком без команды.

## Продажи

- [ ] `Counterparty.roles[]` (`client`/`supplier`…) вместо двух разных контрагентов на одну фирму — если/когда встретится реальный дуал-кейс.
- [x] `Contract.contractStatus: none|file_attached|generated` — редкий необязательный атрибут сделки, не блокирует переход Заказа в производство. **DONE:** C1 schema + C2 write path + C3 multipart PUT/DELETE + C4 focused specs + C5 docs (`WAVE-BACKEND-CONTRACT-FILE`). Файл-вложение — MVP; генерация из шаблона по данным КП — позже.
- [x] `Order.quotationId` optional + `isPaid`/`paidAt` + без UX заглушки КП — **DONE** волна `WAVE-NX-SALES-CANON` (S31/S36/S38).
- [ ] Семья КП (packageTag/master-variant, раскатка одного состава на несколько юрлиц) — приоритетная фича первого релиза. **TZ выданы:** `WAVE-NX-KP-FAMILY` S40–S48 (BE уже SALES-303; волна = NX UI).
- [ ] Убрать/не реализовывать: гостевой просмотр КП без логина, CRM-таймлайн взаимодействий (Interaction) — вне канона.

## Склад / Производство

- [ ] Авто-резерв материалов на складе при укомплектованном изделии в заказе; при нехватке — авто-`SupplyRequest`, привязанный к конкретному заказу+изделию (не общий).
- [ ] Склад — один, логические подсклады (металл, труба, дерево, метизы…), без адресов/ячеек — подтверждённый канон, не расширять.
- [ ] Частичная отгрузка по изделиям заказа с фиксацией «что уехало / что осталось» в документе.
- [ ] Документы отгрузки (акты, накладные) — генерация из данных заказа + редактируемый шаблон (сохранение правок как шаблона для повторного использования).
- [ ] Нехватка материала — мягкий блок (warning), подтверждённое поведение, не менять на жёсткий.
- [ ] Стадия «Проектирование/чертежи» — обязательна там, где изделию она нужна; проверить, что переход дальше по цепочке инициирует сам раздел проектирования.
- [ ] Тендеры — не строить модуль; максимум пара резервных полей на будущее, без UI.
- [ ] Комплаенс-движок с блокировкой паспорта — не строить; максимум мягкие предупреждения при явной необходимости.

## Финансы

- [ ] Полная цепочка Invoice/Payment/Refund — НЕ делать сейчас. Убедиться, что нужные для будущей аналитики данные (себестоимость, факт-стоимость, движения) уже пишутся и архивируются, ничего не теряется.
- [x] Валюта — только RUB. Legacy seed USD/EUR retired — **DONE** `TZ-NX-SALES-S30` (`e7c824e7`).
- [ ] `statusOverride {byUserId, at, reason, previousStatus}` на Заказе — возможность для Директора/Админа откатывать/переопределять статус (в т.ч. `isPaid`, `closed`) с записью в Audit log. Обычные роли — без доступа.

## Доступ

- [x] Онбординг сотрудника через инвайт-ссылку — **уже реализовано** (`backend/src/modules/auth/{auth.service,auth.controller}.ts`, `register.dto.ts`). PO подтвердил как канон, доп. работы не требуется.
- [ ] Второй уровень прав поверх «страница целиком»: небольшой фиксированный набор capability-флагов на роль (`canDelete`, `canEditAfterPaid`, `canOverrideStatus` и т.п.) — не разрастающаяся ACL-матрица. Дизайн конкретного набора флагов — на усмотрение исполнителя при первой TZ, где это понадобится.
