ЦЕЛЬ АУДИТА
════════════
Понять, насколько гибка и вертикально масштабируема ERP-платформа
перед грядущей нагрузкой (рост числа фич, сущностей, модулей).
Найти закономерности, которые сегодня копятся как долг и завтра
станут блокером. НЕ пересматривать стек и НЕ переписывать ядро —
платформа работает. Точечные, доказанные изменения.

Серия НЕ дублирует TZ-280 (process/CI/operational шум) и НЕ дублирует
TZ-199..205 (консолидация дубликатов data-model). Разрез Z —
паттерны и связность слоёв.

═══════════════════════════════════════════════════════════════
СВОДКА НАХОДОК (верифицировано по коду 2026-08-02)
═══════════════════════════════════════════════════════════════

СЛАБОЕ ЗВЕНО №1 — целостность данных (HIGH).
Бэкенд умеет `withTransaction` и `SessionRunner` и применяет их в
`stock-movement.create`, `contract.activate`, `production-order.create`.
НО три денежных/складских write-пути идут без транзакции:
`shipment.dispatch`, `purchase-order.receive`, `order.ship`.
Любой throw после первой записи оставляет «грязный» склад.
→ Z-001.

СЛАБОЕ ЗВЕНО №2 — фронтовый DSL мёртв (HIGH).
`defineEntity` + `PiEntityListComponent` — флагманская абстракция —
имеет НОЛЬ реальных потребителей (только spec). При этом ~14 канонических
сервисов вручную копируют один и тот же 5-методный CRUD. Каждый новый
объект = ~5 файлов бойлерплейта. Гибкость платформы на фронте — иллюзия.
→ Z-002.

СЛАБОЕ ЗВЕНО №3 — бэкенд не имеет generic CRUD-базы (MED).
Каждый из ~60 модулей заново пишет findAll/findById/update/remove +
пагинацию + soft-delete вручную. `optimisticLockPlugin` стоит на 4 из
72 схем. EAV-слой (целая инфраструктура) используется 1 модулем.
→ Z-003 (база/soft-delete), Z-005 (EAV).

СЛАБОЕ ЗВЕНО №4 — связность модулей растёт (MED).
`production-order` инжектит 5 чужих моделей напрямую. Цикл
order↔reservation↔shipment↔stock-movement намечается. При росте числа
сущностей это станет хрупким.
→ Z-004 (domain events).

СЛАБОЕ ЗВЕНО №5 — дублирование UI (MED).
19 страниц копируют один и тот же `role="alert"` error-блок дословно.
7 страниц обходят `app-pi-table` и пишут сырой `<table>`. 79 вызовов
`this.toast.error(extractErrorMessage(...))`.
→ Z-006.

СЛАБОЕ ЗВЕНО №6 — RBAC на чтение неформализован (LOW→MED).
Read/list endpoints оформлены кто во что горазд: одни gated через
`@Roles('admin','manager')`, другие — только JwtAuthGuard. Невозможно
рассуждать о модели видимости единообразно.
→ Z-007.

═══════════════════════════════════════════════════════════════
ЧТО ХОРОШО (НЕ ТРОГАТЬ — подтверждено аудитом)
═══════════════════════════════════════════════════════════════

- Angular 20 standalone + Signals + OnPush: 119/117 компонентов на OnPush,
  ноль `markForCheck`, ноль `@Input()`-сеттеров. `input()/computed()/signal()`
  используется консистентно. Это сильнейшая часть кодовой базы.
- Global guards chain (JwtAuth→Permissions→Roles) + интерсепторы
  (UserContext, Audit) + единый `HttpExceptionFilter` с i18n RU.
- Soft-delete через глобальный plugin + `optimisticLockPlugin` (там где
  применён) — инженерно чисто.
- `silent-http` + `httpResource` — две крепкие read-примитивы (надо только
  решить, какая каноническая — см. Z-002).
- Конвенция «одна страница = один контракт» (docs/pages) — редкая зрелость.
