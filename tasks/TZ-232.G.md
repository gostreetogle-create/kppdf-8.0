## 0. TL;DR для PO

**Что сделано в этой TZ:**

1. Создан новый standalone-обёрточный компонент `<app-pi-entity-form>`, который ОТНИМАЕТ у form-dialog'ов всю повторяющуюся submit/error/cancel/toast/SubmitGuard буилдерную обвязку.
2. Определён узкий интерфейс `EntityMutator<T>` (только `create` + `update`), чтобы диалоги могли пробрасывать свой hand-written HTTP-сервис без adapter-церемонии.
3. Мигрированы 3 ПИЛОТНЫХ диалога:
   - **WorkType** (простой без FormArray — базовый сценарий)
   - **Organization** (со своим UI: multi-role chip-toggle)
   - **Module** (с `workTypes[]` FormArray + catalog fetch на mount — самый сложный)
4. Spec покрывает SubmitGuard-интеграцию, success/error пути, валидацию формы, защиту от double-click.

> **Honest framing:** пилотные миграции #1-3 сегодня НЕ показывают чистой economy в LoC —
> wrapper overhead (~330 LoC нового wrapper + interface + spec) превышает
> boilerplate, удалённый из каждого диалога. Конкретные цифры:
> **WorkType** 144→149 LoC (+5), **Organization** 152→185 LoC (+33), **Module** 228→256 LoC (+28).
> Суммарно диалоги: 524 → 590 LoC (+66). Плюс новый wrapper-код: ~330 LoC.
> **Net для этой TZ: +396 LoC.** Реальная economy появляется с миграции #4 (Wave G.2),
> когда каждая новая миграция стоит ~50-150 LoC вместо исходных 130-370. Spec сопровождает
> эту честную framing, чтобы PO не обманывался цифрами «slimmed».

**Цель TZ:** устранить ~80% копипасты в 10 form-dialogs, обеспечив при этом:
- **Compile-time safety** — компонентные inputs требуются (`formGroup`, `payloadFn`, `mutator`), нельзя забыть одну из обязательных зависимостей.
- **Runtime safety** — SubmitGuard гарантирует, что даже если две быстрых клика пробьют UI-disable, backend всё равно получит только один запрос.
- **UX consistency** — все 10 (после Wave G.2) form-dialog'ов получают идентичную подачу ошибок + toast + cancel/submit поведение.

**Forward projection (TZ-232.G.2):** TZ-G.2 мигрирует остальные 7 диалогов (`ModuleMaterials`, `Category`, `Product`, `Order`, `Contract`, `Material`, `TableTemplate`). Оценка: ~150 LoC средняя economy на диалог = ~1,050 LoC удалено минус TZ-G net +396 LoC → net **-654 LoC** к концу G.2 + greenfield consistency на будущие dialogs. Break-even + профит достигается в одной TZ-G.2 сессии.

## 1. Определения и контракты

### 1.1 `EntityMutator<T>` (узкий интерфейс)

Файл: `frontend/src/app/shared/dsl/entity-form/entity-mutator.ts`

```typescript
export interface EntityMutator<T> {
  create(payload: Partial<T>): Observable<SilentResult<T>>;
  update(id: string, payload: Partial<T>): Observable<SilentResult<T>>;
}
```

**Почему не `EntityService<T, P>`?** Полный 5-CRUD интерфейс (list/findById/create/update/remove) НЕ НУЖЕН form-dialog'ам — list никогда не вызывается из save-флоу, findById тоже. Hand-written сервисы типа `WorkTypesService` уже реализуют `create` + `update`, поэтому вписываются структурно. Использование узкого интерфейса устраняет потребность в `toEntityService`-adapter в каждом dialog-файле.

### 1.2 `<pi-entity-form>` API surface

**Required inputs:**
- `mutator: EntityMutator<T>` — сервис, вызывающий POST/PATCH endpoint
- `endpoint: string` — для SubmitGuard composite key (`method|url|formKey`)
- `title: string` — заголовок диалога
- `formGroup: FormGroup` — родительский (dialog-owned) form
- `payloadFn: () => Partial<T>` — pure-mapping из `formGroup.getRawValue()` в API-payload
- `createSuccessMessage: string` — toast при успешном создании
- `updateSuccessMessage: string` — toast при успешном обновлении

**Optional inputs:**
- `isEdit: boolean` (default `false`) — определяет POST vs PATCH
- `width: 'sm' | 'md' | 'lg'` (default `'md'`)
- `saveLabel / createLabel: string` — лейблы submit-кнопки

**Outputs:**
- `saved: T` — эмит после успешного сохранения (до `ref.close()`)
- `cancelled: void` — на cancel

**Slots (ng-content):**
- `[fields]` — projected form fields (FormGroup + formControlName bindings)
- `[footerExtras]` — projected extra buttons на footer (левее Cancel)

**Signals exposed:**
- `submitting()` — UI-уровень lock
- `errorMessage()` — для inline error rendering
- `valid()` — `toSignal(statusChanges, { initialValue: form.valid })`

## 3. Что делает wrapper (встроенная защита)

### 3.1 SubmitGuard orchestration (TZ-232.A contract)

```typescript
const result = await this.guard.guard<T>({
  formKey: id ?? 'new',
  url,
  method,
  debounceMs: 0,            // UI-disable уже даёт быструю защиту
  fetcher: () => op,
});
```

Composite key = `method | url | formKey` гарантирует:
- PATCH `/product-modules/abc-123` отличается от POST `/product-modules` (т.е. create и update одного и того же диалога не интерферируют)
- Одновременно открытые диалоги РАЗНЫХ сущностей не интерферируют (URL-префикс уникален)

### 3.2 Rapid double-click protection

Двойная блокировка:
1. **UI-уровень:** `submitting()` signal синхронно ставится в true первой строкой `onSubmit` ДО любого await. Кнопка дизейблится моментально.
2. **Network-уровень:** SubmitGuard.inFlight Map проверяет `method|url|formKey` — если POST уже в полёте, второй вернёт `{ ok: false, error: HttpErrorResponse(429, ...) }`.

### 3.3 FormArray 100% in parent (subsumption by projection)

Wrapper не имеет специальной поддержки FormArray. Родительский dialog передаёт root `FormGroup` (содержащий `workTypes: FormArray` как дочерний control) через `[formGroup]` input. Вся разметка FormArray (включая `@for (ctrl of workTypesArray.controls)`) пишется в родительском dialog template и проецируется через `[fields]` slot.

## 8. Notes for downstream agents

- `<pi-entity-form>` imports `PiDialogComponent`, `ButtonComponent` (submit/cancel buttons), `SubmitGuard`, `PiToastService`, `DialogRef`/`PI_DIALOG_DATA`/`PI_DIALOG_REF` tokens. Heavily relies on `takeUntilDestroyed` (DestroyRef cleanup, TZ-232.A pattern). Do NOT replace with manual `ngOnDestroy` subscriptions — ESLint rule `@pi-dsl/no-takeuntil-notakeuntil-destroyed` (TODO) would flag regressions if it exists; otherwise follow TZ-232.A precedent.
- Dialog files using `<pi-entity-form>` **MUST** STILL inhect `PI_DIALOG_DATA` data — wrapper derives `isEdit` + ID via this token, NOT via @Input. Parent `dialog.open(WorkTypeFormDialogComponent, { data: existingWorkType })` contract preserved.
- Если мигрируете новый dialog и форма имеет МНОГО валидаторов — выносите `errorFor(name)` helpers в computed-сигналы, как в OrganizationFormDialog, чтобы избежать boilerplate.
