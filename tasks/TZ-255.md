## 0. Цель

- Минимальный `@Permissions('material:write', 'product:write', ...)` decorator.
- PermissionsGuard читает decorator + user — enforce.
- Canonical permission key validation against TZ-254 catalog.
- Effective permissions (union of role + user perms).
- Compatibility со старыми `@Roles()` decorators (composable, NOT replace).
- Server-side enforcement **всех** endpoints из matrix.
- Negative integration tests.

**НЕ заменять старые `@Roles`** механически без matrix.
**Никогда не** лежать на frontend единственный enforcement layer.

```typescript
export const PERMISSIONS_KEY = 'permissions';
export const Permissions = (...keys: PermissionKey[]) =>
  SetMetadata(PERMISSIONS_KEY, keys);
```

Validator-implementation: throws на non-canonical key (если не wildcard '*') при boot.

### ШАГ 2: PermissionsGuard

```typescript
// backend/src/common/guards/permissions.guard.ts
@Injectable()
export class PermissionsGuard implements CanActivate {
  constructor(
    private reflector: Reflector,
    private userModel: Model<User>,
    private roleModel: Model<Role>,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const required = this.reflector.getAllAndOverride<PermissionKey[]>(
      PERMISSIONS_KEY,
      [context.getHandler(), context.getClass()],
    );
    if (!required || required.length === 0) return true;

    const req = context.switchToHttp().getRequest<{ user?: AuthenticatedUser }>();
    const user = req.user;
    if (!user) return false;

    const effective = await this.computeEffectivePermissions(user);
    const hasAll = required.every((k) => effective.has(k));
    if (!hasAll) {
      throw new ForbiddenException(
        `Required permissions: ${required.join(', ')}`,
      );
    }
    return true;
  }
```

### ШАГ 3: Compatibility with @Roles

- Both decorators хранят metadata KEY separately — `ROLES_KEY` и `PERMISSIONS_KEY`.
- Runtime: `@Roles('admin')` + `@Permissions('material:write')` = **AND** semantics (must satisfy both).
- Existing `@Roles('admin','manager')` не блокируется: admin-managed endpoints conservatively pass on `RolesGuard`; если хотите enforce ор-семантику, добавьте `@Permissions` явно.

### ШАГ 4: Canonical key validation at boot

AppModule scan all controllers:
- Reflector.getAllAndOverride на каждый handler + class.
- Если ключ не в `PERMISSIONS_CATALOG` AND не `'*'` → throw на BootValidationModule.
- Disable-able через `NODE_ENV !== 'production' && BOOT_RELAX=1`.

### ШАГ 5: Tests

- Unit `permissions.guard.spec.ts`:
  - empty metadata → bypass;
  - exact match → allow;
  - missing 1 of N → 403;
  - wildcard * user → all permissions;
  - no user → 403.
- e2e `permissions-full.e2e-spec.ts`:
  - Для КАЖДОГО endpoint в matrix:
    - user with permission → 200;
    - user without permission → 403;
    - admin with wildcard → 200.
- Negative: missing permission → 403, not 401.

### ШАГ 6: CMake rule (microservice config)

Add to `backend/src/app.module.ts`:
```typescript
{ provide: APP_GUARD, useClass: JwtAuthGuard },
{ provide: APP_GUARD, useClass: PermissionsGuard }, // NEW, after RolesGuard
{ provide: APP_GUARD, useClass: RolesGuard },
```

(Note: order matters — JwtAuthGuard populates req.user; Permissions/RolesGuard read it.)

## 4. Критерии приёмки

1. `@Permissions('material:write')` без `'material:write'` в effective → 403.
2. `@Roles('admin')` всё ещё работает для доступов, не покрытых permissions matrix.
3. controller с `@Permissions('bad:key')` → fails на boot в production.
4. canonical key catalog concistent с TZ-254.
5. Effective permissions = role.permissions ∪ user.permissions ∪ wildcard.
6. Existing e2e tests pass (no regression).
7. backend pnpm test exit 0; pnpm typecheck exit 0.
