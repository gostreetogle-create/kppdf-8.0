# TZ-255 — Server-side permissions enforcement

**Статус:** READY / обязательный фундамент до production-админки.

**РОЛЬ АГЕНТА:** Backend Authorization Engineer + QA

**ЗАВИСИМОСТИ:** TZ-254 и TZ-251 обязательно.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/common/guards/roles.guard.ts`; `backend/src/common/decorators/roles.decorator.ts`; `backend/src/common/guards/permission.guard.ts` (NEW); `backend/src/common/decorators/permission.decorator.ts` (NEW); `backend/src/modules/**/*.controller.ts` (только endpoints из authorization matrix); `backend/src/modules/**/*.service.ts` (только object/policy checks из matrix); `backend/test/**`; `docs/DEVELOPMENT-PATTERNS.md`

## Цель

Сделать так, чтобы permissions действительно защищали API. Скрытая кнопка или frontend route guard не являются authorization. Каждый защищённый endpoint должен проверяться на сервере независимо от Angular UI.

## Что сделать

1. На основе matrix из TZ-254 выбрать минимальный механизм: например, `@Permissions('product:read')` + глобальный `PermissionGuard`, который вычисляет effective permissions пользователя и роли.
2. Явно решить режим migration: старые `@Roles()` либо остаются совместимым shortcut для system roles, либо постепенно заменяются permission metadata. Не оставлять endpoint без понятной policy из-за смешения двух подходов.
3. Провести inventory всех controller methods, включая upload/download, admin, settings, audit, rate-limit и document-constructor endpoints. Зафиксировать intentional public routes отдельно.
4. Закрыть mutation-поля `role`, `permissions`, `isActive`, system-role flags и feature/settings administration от manager/user независимо от DTO и UI.
5. Добавить отрицательные integration tests для user, manager, admin: 401, 403, чужой endpoint/action, попытка изменить role/permissions, системная запись и последний admin.

## Файлы для изменения

- Backend guards/decorators и controllers из matrix.
- Backend tests и authorization documentation.

**Не изменять:** frontend navigation до определения стабильных permission keys; не добавлять client-side-only authorization.

## Критерии приёмки

1. Любой endpoint из matrix имеет server-side permission/role policy; отсутствие UI-элемента не используется как защита.
2. Пользователь без permission получает 403 даже при ручном HTTP-запросе.
3. Admin wildcard/effective permissions работают предсказуемо, а обычный user не получает доступ из-за произвольной строки в body.
4. Роли и permission keys валидируются против canonical catalog; неизвестные keys не дают доступ.
5. Integration tests покрывают минимум users, roles, settings, audit и document-constructor.
6. Backend tests, build и lint проходят.

## Ограничения

Не мигрировать все сотни endpoint-ов механически без matrix и теста. Не внедрять ABAC и object-policy engine; ownership checks остаются областью TZ-251.
