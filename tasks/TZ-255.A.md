## 0. Контекст и причины появления

TZ-255 (Server-side permissions enforcement) формально закрыт — 26/26 unit-тестов
PASS, typecheck EXIT 0, baselines для TZ-248/249/251/254 все зелёные. Однако
code-reviewer-minimax-m3 проходом round 2 было отмечено 3 неблокирующих gap, которые
**не были решены** в основной сессии TZ-255 (сознательно, чтобы не блокировать
верификацию). Этот TZ собирает их в одну дорожную карту:

1. **Mongo e2e для PermissionsGuard** — TZ-255 §ШАГ 5 тест-плана матрица
   (user-with-perm → 200, user-without → 403, admin-wildcard → 200, no-user → 401,
   missing-perm vs missing-role distinction). Реальное Mongoose + JwtAuthGuard
   vs RolesGuard взаимодействие не проверено в основной сессии.

2. **Nest container integration test для `PermissionsBootValidator`** — текущая
   спецификация покрывает только статический `validateKeys` helper; живой
   `OnApplicationBootstrap` путь (с DiscoveryService + MetadataScanner +
   Reflector + реальной AppModule) не прикрыт unit-тестом. Reviewer отметил
   gap явно (Item 6).

3. **`__TESTING_CANONICAL_PERMISSION_KEYS` dunder naming** — non-idiomatic
   prefix в TypeScript (Python-ism). Reviewer Item 5. Низкий приоритет, чисто
   cosmetic, но лучше убрать пока ещё свежо.

## 1. Acceptance criteria

### 1a. Mongo e2e matrix (when Mongo harness available)

Файл `backend/test/permissions-full.e2e-spec.ts`, минимальная матрица
(по образцу TZ-251.A §1):

| # | Endpoint                              | User   | Required  | Expected | Rationale                                       |
|---|---------------------------------------|--------|-----------|----------|-------------------------------------------------|
| 1 | GET /api/materials                    | user   | `material:read`        | 200      | normal capability match |
| 2 | GET /api/materials                    | user   | lacks `material:read`  | **403**  | PermissionsGuard blocks BEFORE RolesGuard      |
| 3 | POST /api/materials                   | user   | lacks `material:write` | **403**  | same                                            |
| 4 | POST /api/materials                   | manager| has `material:write`   | 200      | role + capability match                        |
| 5 | GET /api/admin/users (no @Roles yet)  | user   | lacks `user:admin`     | **403**  | pure capability rejection                      |
| 6 | GET /api/admin/users                  | admin  | role='admin'           | 200      | admin shortcut via TZ-254 effectivePermissions |
| 7 | unauthenticated GET /                   | (none) | any                     | **401**  | JwtAuthGuard rejects before everything else     |
| 8 | invalid-perm decorator wired but boot-time  | (prod)  | n/a   | process exit code 1 | boot validator refuses at OnApplicationBootstrap |

### 1b. Nest container integration test

Расширение `backend/src/common/middleware/permissions-boot-validator.spec.ts`:

- mount a stub Nest `TestingModule` with a stub controller that has `@Permissions('bad:key')`;
- call `validator.onApplicationBootstrap()`;
- assert that:
  - in test mode (`NODE_ENV !== 'production'`), the warning log path is taken (NOT throw);
  - the Static.validateKeys helper returns the offending set;
- ALSO mount a stub controller with all-canonical keys; assert `onApplicationBootstrap` returns without throw.

### 1c. Dunder rename

Файл `backend/src/common/decorators/permissions.decorator.ts`:

- rename export `__TESTING_CANONICAL_PERMISSION_KEYS` → `CANONICAL_PERMISSION_KEYS_FOR_TESTS` (or relocate to a dedicated `__testing__/permissions-catalog.ts` mock);
- update TZ-251's rbac-contract + boot validator + spec imports accordingly.
