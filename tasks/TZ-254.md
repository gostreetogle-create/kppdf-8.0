# TZ-254 — RBAC contract и политика доступа

**Статус:** READY / обязательный фундамент до полноценной админки.

**РОЛЬ АГЕНТА:** Authorization Architect + Backend Security Engineer

**ЗАВИСИМОСТИ:** TZ-248 и TZ-249 желательно выполнить до начала; текущие production-изменения справочников не являются зависимостью.

**LAYER:** 4

**CONFLICT KEYS:** `backend/src/common/seed/permissions.constants.ts`; `backend/src/common/decorators/roles.decorator.ts`; `backend/src/common/guards/roles.guard.ts`; `backend/src/modules/role/role.schema.ts`; `backend/src/modules/role/role.service.ts`; `backend/src/modules/role/role.controller.ts`; `backend/src/modules/permissions/permission.schema.ts`; `backend/src/modules/permissions/permissions.service.ts`; `backend/src/modules/user/user.schema.ts`; `backend/src/modules/user/dto/*.dto.ts`; `docs/data-model.md`; `docs/data-model-audit.md`; `docs/DEVELOPMENT-PATTERNS.md`

## Цель

Зафиксировать единый authorization contract до создания админки, чтобы последующие backend guards, frontend visibility и admin forms использовали одну модель доступа.

## Почему это нужно сейчас

В проекте уже есть `Role`, `Permission`, каталог permission-ключей и глобальный `RolesGuard`, но текущие endpoint-ы в основном проверяют только строковые роли `admin/manager/user`. `User.permissions` и `Role.permissions` не образуют единый проверяемый контракт. Если сначала построить UI админки, а потом решать, что именно означает permission, придётся переделывать формы, guards, route metadata и тесты.

## Что сделать

1. Зафиксировать простой контракт: `section:action`, где `read` отвечает за просмотр, `write` — за создание/изменение, `admin` — за удаление и критические операции. Backend остаётся единственным источником истины.
2. Определить, что делает система с `Role.permissions`, `User.permissions` и wildcard admin. Выбрать один ясный вариант вычисления effective permissions; не оставлять два независимых механизма.
3. Разделить неизменяемые system roles и редактируемые custom roles. Системные роли нельзя удалить или случайно лишить минимального доступа; операции, способные оставить систему без admin, должны быть запрещены.
4. Определить policy для shared corporate data: role-based доступ применяется ко всем сотрудникам, ownership checks добавляются только для действительно user-owned сущностей.
5. Выпустить короткий authorization matrix для модулей и действий, начиная с users/roles/permissions/settings/audit и document-constructor. Устаревшие рекомендации в документации пометить явно.
6. Не переводить `User.role` на `roleId` и не вводить ABAC/tenant-политику без реальной бизнес-потребности; для команды до 10 человек текущая строковая роль может остаться совместимым storage-контрактом.

## Файлы для изменения

- Файлы из CONFLICT KEYS — только для фиксации выбранного контракта и необходимых invariants.
- `docs/**` — authorization matrix и правила для новых страниц.
- Тесты ролей/permissions.

**Не изменять:** frontend pages и навигацию; admin UI создаётся отдельными TZ после стабилизации контракта.

## Критерии приёмки

1. В документации есть одна таблица effective-permissions и приоритетов `user/role/admin`.
2. Для каждой canonical permission описаны section, action, label и серверные потребители.
3. System role invariants формализованы и покрыты тестами; нельзя удалить, деактивировать или разжаловать последнего admin-аккаунта случайным изменением роли.
4. Решение по `User.permissions` не оставляет скрытого второго authorization path.
5. New-page checklist содержит правило: backend permission first, frontend visibility second.
6. Backend tests, build и lint проходят.

## Ограничения

Не создавать новый policy engine, multi-tenancy, SSO, ABAC или отдельную permission database. Нужен один небольшой и понятный RBAC-контракт.
