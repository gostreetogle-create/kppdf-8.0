TZ-174: Добавить backend в lint-staged
═══════════════════════════════════════════════════════════════

РОЛЬ АГЕНТА: Backend Developer / DevOps

ЗАВИСИМОСТИ: TZ-173 (format:check скрипт нужен)

LAYER: 4

CONFLICT KEYS: package.json (root); backend/.eslintrc.js; .husky/pre-commit

═══════════════════════════════════════════════════════════════
ИСХОДНОЕ СОСТОЯНИЕ
═══════════════════════════════════════════════════════════════

1. Root `package.json` содержит lint-staged конфигурацию:
   ```json
   "lint-staged": {
     "frontend/**/*.{ts,html,css}": ["prettier --write", "eslint --fix"]
   }
   ```

2. Backend `.ts` файлы НЕ включены в lint-staged — коммиты с
   backend code проходят без проверки форматирования и линтинга.

3. Это создаёт situation: frontend получает auto-fix при коммите,
   backend — нет. Форматирование и lint-ошибки накапливаются.

4. Backend ESLint использует legacy `.eslintrc.js` (ESLint v8 + typescript-eslint v7).
   Frontend использует ESLint v10 + flat config. Разные версии — OK для lint-staged,
   но консистентность полезна.

═══════════════════════════════════════════════════════════════
ЧТО ДЕЛАТЬ
═══════════════════════════════════════════════════════════════

ШАГ 1: Добавить backend в lint-staged

В корневом `package.json` в секцию `lint-staged` добавить:
```json
"backend/**/*.ts": ["prettier --write", "eslint --fix --config backend/.eslintrc.js"]
```

  Под-шаг 1.1: Прочитать текущий lint-staged в root package.json
  Под-шаг 1.2: Добавить backend glob
  Под-шаг 1.3: Указать путь к backend ESLint config

ШАГ 2: Добавить format:check в pre-commit

Убедиться что `.husky/pre-commit` запускает `pnpm run lint-staged`
(уже должно быть). Если нет — добавить.

ШАГ 3: Проверить что backend ESLint работает через lint-staged

Запустить `npx lint-staged` в корне проекта с модифицированным backend/.ts файлом.
Убедиться что:
- Prettier применяется
- ESLint --fix применяется
