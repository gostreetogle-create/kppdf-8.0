## 1. Контекст

`TZ-202.B (3NF computed-field cleanup)` затрагивает User.password security surface (plaintext → bcrypt только). Per code-reviewer verdict на TZ-202 (NEED-FIX #4): User.password fix должен идти **только после** dedicated security audit. Эта TZ — это security audit **prerequisite** до старта TZ-202.B.

Architectural lineage: TZ-91 (Security Architecture baseline), TZ-91A (sensitive-endpoint throttler), TZ-104 (MongoDB injection hardening), TZ-104.5 (server-side input sanitization).

## 2. Проблема

User schema был проверен TZ-04 baseline, но **никаких recent password-storage audit'ов не было**. Audit §3.1 #7 явно flag'ит `password` как plaintext — это actively dangerous bug. Migration на bcrypt-only нон-тривиально (historical password hashes могут быть в mixed format).

## 4. Action Steps

1. **Field audit**: grep `password:.*type` в `user.schema.ts` — verify ONLY `passwordHash: string` exists (no plain `password: string` field).
2. **Hash algorithm audit**: 
   - Verify bcryptjs rounds ≥ 10.
   - Verify no legacy `md5/sha1` paths.
3. **Migration-path audit** for `password → passwordHash` consolidation (if both present):
   - bcryptjs new hash for any plain-text passwords.
   - User prompt-at-login if null hash (force-reset).
4. **Login flow audit**: ensure password input not logged accidentally.
5. **Sensitive data audit**: confirm `Audit` plugin correctly excludes `passwordHash/refreshTokenVersion` from snapshots.
6. **Output report**: `docs/security-audit-tz-205-pre-tz-202.B.md` with green-light for TZ-202.B migration.
