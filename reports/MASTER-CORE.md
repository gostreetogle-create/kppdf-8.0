## 1. Технологический стек и Архитектура

**Выжимка лучших решений, которые стоит взять в финал.**

### 1.1 Стек (проверен на 8 слоях)
- **Frontend:** Angular 20 standalone + **Signals** (никаких NgRx/RxJS-store) + `ChangeDetectionStrategy.OnPush`. Inputs через `input<T>()`, DI через `inject()`, control-flow `@if/@for`.
- **Дизайн-система:** **Paper & Ink** — Swiss-minimalism на **OKLCH**-токенах, hairline-границы (1px, без `box-shadow`), единый `pi-focus-ring`, тёмная тема через `oklch()`-оверрайды. Никаких Material/PrimeNG/AG Grid. Icons: Lucide.
- **Стили:** TailwindCSS v4 + CSS-переменные `--color-*`; запрет `#[hex]`, `bg-white`.
- **Backend:** NestJS 10 + Mongoose 8 + MongoDB 7 (**Replica Set обязателен** — атомарные счётчики/транзакции).
- **Гос. проверки:** jest (unit+e2e), ESLint (в т.ч. machine-enforced `no-raw-ui-values`), `madge` (circular deps), axe-core a11y.

### 1.2 Ключевые архитектурные решения (канон)
1. **Frontend-only SSR отменён** → CSR SPA через статические сервер (`start.mjs --prod`). (TZ-80 REJECTED — не возвращаться.)
2. **Поиск только MongoDB (regex + compound-индексы).** Vector DB вердикт CANONICAL (TZ-105.1); предусмотрен future seam на `$vectorSearch`/Qdrant, но НЕ сейчас.
3. **Pipeline данных: Signals + httpResource + silent-http.** `silentGet/Post/...` — Observable никогда не «падает», возвращает `{ok, data|error}`. Запрещены голые `subscribe({next,error})`.
4. **Против двойных сабмитов:** `SubmitGuard` (debounce → in-flight → cache) + `IdempotencyInterceptor` (Idempotency-Key).
5. **DSL CRUD:** `defineEntity<T,P>()` — фабрика 5-CRUD сервисов + `PiEntityListComponent` (список с поиском/пагинацией/сортировкой). Писать руками CRUD-страницы — анти-паттерн.
6. **Backend паттерн:** Module → Controller → Service → Schema; DTO `class-validator` (whitelist+forbidNonWhitelisted); глобальные guards/interceptors.
7. **Аудит без ручной передачи контекста:** AsyncLocalStorage → Mongoose `$locals.userId` → `auditPlugin` (createdBy/updatedBy). `@AuditAction()` интерцептор.
8. **Полнота данных по стадиям (snapshot immutability, CORE-301):** при переходах (КП→Order→shipment) встраивается deep-frozen снапшот `_snapshot {stage, capturedAt, sourceId, hash}` — правки каталога не «протекают» в архив/отгрузку задним числом.
9. **Атомарная нумерация:** Counter service — `prefix-YYYY-NNN` через `session.withTransaction` + `$inc`. Требует Replica Set.
10. **Multi-agent операция:** Team Room (OrchestratorKit) — локальный coordination с claim`ы по CONFLICT-KEYS; один репозиторий, много параллельных агентов без рассинхрона.

### 1.3 Границы и запреты (перенести в финал как есть)
- `@Input()`, constructor DI, `*ngIf/*ngFor`, `any`, `box-shadow/drop-shadow`, `#[hex]`, `bg-white`, Vector DB SDK.
- i18n: все бизнес-тексты в API на русском; UI через токены.
- Единая схема DTO frontend/backend (шелларь, а не копипаст).

## 2. Архитектура данных (Сущности)

**Просто для не-технического создателя:** система — это связанные «коробки», где каждая запись связана с другими. Ключевое: устранить дубли (в legacy-модели было **90 сущностей / 16 пар дублей**), свести к ядру.

### 2.1 Упрощённая карта — 6 главных «кирпичей»
```
  Каталог ──► КП ──► Заказ ──► Производство ──► Склад ──► Отгрузка
    (материалы,  (предложение   (договор,      (задачи,     (остатки,   (частичные
     изделия,     клиенту)      документы)      Гант, люди)  резервы)    отгрузки)
```
и вокруг них: **Контрагенты/Организации**, **Люди (инкогнито: Операция ≠ Сотрудник)**, **Документы/Шаблоны**, **Справочники**, **Финансы/Себестоимость**.

### 2.2 Связанные сущности (главные — на человеческом языке)

| Блок | Сущности | Связи (что с чем) |
|------|----------|-------------------|
| **Каталог** | Материал, Изделие, Модуль, Состав (BOM/Composition), Категория, Ед.изм | Изделие = Материалы+Модули в составе `composition[]`; до глубины 8; циклы запрещены; Product→raw материал запрещён (только через модуль) |
| **Клиенты** | Организация, Контрагент, Человек(Person), Роль-контрагента, Взаимодействия | Контрагент ⚠️ почти дубль Организации; Человек связан через ОргКонтакты; Контактные лица внутри организации |
| **Продажи** | КП (в идеале ЕДИНАЯ), Договор, Заказ, Счёт, Отгрузка, Оплата(флаг) | КП → Заказ → Договор(optional) → Склад/Отгрузка; у Заказа свой статус-FSM |
| **Производство** | Заказ-производства, Вид работ, Раб.центр, Техпроцесс, Маршрут, Сотрудник(Worker), Задача | Сотрудник связан c Видами работ и ставкой; Задача ← Заказ |
| **Склад** | Склад, Позиция-хранения, Движение, Резерв, Инвентаризация | **Остаток = сумма движений**, не поле на материале; резерв связывает Заказ↔Склад |
| **Закупки (новые)** | SupplyRequest, SupplyTask | Заменяют legacy PurchaseRequest/PurchaseOrder; закупка ≠ договор продажи |
| **Документы** | Шаблон, Тип документа, Текстовый блок, Таблица-шаблон, Сформированный документ, Реестр | Шаблон → сформированный PDF/HTML по сделке; автозаполнение из заказа |
| **Финансы** | Себестоимость/Калькуляция, Факт-стоимость, Сверка, Отчёт | Калькуляция = Σ материалов + Σ работ + overhead% (только от материалов) |
| **Доступ** | Пользователь, Роль, Право, Страница√, Изменение-аудит | Пользователь≠Сотрудник; роль выдает «страницы целиком» |

### 2.3 Критичные правила данных (решения, не трогать)
- **Валюта — только RUB.** (Удалён модуль Currency; ⚠️ но остался seed RUB/USD/EUR — см. вопрос в конце.)
- **Остаток склада SoT = StorageItem+moments**, а не поле на материале.
- **snapshot при переходе** — past заказы/отгрузки не «плывут» при правке каталога.
- **soft-delete** глобально (auto-filter `deletedAt: null`); unique index + `deletedAt: null`.
- Артикул/стабильные ключи важны для миграций и portable-export (см. фичу IDEA-001).

## 3. Целостная Бизнес-логика

**Сквозной путь «КП → производство → отгрузка», синтезированный в один бесшовный механизм.**

### 3.1 Жизненный цикл сделки (последовательность)
1. **Каталог готов** → материалы/изделия/модули с актуальной ценой и себестоимостью.
2. **Менеджер собирает КП** (одна сущность «КП», а не три дубля). Из каталога + цены + персональная наценка клиента (если есть).
3. **КП подтвердили** → «в работу» → **Заказ** (перенос состава; snapshot immutability: что было в КП — зафиксировано). Договор — **опциональный** юридический артефакт рядом, не обязательная ступень.
4. **Заказ готов к производству?**
   - Нет → **Проектирование/чертежи** (дыра №1 в текущем коде — заложить как стадию заранее).
   - Да → **Производство**: разбивка по видам работ/модулям → люди/раб. центры → задачи в **Production Cockpit (Гант план-оценка)**.
5. **Снабжение** (только если нужно докупать) — новые SupplyRequest/SupplyTask.
6. **Готово** → **Склад**: приход ГП/модулей, **резерв под заказ** (glue резерв→заказ сейчас дыра).
7. **Отгрузка частичная** — до отгрузки не списывать окончательно.
8. **Оплата/Флаг** + **Архив**: стадия/снапшот замораживается в read-only архив.

### 3.2 Статусы и FSM (важно для ядра)
- У **Заказа** должен быть единый FSM, по которому строятся остальные статусы (КП, Отгрузка, Производство фильтруют его). Не изобретать параллельные статусы на каждой сущности.
- **Остаток** — производное от движений, никогда не «ручная циферка».
- **Себестоимость**: recalc-модули × qty, snap в калькуляцию при «активации» (история стоимости не меняется задним числом).

### 3.3 Автоматизации (рекомендуемые в финал)
- **Нумерация документов** автоматически (`КП-2026-001`…), атомарно, без дублей.
- **Автозаполнение документов** из заказа/КП (шаблон → поля → PDF).
- **Аудит изменений** автоматически (кто/когда менял) — без ручной передачи контекста.
- Резерв/списание при отгрузке (после закрытия дыры glue).
- Уведомления смены статуса (сейчас нет — заложить лёгкий каркас).

### 3.4 Модель доступа (Page-level) для ~10 человек
Роли смысловые: **Админ** (пользователи), **Директор** (видит почти всё, выдаёт «страницы» галочками), **Менеджер** (КП/заказы/клиенты/документы), **Работник** (свои задачи, склад по нужде, без админки/чужих справочников). Правило: **доступ «страница целиком»**, а не кнопка×кнопка. Backend остаётся защитником (authority), FE-гейт только прячет UI.

## 4. Золотой фонд фич (Lost & Found)

**Фичи/решения, которые были хорошими и должны пережить в финал.**

| Фича | Где жила | Почему золото |
|------|----------|---------------|
| **Paper & Ink + OKLCH + hairline** | frontend | Согласованный, «дорогой» чистовой UI без борьбы с MD3 |
| **◉ Signals + silent-http + httpResource** | frontend | Детерминированный data-flow без стОра/утечек подписок |
| **Dict/CRUD DSL (`defineEntity`)** | frontend | CRUD-страницы за минуты, единый вид, меньше багов |
| **⌘K command palette** | frontend | Быстрый доступ без навигации по меню — почти в каждой ERP ждут |
| **Live OKLCH theme editor** | frontend | Возможность сменить фирменный стиль без рефактора токенов |
| **Pure-Angular SVG charts (NO d3)** | frontend | Лёгкие графики без тяжёлой зависимости |
| **Snapshot immutability (CORE-301)** | backend | Заказ/отгрузка/архив не «плывут» при правке каталога — trust |
| **Атомарные счётчики `prefix-YYYY-NNN`** | backend | Номера документов никогда не дублируются |
| **Audit-плагин + AsyncLocalStorage** | backend | «Кто и что менял» бесплатно, без ручного кода |
| **Idempotency-Key + SubmitGuard** | frontend/backend | Двойной сабмит ≠ двойной заказ (последствие бага на проде) |
| **Excel/фото импорт (desktop, Wave 4)** | desktop | Быстрый ввод каталога, который людей утомляет руками |
| **Portable Export / Excel-пакет (IDEA-001)** | docs/бэклог | «Данные предприятия у PO в сейфе», DR, лёгкая миграция — высокая ценность |
| **Studio S2 с честной геометрией A4** | frontend-nx | Документы как на бумаге (альбомный ratio 1.414, не искажение 1.726) |
| **Себестоимость/калькуляция** | backend/frontend | КП не «на глаз», а по факту материалов + работ |
| **Реестры + capabilityRouteGuard** | frontend-nx | Организованный список справочников с правами |
| **Team Room multi-agent** | OrchestratorKit | Параллельная разработка без конфликтов на одном репо |

**Потерянные в поздних версиях (вернуть/решить):**
- `Interaction` (звонки/встречи/письма) — единственный «CRM-ускоритель», который vision сознательно выкинул; мини-версия (единый таймлайн сделки) золотая.
- `personalMarkupPercent` (персональная наценка клиента) — при консолидации Client→Counterparty не потерять.
- Wild `Employees`/`Client`/`Roles` дубли — консолидировать, не носить дальше.
- `Tender/закупки` — богатая модель; решить «рабочая закупка» это или только SupplyRequest (см. вопросы).

## 5. Чек-лист вопросов для Создателя

> Противоречия/дыры, найденные в бизнес-логике. Задаю **в самом конце** — до фиксации ядра.

1. **Одна ли сущность «КП»?** В модели есть Proposal и Quotation (дубль), плюс Договор отдельно. Канон production-vision говорит «одна КП-сущность, не три дубля». Как правильно: КП единая + отдельный Договор, или КП→Договор это стадии одной сделки?

2. **Order.status FSM.** У Заказа в модели много статусов, а отдельные сущности (Invoice, Shipment, OrderClosing) живут сами по себе. Делать единый FSM заказа, как единственную правду, по которой движутся склад/отгрузка/производство?

3. **CRM в ядре или нет?** Vision «не наше»: звонки/активности/CRM out of scope. Но модель хранит `Interaction` и есть `/counterparties`. Нужна ли вообще таймлайн взаимодействий по сделке, или сознательно убрать навсегда?

4. **Закупки: новые или legacy?** Есть и legacy (PurchaseRequest/PurchaseOrder/Tender) и новые (SupplyRequest/SupplyTask). Какие сущности закупок — рабочий канон финального ядра?

5. **Валюта.** Решение «только RUB», модуль Currency удалён, но в seeds остался RUB/USD/EUR. Окончательно: только ₽, или заложить multi-currency заранее (миграция дороже на пустом месте)?

6. **Кто логинится: Сотрудник или Пользователь?** `Worker` (табельные данные/ставки) отдельно от `User` (аккаунт), связь опциональная через `userId`. Сотрудник должен сам заходить в систему, или учёт ведёт менеджер?

7. **Глубина склада.** Vision: «склад по мере необходимости, не второй SAP». Модель: полные Warehouse/StorageItem/reservation/инвентаризация. Насколько глубоко делать остатки в финале (просто остатки vs полный многоскладский учёт с резервами)?

8. **Отгрузка/оплата до конца.** Флаг оплаты и отгрузка в vision отложены. Нужна ли цепочка Оплата→Отгрузка→Закрытие как обязательная стадия, чтобы КП-заказ считался завершённым?

9. **Проектирование/чертежи — стадия №1.** В vision это «дыра №1». Закладывать стадию «Проектирование/чертежи» как обязательную между Заказом и Производством, или она optional?

10. **Два фронтенда.** Есть legacy `frontend/` и новый `frontend-nx/` — это два параллельных приложения. Финальный продукт живёт в каком? Какой из двух — база для ядра (иначе дублирование усилий навсегда)?

11. **Масштаб людей и ACL.** «~10 пользователей, страница-целиком» vs развитая permission-system (capability:key, `user:admin`). Оставить страничный доступ как осознанный выбор (проще), а детальную защиту только на деньгах/пользователях?

12. **Archived-будущее данных.** Portable Export (IDEA-001): v1 из чего (каталог+материалы+медиа?) и нужен ли человекочитаемый Excel-пакет параллельно с machine-first JSON?
